# DataForSEO 수집 기능 업데이트

> 적용 예정일: 2026-11-18

프롬프트 라이브러리에서 Google AIO, Google AI Mode, Naver AIO 검색 결과를 SERP API로 수집할 수 있습니다.

## 달라진 점

- 수집을 시작하기 전에 예상 요청 수와 비용을 확인할 수 있습니다.
- 수집 중인 항목은 프롬프트 라이브러리와 수집 로그에서 확인할 수 있습니다.
- 페이지를 이동했다가 돌아와도 진행 중인 수집 내역이 다시 표시됩니다.
- 아직 API에 제출되지 않은 작업은 `수집 대기`로 표시되며, 직접 제출하거나 삭제할 수 있습니다.
- 이미 같은 프롬프트를 수집 중이라면 해당 작업의 시작 시각과 검색 엔진을 안내합니다. 그래도 다시 수집할 때만 확인 후 중복 수집을 진행합니다.
- 여러 프롬프트를 한 번에 선택해 대량으로 수집할 수 있습니다.

## 알아두세요

- API에 제출된 수집은 페이지를 떠나도 계속 진행됩니다. 다만 현재는 별도 서버 worker가 없으므로, 페이지를 떠난 동안 완료된 결과는 프롬프트 라이브러리나 수집 로그 페이지에 다시 진입했을 때 반영됩니다. 따라서 수집 중에는 페이지를 이탈하지 않는 것을 권장드립니다.
- 대량 수집은 모든 작업이 API에 제출(수집 시작)될 때까지 해당 페이지를 유지하는 것이 안전합니다.
- SERP API 수집은 실제 API 비용이 발생합니다.
  - Google AIO: 건당 $0.0024
  - Google AI Mode: 건당 $0.0012
  - 네이버 AIO: 건당 $0.0006

## 작업 큐 전환 변경 기록

### 2026-11-18

- 수집 요청 상세의 별도 미완료 수집 섹션을 제거하고, 실행 목록 안에 ‘실패 항목 전체 선택’과 ‘수집하기’를 배치했습니다. 전체 선택은 필터·페이지와 관계없이 해당 요청의 로컬·SERP API 실패 건을 선택하며, 개별 체크도 가능합니다.
- 프롬프트 라이브러리처럼 선택 → 엔진·수집 방식·기기 및 SERP 예상 총액 확인 → 수집 진행 흐름으로 재수집합니다. 선택한 SERP 항목도 새 요청으로 등록하며, 원본 요청·작업과 연결합니다. 제출 여부 확인 필요나 저장 결과 복구 대상은 유료 재수집 대상에서 제외합니다.
- 개발 DB에 여러 엔진이 섞인 실패 fixture 요청 1개를 추가했습니다(로컬 5건 + SERP API 4건). 생성 과정은 외부 API를 호출하지 않으며, 모든 항목을 실패·취소 상태로 한 번에 저장해 자동 실행되지 않습니다.
- 화면의 ‘레거시 수집’ 표현을 ‘로컬 수집’으로 통일했습니다. 요청 상세에서 로컬 항목의 수집 대기·수집 중 상태를 구분합니다.
- 요청 상세에 현재 페이지 전체 선택·개별 선택과 선택 수집 시작·대기 취소·재시도 버튼을 추가했습니다. 확인 모달에서 선택 항목과 고정된 엔진을 확인한 뒤 실행하며, 기존 선택 수집 진행 모달을 공유합니다.
- 시작·재시도는 선택한 항목만 원본에 연결된 새 요청으로 실행하고, 원본 이력은 보존합니다. 완료 항목·SERP API는 제외하며, 다른 화면에서 수집 중인 항목은 중복 실행·취소하지 않습니다. 대기 취소는 외부 API 호출 없이 기록만 남깁니다.
- DB 롤백 테스트로 선택 범위·미선택 항목 보존·최근 세션 중복 차단·대기 취소와 선택 시작을 검증했습니다. 실제 유료 수집 호출은 하지 않았습니다.
- 혼합 수집 모달에서 SERP API는 레거시 완료와 관계없이 바로 등록된다는 안내를 명확히 했고, SERP 전용 등록 화면의 '계속 작업' 버튼을 제거했습니다.
- 로컬 서버 수집 모드에 남아 있던 순차 실행 분기를 통합 모달로 바꿔 SERP 등록이 레거시 완료를 기다리지 않도록 했습니다. 로컬 AI 수집 결과도 같은 요청에 연결합니다.
- 모달 종료·페이지 이탈 시 미완료 레거시 항목을 중단 처리하고, 요청 상세에서 사용자가 확인 후 해당 항목만 새 요청으로 다시 시도하도록 연결했습니다. 완료 항목과 SERP 작업은 재제출하지 않으며, 최근 실행 중인 요청의 중복 재시도를 막습니다.
- 구글 AIO 재시도는 미완료 프롬프트·기기 조합으로 한정합니다. 재시도 이력과 원본 요청을 연결하고, Gemini 항목이 포함되면 추가 API 비용 가능성을 안내합니다.
- 수집 요청 목록에서 행 전체를 클릭하거나 키보드로 선택해 상세로 이동할 수 있도록 바꿨습니다. 상태는 대기·진행·완료·일부 실패·확인 필요·취소별 색상 배지로 표시합니다.
- 이전 개별 수집 이력에서 SERP API 요청 현황 섹션과 해당 요약 조회를 제거했습니다. 상세의 실시간 현황과 대기 요청 조작은 다음 소작업입니다.
- 수집 현황 위치·대기 요청 조작·목록 행 클릭과 상태 배지에 대한 새 요청을 사용자 원문 그대로 최우선 작업에 기록했습니다. 구현과 검토는 아직 수행하지 않았습니다.
- 요청 상세와 이전 개별 이력의 '수집 실행 목록'을 같은 컴포넌트로 통합했습니다. 열 구성, 검색, 행 펼치기, 원문·인용, 페이지 이동과 분석 버튼을 공유하며 요청 상세의 원문 조회는 요청 소속을 검사합니다.
- 이전 개별 이력은 요청 연결이 없는 과거 버전의 하위 호환용입니다. 새 선택 수집은 레거시 전용·혼합 수집 모두 같은 요청으로 등록하고, SERP·레거시 항목을 합산해 동일 목록과 상세에 표시하도록 연결했습니다.
- 네이버·구글 AI·Gemini·구글 AIO의 결과 저장에 명시적인 요청 ID를 연결하고 레거시 대기·진행·실패·중단 상태를 기록합니다. 실제 유료 수집 호출 없이 DB 트랜잭션 롤백으로 등록 중복 방지와 결과 연결을 확인했습니다.
- 수집 로그 진입 시 요청별 목록을 기본으로 표시하도록 변경했습니다. 기존 개별 이력은 별도 버튼으로 접근합니다.
- 요청 목록·상세의 바깥 여백을 24px, 최대 너비를 기존 로그와 동일하게 맞추고, 섹션 간격·필터 높이·목록 셀·페이지 이동 영역의 여백을 정리했습니다.
- 기존 수집 로그에 '수집 요청별 보기'를 추가했습니다. 요청 목록에서 검색·상태·엔진 필터와 페이지 이동을 사용하고 요청 상세의 건수·비용·개별 항목을 확인할 수 있습니다.
- 레거시와 과거 이력은 기존 화면에서 계속 확인하도록 유지했습니다. 상세의 원문·인용 펼치기, 단계별 시각화와 재제출 화면 연결은 후속 작업입니다.
- 수집 요청 요약과 요청별 개별 항목 조회 API를 추가했습니다. 대기·실패·확인 필요 항목도 결과 생성 여부와 관계없이 조회할 수 있습니다. 화면 연결은 아직 적용 전입니다.
- 요청의 조직·브랜드 범위를 검사하고, 동일 작업에 결과가 여러 개 있어도 최신 결과 한 건만 연결합니다. PostgreSQL에서 범위 차단·결과 없는 항목·중복 방지를 검증했습니다.
- 수집 요청 목록을 조회하는 API를 추가했습니다. 조직·브랜드별로 요청을 구분하고 상태·엔진·기간·검색 조건, 전체 건수와 페이지네이션을 지원합니다. 화면 연결은 다음 단계입니다.
- 엔진으로 필터해도 요청 전체의 건수와 실제 비용을 유지하며, 진행 상태는 개별 작업의 현재 상태를 합산해 표시하도록 했습니다. 실제 DB의 임시 테이블로 범위 제한과 집계를 검증했습니다.
- 수집 요청별 목록과 상세 화면을 위한 데이터 연결과 조회 API 계약을 정리했습니다. 완료 결과가 없는 작업도 표시하고, 요청 전체의 상태·비용을 일관되게 집계하도록 기준을 정했습니다.
- 레거시 수집과 과거 이력을 계속 확인할 수 있도록 기존 로그 화면을 유지하며 단계적으로 전환하는 순서를 기록했습니다. API와 화면 구현은 다음 단계입니다.

> 상태: 개발 중 · 현재 수집 화면과 실행 방식에는 아직 적용되지 않음

### 2026-11-17

- 로컬 mock 수집의 사용자 확인을 기록했습니다. 다음 작업은 수집 로그를 '수집 요청 목록 → 요청 상세의 개별 항목' 구조로 개편하는 것이며, AEMaaCS 파이프라인 실행 상세를 참고한 지침과 남은 작업 순서를 문서에 정리했습니다. 화면 개편은 아직 적용 전입니다.
- Vercel 연결 없이 같은 DB 작업 큐를 처리하는 로컬 worker와 환경변수로 선택하는 가짜 응답 모드를 추가했습니다. 가짜 결과는 테스트 문구와 실제 비용 0으로 기록하며 외부 API를 호출하지 않습니다.
- 로컬 실행 방법과 큐 전환 후속 작업의 복귀 지점을 `LOCAL-WORKER.md`에 기록했습니다.
- 개발 모드에서 SERP API 등록 요청이 React의 효과 재실행 중 취소되고 오류로 표시되던 문제를 해결했습니다. 실제 취소된 요청은 실패로 표시하지 않고 등록을 다시 시작합니다.
- 기존 `provider_tasks` 테이블에 `query_snapshot`이 없는 환경도 데이터를 보존하며 자동 보정하도록 전진 마이그레이션을 추가했습니다.
- SERP API 작업 등록 실패 시 일반 안내만 표시하지 않고 서버가 반환한 실제 오류 사유도 확인할 수 있게 했습니다.
- 승인한 SERP API 수집을 요청 단위로 안전하게 보관할 수 있는 기반을 추가했습니다.
- 사용자가 승인한 수집 건수와 예상 비용을 하나의 요청으로 저장하고 다시 확인할 수 있게 준비했습니다.
- 승인된 요청과 그 안의 개별 수집 작업이 일부만 저장되지 않도록 하나의 처리 단위로 묶었습니다.
- 최대 2,000건 규모의 수집도 개별 저장 요청을 반복하지 않고 한 번에 등록할 수 있도록 대량 예약 방식을 추가했습니다.
- 여러 서버가 동시에 작업하더라도 설정된 동시 수집 수를 넘지 않고, 중단된 서버가 잡고 있던 미제출 작업은 일정 시간 뒤 안전하게 이어받도록 준비했습니다.
- 서버가 선점한 작업만 최초 제출하고, 접수 여부가 불명확한 작업은 비용 보호를 위해 자동으로 다시 제출하지 않도록 Submit worker를 추가했습니다.
- 제출된 작업은 조회 예정 시각이 된 건만 서버가 회수하고, 아직 처리 중이면 다음 확인 시각을 예약해 불필요한 반복 조회를 줄였습니다.
- 수집 로그의 진행 확인은 이제 Provider 작업을 직접 실행하지 않고 저장된 상태만 조회하며, 보기 권한이 있는 사용자도 최신 상태를 확인할 수 있습니다.
- 수집 로그 상단에서 최근 SERP API 요청별 전체 건수, 완료율, 대기·처리·실패 건수와 예상·사용 비용을 한눈에 확인할 수 있습니다.
- 페이지 진입 시 사이드바의 수집 로그 메뉴에서 진행 중인 작업과 사용자 확인이 필요한 작업 수를 확인할 수 있습니다.
- 화면과 독립적으로 결과 회수 후 신규 제출을 이어갈 수 있는 인증된 작업 큐 실행 진입점을 준비했습니다.
- 프롬프트 라이브러리는 SERP API 작업을 큐에 등록한 뒤 반복 조회하지 않으며, 이후 진행 확인은 수집 로그에서 하도록 분리했습니다.
- 프롬프트 라이브러리에 다시 들어와도 진행 중인 SERP API 작업 때문에 진행 모달이 자동으로 열리지 않도록 변경했습니다.
- SERP API만 수집할 때는 작업 큐 등록 결과와 수집 로그 이동만 안내하고, 레거시 수집을 함께 실행할 때는 기존 진행 화면을 유지하도록 정리했습니다.
- 혼합 수집 화면에서 SERP API는 진행률 패널 대신 서버 작업 큐 등록 상태로 구분해 표시합니다.
- 한 번의 사용자 승인에서 나뉘어 들어오는 엔진·배치 요청을 하나의 수집 요청으로 식별할 수 있도록 실행 ID 저장 기반을 추가했습니다.
- 프롬프트 라이브러리의 실제 예약 API가 같은 실행 ID의 수집 요청을 재사용하고, 새로 만든 Provider 작업만 건수와 예상 비용에 누적하도록 연결했습니다.
- 이미 진행 중인 작업을 재사용하거나 같은 예약 요청이 다시 도착해도 수집 요청 비용이 중복 집계되지 않도록 처리했습니다.
- 예약 작업이 생기면 Vercel Queue가 worker를 깨우고, 처리할 작업이 남은 동안에만 지연 메시지로 후속 실행하도록 이벤트 기반 실행 경로를 추가했습니다.
- 큐 메시지 발행은 실행 플래그로 분리했으며, 작업 ID 기반 중복 방지 키로 같은 예약 요청이 다시 도착해도 불필요한 worker 호출을 줄였습니다.
- Provider 제출 도중 서버가 종료되어 오래 `submitting`에 머문 작업은 자동 재제출하지 않고 `확인 필요` 상태로 격리하는 stale-task sweeper를 추가했습니다.
- 최근 제출이거나 기존 worker lease가 살아 있는 작업은 sweeper가 건드리지 않도록 보호했습니다.
- 요청 묶음과 각 수집 작업을 연결하고, 서버가 중단된 작업을 이어받을 수 있도록 필요한 기록 항목을 준비했습니다.
- 이용량이 늘어도 화면 서버 전체가 아니라 수집 처리 부분만 확장할 수 있도록 실행 영역의 분리 기준을 정했습니다.
- 이후 화면을 닫아도 서버가 남은 제출과 결과 반영을 이어가고, 수집 로그에서 요청 전체의 진행 상황을 확인할 수 있도록 단계적으로 적용합니다.
