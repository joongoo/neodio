- 요청 상세는 기존 개별 이력과 동일한 `CollectionRunList` 컴포넌트와 열·원문/인용 펼치기·분석·페이지 이동을 사용한다.
- 새 선택 수집은 레거시 항목을 시작 전에 등록하며 SERP와 같은 요청 ID로 묶는다. `legacy_collection_items`, `collection_execution_items` 뷰와 import/Gemini/AIO 연결을 추가했다.
- 실제 Provider 호출 없이 관련 테스트 74개, TypeScript와 ESLint를 통과했다. 실제 레거시 수집과 브라우저 시각 검증은 별도로 필요하다.
- 이번 최우선 요청은 원문 기록만 수행했다. 실행 방식·정책·폴링 타당성은 다음 구현 시 판단할 사항이며 이번 기록에서 확정하지 않는다.
- 원래 잔여 작업은 아래에 유지한다. 최우선 요청을 마친 뒤 재제출·취소의 남은 부분, 단계별 상태 표현, 예산·운영 보호와 배포 검증으로 돌아간다.

## 새로 확정한 수집 로그 구조

수집 로그의 기본 목록은 개별 결과가 아닌 **수집 요청 한 건당 한 행**으로 변경한다. 요청을 클릭하면 별도 상세 페이지로 들어가고, 그 안에서 해당 요청의 개별 항목을 현재 수집 로그 테이블 형태로 확인한다. 기존 상단 요청 요약 카드를 추가하는 수준이 아니라 목록의 기본 단위를 변경하는 작업이다.

이 상세 페이지에서는 polling을 5초에 1번 수준으로 해도 될 지 검토 필요.

### 요청 목록

- 한 번의 사용자 수집 승인으로 생성된 `collection_request`를 한 행으로 보여준다. 엔진·배치·기기가 나뉘어도 같은 요청을 중복 행으로 만들지 않는다.
- 요청 식별자, 요청자, 등록 시각, 엔진 구성, 전체 항목 수, 완료/대기/진행/실패/확인 필요 건수, 예상·실제 USD 비용을 표시한다.
- 상태·기간·엔진 필터, 정렬, 서버 페이지네이션을 제공한다. 첫 화면을 최근 5개 요청 요약에 한정하지 않는다.
- 진행 중이거나 실패했거나 아직 결과가 없는 요청도 목록에 포함한다. 결과 테이블만 기준으로 목록을 만들지 않는다.
- 행을 누르면 해당 요청 상세로 이동하고, 뒤로 돌아올 때 목록 필터와 페이지를 유지한다.

### 요청 상세

- 제안 경로: `/{org}/{brand}/collection-runs/{requestId}`. 기존 개별 항목 상세 API와 혼동하지 않도록 이름과 계약을 정리한다.
- 상단에 요청 ID, 전체 상태, 요청자·시각, 엔진·기기 구성, 건수와 비용 요약, 원본 요청/재제출 요청 연결을 둔다.
- AEM 파이프라인 실행 상세처럼 등록 → 제출 → 결과 회수 → 저장의 흐름을 표현한다. 각 항목은 병렬 실행되므로 전체 요청이 한 단계씩 직렬로 이동하는 것처럼 표시하지 않는다. 단계별 건수와 개별 항목의 상태를 함께 확인하도록 설계한다.
- 본문에는 **현재 수집 로그의 개별 항목 테이블**을 재사용한다. 현재 제공하는 결과 확인 기능은 상세 안으로 이동한다.
- 테이블은 해당 요청 소속 항목만 서버에서 조회하고, 프롬프트·엔진·기기·상태·시간·비용·오류·결과를 확인할 수 있게 한다.
- 미제출·처리 중·실패·확인 필요 항목도 행으로 보여준다. 정상 결과가 생성되지 않았다는 이유로 항목을 숨기지 않는다.
- 상태별 필터와 페이지네이션, 개별 항목 결과/오류 상세, 선택한 실패 건의 명시적 재제출을 제공한다.
- 완료된 항목의 결과는 요청 전체 종료를 기다리지 않고 즉시 열람할 수 있다.
- 읽기 권한 사용자는 조회하고, 제출·재제출·미제출 취소는 기존 쓰기 권한을 따른다. 요청 ID 직접 접근에도 조직·브랜드 범위를 검사한다.

### 레거시·혼합 수집과 과거 이력

- 최종 목표는 SERP API와 레거시 수집 모두 동일한 사용자 승인 요청에 연결하는 것이다. 혼합 수집도 요청 한 행에서 각 실행 경로의 상태를 확인한다.
- 현재 `collection_requests`와 레거시 `collection_jobs`의 연결 여부를 먼저 조사하고, 레거시 항목을 요청 상세로 이동하기 위한 연결을 구현한다.
- 과거 이력은 실제 job/request 관계가 확인되는 경우 그 단위로 묶는다. 시각이나 프롬프트 유사성만으로 서로 다른 실행을 임의 병합하지 않는다.
- 요청 연결 정보가 없는 과거·수동 import 이력을 어떻게 노출할지 구현 전 정리한다. 필요하면 '이전 개별 수집 이력' 진입점을 유지해 기존 결과를 계속 찾을 수 있게 한다.
- 활성 task를 재사용할 때 원래 요청 소유권을 바꾸거나 비용을 중복 집계하지 않는다. 새 요청에서 재사용 항목을 어떻게 안내할지는 현재 예약 API 계약과 맞춘다.

## 유지할 결정

2026-11-18 레거시 연결 구현: 새 선택 수집을 시작하기 전에 legacy_collection_items에 항목을 등록하고 같은 clientRequestId로 SERP 요청과 합친다. requestLog/requestItems는 collection_execution_items 뷰로 두 경로를 합산한다. import·Gemini·AIO(로컬/설치형) 결과를 요청에 명시적으로 연결하고 실행 목록 컴포넌트를 재사용한다. 실수집과 브라우저 시각 확인은 별도로 필요하며 과거 행을 시간 기준으로 자동 병합하지 않는다. 요청 ID를 전달하지 않는 독립 수집 진입점은 기존 이력에 유지한다. 새 선택 수집에서 브라우저가 완전히 종료되면 레거시 미반영 상태의 정합성 복구는 추가 운영 과제다.
