# 04. IDEA_EXTRACTION — geo-visibility-lab → Neodio

## 0. 이 프로젝트의 성격

앞의 두 프로젝트보다 **작고 방법론 중심**이다. 제품 구조는 가져올 게 없고(로컬 파일·단일 브랜드), 가치는 **측정의 정직함에 대한 규율**(0과 미측정 구분, 비교 가능성 지문, 증거 층 분리)과 **브랜드 매칭의 정확도 처리**에 있다.

## 1. Neodio를 직접 확인해서 발견한 사실 (이번 분석의 가장 실용적 결과)

`src/lib/backend/processing/text.ts`의 `findBrandMentions`는 영문/숫자 별칭에도 **단어 경계 검사 없이** `escaped + (선택 조사)` 정규식으로 매칭한다.
- 한국어는 조사 처리 덕분에 좋지만, **짧은 라틴 별칭**(예: 약어 `AI`, `HLY`류, 3~4자 영문 브랜드)이 다른 단어 안에서 일치할 수 있다는 코드상 가능성이 있다. 실제 데이터 영향은 **미측정**.
- 반면 원본은 이 케이스를 테스트로 고정해 둠. → I1.

그 외 Neodio 상태(이미 있는 것): 질문 세트 변경 이력(`config_versions`, `change_log`), 실행 결과 상태(`getRunOutcome`), 미측정 "–" 표시, 반복 실행 가중.

## I1. 문자 체계 인지 브랜드 매칭 + 별칭별 근거 보존

1. 문제: 브랜드명/별칭이 일반 단어·약어일 때의 오탐, 그리고 "왜 언급으로 셌는지" 설명 불가
2. 입력: 응답 텍스트, 브랜드명·별칭(한/영/일 혼합)
3. 출력: 별칭별 일치 위치·횟수, 확정 스니펫, 문자 체계별(한글/라틴/한자/가나) 구분
4. 요구: 한국어 조사 허용 유지 + 라틴 별칭 경계 적용 + 숫자·하이픈·점 포함 약어 처리
5. 원본 한계: 한국어·일본어 처리 없음(CJK 범위만), 스니펫 길이 고정, 검증 세트 없음
6. 일반 원리: 유니코드 정규화(NFKC), 문자 범주별 경계 규칙, 스팬 병합(긴 별칭 우선)
7. Neodio 대안: 문자 체계별 규칙 + **골드셋(오탐/미탐 케이스 목록)** 으로 고정 + 매칭 근거(스팬)를 `brand_observations`에 보존
8. 개선: 별칭 단위 통계(어떤 별칭이 실제로 일치를 만드는지) → 브랜드 관리 화면에서 불필요/위험 별칭 제안
9. 검증: 기존 실데이터에 새 규칙을 **그림자 실행**해 차이 건수·샘플을 사람이 점검(정확도 우선)

## I2. 신원 신뢰도 (동명 브랜드 구분)

1. 문제: 일반명사형 브랜드명·동명 기업을 자사 언급으로 잘못 셈
2. 입력: 매칭 스팬, 응답 내 공식 도메인 인용, 정식명 동반, 브랜드 사업 키워드, 주변 문맥
3. 출력: 언급별 신원 신뢰도 등급(확정/개연/미확인)과 증거 목록
4. 요구: 지표에 어떻게 반영할지 사전 정의(등급별 가중 또는 제외 기준) — **원본은 반영 규칙이 없음**
5. Neodio 대안: 등급을 우선 별도 필드로만 저장·표시하고, 골드셋으로 정밀도 확인 후 지표 반영(정확도 우선 원칙). 프로젝트 2의 답변 평가기(D4)의 입력 신호로도 사용 가능
6. 검증: 동명/일반명사형 브랜드 샘플 세트에서 등급별 정밀도

## I3. 비교 가능성 지문 (Comparability Key)

1. 문제: 질문·설정을 조금 고치면 과거와 비교가 조용히 어긋남
2. 원본 방식: 비교에 영향 주는 필드만 정렬 해시 → 같으면 추세 연결, 다르면 분리
3. Neodio 현황: 프롬프트 편집은 `change_log`에 기록되지만, **지표 추세가 편집 전후를 이어 그리는지/끊는지**는 **미확인**
4. Neodio 대안: 지문을 "프롬프트 집합" 단위가 아니라 **(프롬프트, 엔진, 마켓, 분석 버전) 단위 키**로 두고, 추세 계산 시 같은 키 구간끼리만 비교하거나 구간 경계를 시각 표시. 변경이 지표에 미치는 영향 경고(예: "이번 주 프롬프트 12개 수정됨")
5. 검증: 과거 편집 이력을 재생해 추세 단절 지점이 의도와 일치하는지 점검

## I4. 실행 설정 스냅샷 (재현성 증거)

1. 프로젝트 2의 "실제 적용 지역/전송 문장" 아이디어와 합쳐 하나의 **재현성 봉투(envelope)**로 설계: 모델 식별자, 온도·토큰·타임아웃, 웹 검색 여부, 지역, 실제 전송 문장, 토큰 사용량, 비밀 제외
2. Neodio 현황: `llm-collection.md`에 웹 검색 on/off와 모델 환경변수는 있으나 **실행별 스냅샷 저장 여부는 미확인**(`rawMetadata` 확인 필요)

## I5. 실패 분류의 안정화

1. 원본: 오류 **문자열**로 분류 → 취약
2. Neodio 대안: 어댑터가 **구조화 오류 코드**(제한/타임아웃/인증/파싱/정책거부)를 직접 반환하도록 계약화(`LlmProvider` 계약 확장). 상태는 "미측정"과 "0"을 구분(이미 일부 구현)
3. 이는 프로젝트 2의 D5(내구성 잡)의 재시도 정책과 직접 연결

## I6. 치명 오류 단락과 안전한 재시도

1. 인증/쿼터 오류 시 남은 호출 중단 → D5 요구사항에 반영
2. 원본의 약점(성공 모델 재호출)을 반면교사로 D5의 멱등 키로 해결

## I7. 드라이런 기본 + 호출 수 사전 계산

→ 프로젝트 1의 D1(비용 거버너)의 `previewCost`에 흡수. 별도 설계 없음.

## I8. 증거 층 분리 원칙 (제품 메시지)

"모델 답변 / 검색 발견성 / 일반 검색 색인 / 분석 트래픽 / 비즈니스 문의"를 서로 다른 증거로 취급하고 인과를 단정하지 않는다. Neodio의 GSC·LLM·(예정)CDN 로그를 화면에서 섞어 인과를 암시하지 않도록 하는 **UX/카피 원칙**으로 채택(도움말 "가시성 숫자는 이렇게 읽으세요"와 일치).

## 버리는 아이디어

- 증거 제한 질의("투명 복제")를 핵심 측정으로 사용: 소비자 AI 노출과 다른 지표 → Neodio의 실측 철학과 충돌. 단, **콘텐츠 점검 보조 진단**("이 증거가 주어지면 모델이 우리를 언급할까?")으로는 DEFER
- 로컬 JSON 파일 저장, 루프백 서버, 파일 잠금
- 중국 검색/모델 공급자 종속 구조
- 에이전트 플러그인 배포(Neodio는 SaaS)
