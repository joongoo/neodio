# 04. IDEA_EXTRACTION — langfuse → Neodio

## 0. 성격

Langfuse는 GEO 도구가 아니라 **대규모로 검증된 플랫폼 공학 사례**다. 아이디어는 Neodio의 기능이 아니라 **Neodio 기반 구조(D1, D4, D5 및 보안)를 단단히 하는 요구사항**으로 흡수한다. 새 사용자 기능은 거의 없다.

## 1. Neodio 현황 (직접 확인)

- 수집 잡: 프로세스 메모리 Map + 자식 프로세스 (`collectionJobRunner.ts`)
- 분당 호출 제한: 서버 인스턴스 메모리 (`rateLimit.ts`, 문서 기준)
- 원본 보존: `prompt_runs.rawResponse`(DB 컬럼)에 보관, `process-raw.ts`로 재처리 가능 — 이미 "원본 먼저" 철학
- LLM 호출: 어댑터 계약(`LlmProvider`), 호출 비용 추적은 확인되지 않음
- URL 가져오기: `pageText.ts`가 "IP·localhost 거부, 리다이렉트마다 재검사"(문서 기준) — **연결 시점 IP 검증 여부 미확인**

## I1. 원본 우선 영속 + 참조 전달 + 테넌트 격리 큐 (D5 보강)

1. 문제: 대량 수집 시 한 조직의 폭주·저장소 장애가 전체를 멈추거나 데이터를 잃게 함
2. 입력: 수집 결과(대용량 가능), 조직 id
3. 출력: 유실 없는 영속, 조직별 공정한 처리, 장애 격리
4. 요구: ① 본문은 안전한 저장소에 먼저 쓰고 큐에는 참조만 ② 조직 키 기반 분산 ③ 특정 조직의 연속 실패 시 그 조직만 별도 레인으로 분리 ④ 부분 성공 결과를 항목 단위로 보고
5. 원본 한계: Redis·객체 저장소·별도 워커가 모두 전제, 임시 휴리스틱 다수
6. 일반 원리: 아웃박스/클레임 체크 패턴, 샤딩, 서킷 브레이커, 벌크헤드(격벽)
7. Neodio 대안: 이미 PostgreSQL이 있으므로 **DB 기반 큐(D5)** 로 시작하고, 원본이 커지면(수백 KB~MB 응답/HTML) 객체 저장소로 분리하는 **전환 기준**을 문서화
8. 개선: 원본이 아직 작은 지금은 큐 인프라를 늘리지 않는 쪽이 더 단순 — 원본 아이디어를 "필요해질 때" 단계로 구분
9. 검증: 한 조직에 인위적 장애를 주입해도 다른 조직의 처리 지연이 허용 범위 내인지

## I2. 결정적 샘플링 (부하 조절·평가 비용 조절)

1. 문제: 모든 응답에 LLM 평가를 돌리면 비용이 2배, 일부만 돌리면 재실행 때 결과가 흔들림
2. 원리: 대상 id를 도메인 분리 해시로 [0,1] 값으로 변환하고 비율과 비교 → 상태 없이 항상 같은 결정
3. Neodio 적용: D4 평가기의 **표본 평가**(전체 대신 비율), 지표 신뢰구간(D2)에 "평가 표본 비율" 반영
4. 유의: 샘플링 결과로 만든 지표는 전수 지표와 섞지 않고 표본 표시를 붙인다

## I3. 평가기 거버넌스 (D4 보강)

1. 문제: LLM 판정은 모델·지침·파라미터가 바뀌면 결과가 달라지고, 오류가 반복되면 비용이 낭비됨
2. 요구:
   - 평가기 정의를 **불변 버전**으로 저장(지침, 모델, 파라미터, 출력 스키마)
   - 모든 판정 결과가 어떤 버전·어떤 실행에서 나왔는지 추적
   - **종결성 오류**(인증 무효, 한도 소진, 엔드포인트 불가)는 즉시 평가기를 **일시 정지**하고 사유를 기록 — 같은 오류가 수천 건 반복되지 않게
   - 오류 분류는 구조화 정보 우선, 문자열 패턴은 보조
   - **테스트 실행과 실제 실행이 같은 코드 경로**
   - 모델에 요청하는 필드명이 모델 동작을 바꿀 수 있음(예: 사고 공간으로 오인되는 필드명) → 출력 계약 검증을 실제 모델별로 확인
3. Neodio 대안: 프로젝트 2의 D4 `eval_profile`에 위 요구를 추가. "정지 사유" 열거형 제공
4. 검증: 키 폐기·한도 소진 상황을 주입했을 때 정지 후 알림이 나가고 잡이 재시도 폭주하지 않는지

## I4. 버전 관리되는 모델 단가 + 조건부 티어 (D1 보강)

1. 문제: 모델 단가가 바뀌고, 컨텍스트 길이에 따라 단가가 달라지는 모델이 있음
2. 요구: 단가표를 **유효 시작일 포함 이력**으로 보관, 사용량 조건으로 티어 선택, 일치하지 않으면 명시적 기본 티어, **단가표에 없는 모델은 비용 미상으로 표시하고 예산 계산에서 보수적으로 취급**(0원 처리 금지)
3. 원본 한계: 정규식을 데이터로 저장
4. Neodio 대안: 패턴 대신 **정확한 모델 식별자 + 별칭 테이블**(정규식 없음) — 위험·성능 문제 회피
5. 검증: 과거 시점 비용 재계산이 당시 단가로 재현되는지

## I5. 외부 URL 가져오기: 연결 시점 IP 검증 (P1·P2의 TOCTOU 공백 해소)

1. 문제: 사전에 호스트를 검사해도 실제 연결 때 DNS가 다른 내부 IP로 바뀔 수 있음(리바인딩)
2. 원본 방식(개념): 사전 검증 + 연결 계층에서 실제 해석된 IP를 다시 검증 + 리다이렉트마다 재검증
3. 추가 요구: https 강제 옵션, URL 내 자격증명 금지, 포트 제한, 인코딩 엄격 검사, 런타임이 쓰는 모든 해석 경로 포함
4. Neodio: `pageText.ts` 등 서버가 사용자/브랜드 도메인을 가져오는 모든 지점에 **단일 안전 fetch 모듈**을 적용해야 함. 현 구현이 연결 시점 검증을 하는지 **확인 필요**
5. 검증: 리바인딩 시뮬레이션(첫 해석 공인 IP, 두 번째 사설 IP)에서 차단

## I6. 임계값 모니터와 알림 라우팅

1. 문제: 지표가 악화돼도 사람이 화면을 열어야 알게 됨
2. 요구: 지표·조건·기간·심각도를 정의하는 모니터, 조직/브랜드별 알림 채널, 중복 억제
3. Neodio 연결: D2(변화 신뢰도)의 "유의한 변화"를 모니터 조건으로, 알림 문구에는 노이즈 가능 표시
4. 판단: 자동 알림은 거짓 알림 위험이 있어 D2 검증 후

## I7. 데이터 보존·삭제 파이프라인 (개념)

1. 문제: B2B 고객은 원본 응답(제3자 콘텐츠 포함)의 보존 기간과 삭제를 요구
2. 요구: 조직/브랜드 단위 보존 기간, 배치 삭제, 삭제 가드(실수 방지), 감사 기록, 원본 vs 파생 데이터 구분
3. Neodio: 현 정책은 확인되지 않음 → 조사 필요(법무와 연계)

## I8. 빌드 대신 도입 검토: 내부 LLM 호출 관측

- Neodio 자체의 LLM 호출(브랜드 정리, 리서치 생성, D4 평가기 등)을 **Langfuse 같은 도구로 관측**하면 호출별 입력/출력/토큰/비용/지연을 직접 만들지 않고 얻을 수 있다.
- 주의: 고객 콘텐츠가 외부로 나가는지(호스팅/자체 호스팅), 인프라 부담(자체 호스팅은 ClickHouse·Redis·S3·Postgres), `ee` 기능 사용 금지. → RESEARCH. 이는 **제품 도입**이지 코드 이식이 아니다.
