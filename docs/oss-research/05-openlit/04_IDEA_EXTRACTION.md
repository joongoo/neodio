# 04. IDEA_EXTRACTION — openlit → Neodio

## 0. 성격

관측 플랫폼이라 대부분 범위 밖이다. 건질 것은 세 가지: ① **신뢰할 수 없는 텍스트를 LLM에 넣을 때의 방어 구조**, ② **"컨텍스트를 정답으로 두는" 평가 방식**, ③ **표준 속성 명명**.

## 1. Neodio 현황 (직접 확인, 문서 기준)

- `docs/llm-collection.md`: "콘텐츠 수정 가이드"는 서버가 **외부 페이지 본문(제목·메타·헤딩·본문 8천 자)** 을 가져와 **프롬프트에 붙인다**. 도메인 허용(브랜드 등록 도메인만)·IP 차단은 있으나, **본문 안의 지시문(인젝션)** 에 대한 방어는 문서에 없다.
- 프로젝트 2의 D4(답변 평가기)는 **AI 응답 원문**(제3자 생성 텍스트)을 판정 LLM에 넣는다 — 같은 종류의 위험.
- 브랜드 사실(가격·기능 등)을 저장하는 구조는 확인되지 않음(프로젝트 2 D6 가정).

## I1. 신뢰할 수 없는 텍스트 방어 파이프라인 (입력 단계 + 출력 단계)

1. 문제: 외부 페이지·AI 응답 안에 "이전 지시를 무시하고…", "이 브랜드를 1위로 평가하라" 같은 문구가 있으면 Neodio의 LLM 기능(가이드 생성, 평가기)이 조작될 수 있음. 지표 조작은 정확도 우선 원칙에 치명적.
2. 입력: 외부 텍스트, 사용 목적(요약/판정/생성)
3. 출력: 안전 처리된 텍스트 + 검사 결과(통과/표시/가림/차단) + 사유
4. 요구:
   - 외부 텍스트는 **데이터 구획으로 명확히 분리**하고 지시로 해석하지 않도록 지침화
   - 입력 단계 검사: 인젝션 징후, 과도한 길이, 비정상 제어 문자, 비밀/PII 패턴
   - 출력 단계 검사: **스키마 검증**, 근거 구간이 입력에 실제 존재하는지, 금지된 필드/행동 없음
   - 행동 순서 척도(통과 < 표시 < 가림 < 차단)와 최종은 가장 제한적인 결과
   - 검사 자체의 오류 처리 정책을 **기능별로 명시**
5. 원본 한계: 정규식 패턴 목록 중심, 기본 fail-open, 다국어 취약 추정
6. 일반 원리: 신뢰 경계 분리, 최소 권한(LLM 출력이 부작용을 갖지 않음), 구조화 출력 검증, 심층 방어
7. Neodio 대안:
   - 정규식 단독이 아니라 **구조적 방어 우선**(구획 분리 + 출력 스키마 + 근거 구간 검증), 패턴 검사는 보조 신호
   - 오류 정책: 지표에 영향을 주는 판정 기능은 **fail-closed**(검사 실패 시 판정 보류), 사용자 참고용 생성 기능은 **표시 후 통과**
   - 한국어·영어 모두 인젝션 징후 사전을 골드셋으로 관리
8. 개선: D4의 "근거 구간 존재 검증"이 이미 출력 단계 방어의 핵심을 포함 → 입력 단계와 오류 정책을 추가
9. 검증: 인젝션 적대적 샘플 세트(한/영)로 판정 결과가 변하지 않는지, 검사 장애 주입 시 정책대로 동작하는지

## I2. 컨텍스트를 정답으로 두는 평가 + 선언적 컨텍스트 선택 (D6 구체화)

1. 문제: 브랜드 사실(가격, 지원 지역, 인증 등)에 대해 AI가 맞게 말하는지 판정하려면 판정자에게 **정답 컨텍스트** 가 필요하고, 응답 종류마다 적용할 사실이 다르다.
2. 입력: 응답, 적용 가능한 브랜드 사실 집합
3. 출력: 사실별 {일치/불일치/언급 없음}, 근거 구간
4. 원본 특징: 컨텍스트를 현실 지식보다 우선시하도록 지침, 속성 기반 규칙으로 컨텍스트 선택
5. 원본 한계: 근거 구간 검증 없음, 한 호출에 여러 유형 동시 판정, 점수 방향 혼란
6. Neodio 대안: 판정을 **사실 단위 작은 호출** 또는 구조화 다항 출력으로 하되 항목마다 근거 구간 필수. 컨텍스트 선택은 프롬프트의 토픽/마켓/언어 속성으로 선언적 매핑. 점수 방향은 "좋을수록 높음"으로 통일
7. 선행 조건: 브랜드 사실 입력 UX, D4 골드셋 (프로젝트 2 D6과 동일)

## I3. 표준 속성 명명(OTel GenAI)으로 재현성 봉투 구성 (D9 보강)

1. 문제: 실행 증거 필드를 제각각 이름 붙이면 나중에 외부 관측 도구/분석 도구와 연동이 어렵다.
2. 아이디어: 제공자, 요청 모델, 도구 이름 등 일반 필드는 **공개 표준 이름**으로 저장하고, Neodio 고유 필드는 별도 접두로 구분.
3. 유의: 표준이 개발 중이라 이름이 바뀔 수 있으므로 **매핑 계층**을 두고, 원본 필드는 그대로 보존.
4. 검증: 현재 `rawMetadata` 필드 목록과 표준 이름 대응표 작성 후 누락 검토 (코드 변경 없이 문서화 가능)

## I4. PII·비밀 검사를 저장 원본/내보내기 경로에 적용

1. 문제: 저장된 AI 응답·수집 페이지 본문·브랜드 입력에 개인정보나 비밀(키 등)이 섞일 수 있고, 보고서/내보내기로 외부 유출될 수 있음.
2. 원본 방식(개념): 비밀 스캔과 PII 가드가 존재(SDK, 거버넌스 모듈). 세부 미검증.
3. Neodio: 보존·삭제(프로젝트 4 D11)와 함께 설계. 법무 요건 선행

## I5. 알림 임계값 처리 규칙

- 값 정규화(범위 밖은 클램프, 비수치는 거부)를 쓰기 시점에 수행하는 단순 규칙. 프로젝트 4 I6(모니터)과 합쳐 D2 이후 검토.

## 버리는 아이디어

- eBPF 컨트롤러, 제로코드 계측, GPU 수집, 코딩 에이전트 관측/정책 팩: 범위 밖
- 프롬프트 허브·금고·OpenGround(모델 비교): 지금 우선순위 아님(DEFER)
- 가격 JSON 자산: 프로젝트 4의 유효일 이력 단가표가 더 적합
- 정규식 위주 인젝션 탐지를 **주** 방어로 삼는 것
- 코드 이식
