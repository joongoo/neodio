### 목적과 핵심 기능

"셀프호스팅 AI 가시성 트래커". 브라우저에 상태를 저장하고(IndexedDB), 선택적으로 자기 Supabase에 동기화한다. 한 번의 실행(run)은 프롬프트 × 엔진 조합이다.

- 5개 엔진 수집(ChatGPT, Perplexity, Gemini, Copilot, Google AI Mode) — **Bright Data AI Scraper API**에 위탁
- 0–100 가시성 점수, 감성, 인용 도메인 집계, 드리프트 알림, 국가별 실행
- 경쟁사 배틀카드, 인용 기회, 니치 탐색, 페르소나 팬아웃(LLM 생성)
- AEO 사이트 감사(llms.txt, AI 크롤러 robots 접근, 스키마, BLUF 밀도)
- SRO 분석 파이프라인(교차 플랫폼 인용 → SERP → 페이지 스크래핑 → 사이트 컨텍스트 → LLM 분석)
- **Rank Signal**: 문단의 특정 텍스트 특징이 LLM 선택에 영향을 주는지 쌍대 A/B로 검증(DEJAN AI 방식을 참조했다고 README에 명시)

### 외부 서비스

Bright Data(스크래퍼·SERP·Web Unlocker), OpenRouter(분석·판정·재작성 LLM), Google Gemini(grounding), Supabase(선택 저장소), Vercel(배포).

### 운영 상태

- 활발히 갱신 중(분석 시점 하루 전 커밋). 릴리스/태그 상태는 **미확인**.
- 공개 데모 배포(`isDemoDeploy`)는 유료 API 라우트를 막는 모드가 있다.

### 상용 SaaS 적용 시 위험 요소 (요약)

1. 수집이 전적으로 제3자(Bright Data)의 AI 챗봇 스크래핑에 의존 → 약관·가격·차단 위험 (06 문서)
2. 멀티테넌트·계정·권한 개념이 없음(단일 공유 비밀번호)
3. 스케줄링이 브라우저 열림에 의존
4. 점수 규칙이 단순 가산식이라 비교·해석 신뢰도 낮음

## 02. 아키텍처 분석

### 1. 구조

```
Next.js 16 단일 앱
├─ app/page.tsx → components/sovereign-dashboard.tsx   (상태·탭·KPI 전부 한 클라이언트 컴포넌트, 약 2천 줄)
├─ app/api/*           (scrape, analyze, audit, serp, site-context, unlocker, bulk-sro, rank-signal, state ...)
├─ lib/client/         (IndexedDB 저장소, SSE 클라이언트)
├─ lib/server/         (Bright Data, OpenRouter, Gemini, SSRF, robots, rank-signal-*)
├─ lib/scoring.ts      (브랜드 매칭·감성·점수: 순수 함수)
├─ lib/shared/         (rank-signal 통계: 서버·클라이언트 공용 순수 함수)
├─ proxy.ts            (IP 레이트리밋 + 데모 에이전트 디스커버리)
└─ supabase/migrations/001_kv_store.sql   (테이블 1개)
```

### 2. 데이터 흐름

1. 사용자가 브라우저에서 프롬프트 × 엔진 조합 선택(배치는 풀로 4개씩 동시 실행: `lib/pool.ts`)
2. `/api/scrape` → Bright Data에 요청 → 응답이 즉시 안 오면 `snapshot_id`를 받아 **폴링**(`brightdata-scraper.ts` 모니터/다운로드 단계) → 정규화
3. 답변 본문에서 URL 추출 + 응답의 `citations`/`links_attached`/`sources` 필드 병합·중복 제거
4. **점수·감성 계산은 클라이언트**에서 수행(`lib/scoring.ts`), 결과 전체가 `AppState` JSON 한 덩어리로 IndexedDB(또는 KV)에 저장
5. 자동 실행은 대시보드 컴포넌트 안의 인터벌 타이머 + 직전 점수 대비 변화량이 임계값 이상이면 드리프트 알림 생성

### 3. 저장·격리·인증

| 항목 | 현황 | 근거 |
|---|---|---|
| 저장 | 기본 IndexedDB. 클라우드는 `kv_store(key text PK, value jsonb)` 1테이블, 상태 전체를 키-값으로 덮어쓰기 | `supabase/migrations/001_kv_store.sql`, `app/api/state/route.ts` |
| 인증 | `STATE_SYNC_SECRET` 공유 비밀 헤더 1개(timing-safe 비교). 사용자·조직 개념 없음 | `app/api/state/route.ts` |
| 멀티테넌트 | **없음** (워크스페이스는 클라이언트 상태 안의 배열) | 구조상 |
| 레이트리밋 | 프로세스 메모리 Map, 인스턴스별. 코드 주석이 "버스트 방어일 뿐 전역 보장 아님"이라고 명시 | `proxy.ts` |
| 비용 통제 | Rank Signal에 시간당 USD 원장(메모리) + 요청당 5달러 상한 + 모델 허용목록 + 가격표 | `rank-signal.ts`, `rank-signal-judge.ts` |
| SSRF | 사설/예약 IPv4·IPv6 블록리스트, IPv6 임베디드 IPv4 재검사, DNS 해석 결과 전부 검사, 파싱 불가 시 거부 | `lib/server/ssrf.ts` + 테스트 |

### 4. 비동기·스케줄

- 서버 큐·워커 **없음**. 장시간 작업은 HTTP 요청 안에서 SSE로 스트리밍(`bulk-sro`, `rank-signal`), `maxDuration` 상한에 묶임.
- 정기 실행은 "브라우저 탭이 열려 있어야 도는 인터벌" + GitHub Actions/cron **템플릿 문서**(실제 실행기 아님).

### 5. 시스템 의존성

모든 수집 경로가 Bright Data 단일 벤더를 통과한다. 분석·판정·재작성은 OpenRouter 단일 경유(허용 모델 목록 환경변수).

### 6. 미구현으로 확인되는 것

서버 사이드 잡 큐, 사용자/조직 모델, 응답 원문의 버전 관리된 분석 파이프라인(점수 재계산 이력), 전역 레이트리밋, 다국어 감성(어휘 목록이 영어), 한국 엔진.

## 03. 핵심 로직 조사

구현 코드는 싣지 않고 목적·입출력·한계만 정리한다. 모든 항목은 실제로 읽은 파일 기준이며, 읽지 않은 범위는 "미검증"으로 표시했다.

### L1. 브랜드 언급 감지 — `lib/scoring.ts`

- 목적: 답변에서 브랜드·별칭을 찾는다.
- 입출력: (텍스트, 용어 목록) → 발견된 용어 / 언급 횟수
- 특징: 유니코드 문자·숫자 경계 기준 "전체 단어" 일치, 공백은 임의 길이 공백 허용, **겹치는 용어는 가장 긴 것 하나만** 센다("Acme"와 "Acme Inc").
- 한계: 한국어 조사 처리 없음(경계 규칙이 문자 단위라 "브랜드가"에서 경계가 맞지 않아 놓칠 수 있음 — 추정, 한국어 입력으로 **미검증**). 별칭의 모호성(일반 명사형 브랜드) 대응 없음.

### L2. 감성 — `lib/scoring.ts`

- 방식: 영어 긍정/부정 단어 목록의 **등장 단어 종류 수**를 비교, 차이가 2 이상일 때만 긍정/부정, 아니면 중립.
- 한계: 영어 한정, 브랜드 주변이 아니라 **답변 전체**를 본다("worst competitor ... best us"가 상쇄), 부정문·맥락 무시. 한국어/일본어 입력은 사실상 항상 중립.

### L3. 가시성 점수 — `lib/scoring.ts`

가산식 루브릭: 언급이 있으면 기본점, 첫 200자 안에 있으면 가산, 반복 횟수 구간 가산, 자사 도메인이 출처에 있으면 가산, 감성 가산. 상한 100.

한계(정확도 관점):
1. **언급만 해도 기본점**이 붙어 낮은 품질의 언급이 부풀려진다.
2. "첫 200자"는 답변 길이에 무관한 절대 길이라 짧은/긴 답변을 같은 잣대로 평가.
3. 자사 도메인 판정이 **부분 문자열 포함**(출처 URL 문자열에 도메인이 들어 있으면 일치) — 유사 도메인/경로 안 문자열 오탐 가능. 정규화된 호스트 비교가 아님.
4. 경쟁사 대비 위치(순위)·Share of Voice 개념 없음 — 점수는 "자사 단독" 지표.
5. 실행 단위 점수의 평균/집계 규칙, 반복 실행 가중 규칙이 문서화되지 않음.
6. 점수 구성 변경 시 과거 점수 재계산·버전 관리 없음(저장된 값이 곧 기록).

### L4. 인용 URL 추출 — `lib/server/brightdata-scraper.ts`

- 답변 본문의 URL + 응답의 구조화 필드(여러 후보 이름) 병합 후 중복 제거.
- 한계: 도메인 정규화(www, 추적 파라미터, 단축 URL) 규칙이 이 경로에서 확인되지 않음 — 집계 단계는 미검증. 필드명이 벤더 응답 스키마에 의존.

### L5. 드리프트 알림 — `components/sovereign-dashboard.tsx`

- 직전 대비 점수 변화가 **고정 임계값(10점)** 이상이면 알림.
- 한계: LLM 응답은 본질적으로 무작위라 표본 수에 따라 노이즈 크기가 다른데, 고정 임계값은 이를 반영하지 않는다 → 소표본에서 거짓 알림, 대표본에서 놓침.

### L6. 실행·재시도·동시성 — `lib/pool.ts`, `brightdata-scraper.ts`

- 고정 동시성 풀(입력 순서 유지, 개별 실패 격리). Retry-After 헤더 해석(최대 60초). 스냅샷 폴링 타임아웃.
- 한계: 전역(서버 전체) 동시성·예산 제어 없음, 풀 크기가 사용자 브라우저에서 결정됨.

### L7. Rank Signal (가장 독창적인 부분) — `lib/server/rank-signal*.ts`, `lib/shared/rank-signal-stats.ts`

목적: "어떤 텍스트 특징이 문단 선택에 영향을 주는가"를 **통제된 쌍대 비교**로 검증.

개념 구조(구현 순서 아님):
1. 자사·경쟁사·SERP 상위 페이지에서 문단 풀 구성(최소 풀 크기 요건)
2. 특징 하나만 다른 두 버전(with/without)을 만든다. 코드로 만드는 특징과 LLM 재작성으로 만드는 특징이 있고, **재작성본은 통제 검사**(다른 부분이 동일한지)를 통과해야 쓴다
3. 판정 모델이 질의 + 두 문단만 보고(URL·도메인·제목 제거) 하나를 선택
4. 승률의 사후분포(Beta, Jeffreys 사전)로 95% 구간, **순차 중간 확인 지점**에서만 판정 읽기(조기 종료 허용), 판정은 저장하지 않고 매번 재계산
5. **플라시보**(의미·길이를 유지한 한 문장 재서술) 특징으로 "편집 자체에 판정자가 반응하는 정도"를 따로 측정
6. 카탈로그 버전 번호로 특징 정의가 바뀌면 결과 비교 불가를 표시
7. 비용: 호출 전 예산 추정, 연속 실패 중단, 시간당 상한

한계:
- 판정 모델의 **선호도 대리 지표**일 뿐 실제 AI 검색의 grounding 선택이 아님(README도 명시).
- 작은 표본(최대 40), 다중 비교 보정 언급 없음(특징 14여 개를 동시에 보면 거짓 양성 위험 — 미검증).
- 지출 원장이 프로세스 메모리 — 인스턴스가 늘면 상한 무력화(코드 주석도 인정).
- 한 가지 모델·한 가지 언어 중심.

### L8. AEO 감사 — `app/api/audit/route.ts`, `lib/server/robots.ts`

- llms.txt / llms-full.txt / robots.txt / sitemap 존재 확인, AI 크롤러별 허용 여부(RFC 9309 의미 적용: 4xx면 제한 없음, 5xx·네트워크 오류는 보수적 처리), 스키마·BLUF·헤딩 구조 점검.
- 한계: llms.txt는 표준이 아니며 AI 시스템의 실제 사용 여부는 입증된 바 없음(체크 항목의 "중요도"는 원본이 단정하는 정도로 신뢰하면 안 됨).

### L9. SSRF 방어 — `lib/server/ssrf.ts`

- 방식: 스킴 제한, IP 리터럴 검사, 로컬 호스트명 접미사 거부, DNS 해석 결과 **모두** 검사, 파싱 실패는 거부(fail-closed). 테스트 82줄.
- 잔존 위험: 검사 시점과 실제 요청 시점의 DNS 재해석 차이(DNS rebinding)는 이 모듈만으로 막지 못한다(요청 시 해석된 IP 고정이 필요) — 호출부에서 처리하는지 **미검증**.

### L10. 품질 신호

- 테스트: scoring, pool, proxy, ssrf, rank-signal(통계·판정·특징·문단), 스크래퍼, robots, agent-discovery. 통합·E2E 테스트는 확인되지 않음. **테스트 실행은 하지 않았다(미검증)**.
- 타입: TypeScript + zod 입력 검증. 오류는 대체로 일반화된 메시지로 변환(업스트림 본문 미노출 — 좋은 관행).
- 거대 컴포넌트(대시보드 약 2천 줄)와 상태 전체 덮어쓰기 저장은 유지보수·동시편집 한계.

## 04. 아이디어 추출

원칙: 구현이 아니라 **문제 → 입력 → 출력 → 한계 → 일반 원리 → Neodio 대안** 순으로 추상화한다. Neodio 현황은 이 저장소를 직접 읽고 확인한 것만 적는다.

### 0. 먼저: Neodio가 이미 앞선 영역 (가져올 것 없음)

| 영역 | 원본 | Neodio (확인 근거) |
|---|---|---|
| 멀티테넌트·권한 | 없음(공유 비밀 1개) | 조직·멤버십·브랜드별 권한 (`neodio_memberships`, `neodio_membership_brands`) |
| 저장·재현성 | 상태 JSON 덮어쓰기 | `prompt_runs`/`run_analyses`/`brand_observations`/`citations`, `config_versions`, `change_log` |
| 점수 설계 | 가산식 루브릭 | 가중 3요소 + 위치 중요도 + 반복 실행 가중 + 감성 제외 (`processing/visibility.ts`) |
| 수집 | 제3자 스크래퍼 위탁 | 공식 API + 자체 Playwright(네이버·구글) |
| 언어 | 영어 감성 목록 | 한국어 조사 처리 포함 매칭 (`processing/text.ts`) |

→ 원본에서 얻을 가치는 **아래 5가지 아이디어**에 한정된다.

### I1. 통제된 쌍대 실험으로 "무엇이 선택되게 하는가" 검증

1. 사용자 문제: "콘텐츠를 이렇게 고치면 AI가 더 잘 인용할까?"를 상관이 아닌 인과에 가깝게 검증하고 싶다.
2. 입력: 질의, 문단(자사/경쟁), 검증할 텍스트 특징
3. 출력: 특징별 승률과 불확실성 구간, 판정(효과 있음/없음/불충분)
4. 요구사항: 특징 외 다른 요소 통제, 편집 자체 효과 분리, 재현 가능, 비용 상한
5. 원본의 한계: 판정자는 실제 AI 검색이 아닌 대리 모델, 표본 작음, 다중 비교 보정 없음, 단일 모델
6. 일반 원리: 짝지은 실험 설계, 위약 대조, 순차 검정, 베이지안/빈도주의 구간 추정
7. Neodio 대안: 판정 모델 다중화(최소 2개 + 불일치율 보고), **실제 수집 데이터로 교차 검증**(판정 선호가 우리 `citations` 실측과 일치하는지 보정), 다중 비교 보정, 한국어 문단 지원
8. 개선: 실험 결과를 "추천"이 아니라 **기회 카드의 근거 강도**로 연결
9. 검증: 알려진 효과(예: 질의 키워드 포함)와 알려진 무효과(위약)에 대해 방법이 양/음을 올바르게 재현하는지 보정 실험

### I2. 호출 전 비용 추정 + 전역 예산 통제

1. 문제: 대량 배치·AI 생성 기능의 비용 폭주
2. 입력: 모델별 단가, 예상 토큰, 조직 한도
3. 출력: 실행 전 예상 비용, 초과 시 거부/축소, 실행 후 실비 기록
4. 요구: 조직별·기간별 한도, 인스턴스 간 공유
5. 한계(원본): 지출 원장이 메모리라 인스턴스 간 공유 안 됨 — 자체 주석이 인정
6. 원리: 토큰 버킷/원장, 사전 예약-사후 정산
7. Neodio 대안: DB 기반 원장(조직·일 단위) + 기존 `rateLimit.ts`(메모리, 분당 호출) 대체/보완. Neodio 현재는 **분당 호출 수만** 제한하고 비용 단위 통제는 없음(문서 `llm-collection-guide.md` 기준)
8. 개선: 원본보다 한 단계 더 — 전역 공유
9. 검증: 동시 실행 N개에서 한도 초과 0건인지 부하 테스트

### I3. 표본 크기를 반영한 변화 감지(드리프트)

1. 문제: 주간 점수 변화가 진짜 변화인지 노이즈인지 구분
2. 입력: 기간별 (언급 실행 수, 전체 실행 수)
3. 출력: "유의한 변화" 플래그와 구간
4. 원본 한계: 고정 임계값 → 표본 수 무시
5. 원리: 비율 차이의 신뢰구간/검정, 소표본 보정
6. Neodio 대안: 이미 주간 `visibility_scores`와 반복 실행 가중이 있으므로 **같은 가중 표본 크기로 구간을 계산**해 변화 카드에 "노이즈 가능" 표시. 문서 `help.ts`의 "답변 변동성은 정상" 안내를 수치로 뒷받침
7. 검증: 과거 데이터 재생(백테스트)으로 거짓 알림 비율 측정

### I4. AEO 사이트 진단 항목 보강

1. 문제: 자사 사이트가 AI에 읽히는가
2. 요구: AI 크롤러별 접근 허용 여부, 규격에 맞는 robots 해석
3. 원본 특징: 크롤러별 허용 판정에서 4xx는 제한 없음, 5xx·오류는 보수 처리(RFC 9309)
4. Neodio 현황: `robotsTxtReader.ts` 존재, 구조화 데이터·콘텐츠 가시성 회복 기회 존재. **크롤러별 판정 규칙이 RFC 9309와 일치하는지는 미확인** → RESEARCH
5. 주의: llms.txt 효과는 입증되지 않음 → 점수화하지 말고 "참고" 등급

### I5. 서버 요청 URL 방어(SSRF) 점검 목록

1. 문제: 사용자 입력 URL을 서버가 가져올 때의 내부망 노출
2. Neodio 현황: `pageText.ts`에 "IP·localhost 거부, 리다이렉트마다 재검사" (문서 기준)
3. 아이디어: 점검 목록으로 활용 — IPv6 매핑/NAT64/6to4 내장 IPv4, 해석된 모든 주소 검사, 파싱 불가 시 거부, **요청 시점 IP 고정**
4. 이는 코드 이식이 아니라 Neodio 구현이 빠뜨린 케이스가 없는지 **테스트 케이스 목록**을 만드는 용도

### 버리는 아이디어 (이유 포함)

- 제3자 스크래퍼에 AI 챗봇 수집 위탁: 약관·가격 위험, Neodio P0 원칙(공식 API/자체 통제)과 충돌 → 06
- 브라우저 상태 저장, KV 덮어쓰기, 인터벌 스케줄러: SaaS 요건 미충족
- 가산식 점수 / 영어 감성 목록: Neodio가 이미 더 나음

## 05. 독립 설계

> 이 문서는 **원본 소스·파일명·식별자·임계값을 참조하지 않는다.** 승인된 기능 요구사항(04의 I1~I3)만을 입력으로 한 독립 설계다.
> 구현 아님. 모든 수치는 "초기 제안값 — 보정 실험으로 결정"이다.
> 한계: 04와 같은 세션에서 작성되어 엄격한 Clean-Room이 아니다(06 §4).

---

### D1. 비용 거버너 (Cost Governor)

**목표**: LLM 호출 비용을 조직·기간 단위로 통제하고, 실행 전에 예상 비용을 보여준다.

**요구사항**
- R1 호출 전 예상 비용 산출(모델 단가 × 예상 입력/출력 토큰)
- R2 조직별 일/월 한도, 초과 시 차단 또는 축소 실행 선택
- R3 실행 후 실제 비용 기록(제공자가 응답에 비용을 주면 우선, 없으면 토큰×단가)
- R4 서버 인스턴스가 여럿이어도 한도가 정확히 지켜질 것
- R5 단가표에 없는 모델은 실행 거부(조용히 0원 처리 금지)

**설계**
- 방식: "예약 → 정산". 실행 시작 때 예상치를 원장에 예약(reserve)하고 완료 시 실비로 확정(settle), 취소/실패 시 해제.
- 원자성: DB 트랜잭션에서 `기간 합계 + 예약 ≤ 한도`를 검사한 뒤 예약 행을 삽입(직렬화 가능 수준 또는 조직 행 잠금).

**데이터 모델(제안)**
- `llm_price_table(model_id, input_per_mtok, output_per_mtok, effective_from)` — 단가 이력 보존
- `llm_budget(organization_id, period_type, limit_usd)`
- `llm_spend_ledger(id, organization_id, job_id, model_id, state[reserved|settled|released], estimated_usd, actual_usd, created_at)`

**인터페이스(제안)**
- `reserve(org, model, estimatedTokens) → {ok, reservationId, remaining} | {denied, reason}`
- `settle(reservationId, usage)` / `release(reservationId)`
- `previewCost(plan) → {low, high}` (UI 표시용)

**검증**: 동시 100건 예약에서 합계가 한도를 넘지 않음, 비정상 종료 후 만료 예약 정리, 단가 변경 이후 과거 기록 불변.

---

### D2. 변화 신뢰도 표시 (Change Confidence)

**목표**: 주간 지표 변화가 표본 크기에 비해 의미 있는지 표시한다.

**요구사항**
- R1 입력은 기존 주간 집계(가중 언급 수, 가중 전체 실행 수)
- R2 출력은 변화량과 신뢰구간, 라벨(유의/노이즈 가능/표본 부족)
- R3 구간 방법은 소표본에서 안정적인 비율 구간(예: Wilson 또는 Bayesian credible interval)을 후보로 비교해 선택
- R4 표본이 최소 기준 미만이면 변화율을 숫자로 크게 보여주지 않는다

**데이터**: 별도 저장 없이 읽기 시점에 계산(저장하지 않아 정의 변경 시 과거도 일관).

**검증**: 과거 데이터에서 변화가 없다고 알려진 구간(같은 설정 연속 주)으로 거짓 양성률 측정, 후보 구간 방법 간 비교 후 선택.

---

### D3. 콘텐츠 영향 실험 엔진 (Content Effect Lab)

**목표**: "텍스트의 특정 특징이 AI의 선택에 영향을 주는가"를 통제된 대조 실험으로 검증하고, 그 근거 강도를 기회 카드에 연결한다.

**요구사항**
- R1 실험 단위 = (질의, 문단 쌍, 특징). 쌍은 특징 외 모든 내용이 동일해야 한다
- R2 쌍 생성 시 **자동 통제 검사**(길이 편차, 숫자·고유명사 보존, 의미 보존)를 통과해야 시행에 사용
- R3 판정 시 출처 단서(URL, 도메인, 제목)를 제거하고 제시 순서를 무작위화(위치 편향 제거)
- R4 위약 대조 포함: 의미를 바꾸지 않는 편집만으로 판정이 얼마나 움직이는지 기준선으로 보고
- R5 다중 판정 모델 사용 시 모델 간 불일치율 보고
- R6 한국어·영어(필요 시 일본어) 문단 지원
- R7 중간 확인 시점을 사전에 고정하고 그 시점에서만 종료 판단(관측 중 임의 중단 금지)
- R8 여러 특징을 동시에 검증하면 다중 비교 보정을 적용
- R9 **보정 단계**: 판정 모델의 선호를 Neodio가 수집한 실제 인용 데이터와 대조해 일치도를 기록, 일치도가 낮으면 결과에 "대리 지표 신뢰 낮음" 표시
- R10 특징 정의에 버전을 부여, 버전이 다른 결과는 합산하지 않음
- R11 모든 호출은 D1 거버너를 통과

**데이터 모델(제안)**
- `effect_feature(id, version, name, direction_rule, control_rules_json)`
- `effect_experiment(id, organization_id, brand_id, query, feature_id, feature_version, judge_models, config_snapshot, status)`
- `effect_trial(id, experiment_id, passage_ref, variant_a, variant_b, order_seed, judge_model, choice, valid, reject_reason, cost_usd)`
- `effect_result_view` — 저장하지 않고 읽기 시점에 구간·판정 산출

**인터페이스(제안)**
- `proposeExperiment(brand, query, features) → plan(+cost preview)`
- `runExperiment(plan) → stream(progress)`
- `getResult(experimentId) → {effect, interval, placeboBaseline, judgeAgreement, calibration, label}`

**검증**: (a) 효과가 없다고 알려진 위약에서 양성 판정이 임계 비율 이하, (b) 효과가 있다고 알려진 대조 특징에서 양성, (c) 판정 순서 뒤집기에 결과 불변.

**위험/비목표**: 실제 AI 검색 결과를 보장하지 않는다. UI 문구는 "AI 판정 모델 기준 추정"으로 표기(내부 구현 노트를 사용자 문구에 넣지 않는 원칙에 맞춰, 사용자 화면에는 "추정 신뢰도"로만 노출).

- 통계 부분(베타-이항 사후분포, 순차 확인)은 일반 수학 기법이라 문제 없음. D3는 이를 그대로 쓰지 않고 구간 방법을 비교 선택하도록 독립 설계했다.

### 4. Clean-Room 수행의 한계 (정직한 기록)

- 본 분석은 **같은 세션, 같은 에이전트**가 원본 읽기(Source Analyst)와 설계(Product Architect/Independent Designer)를 모두 수행했다. 에이전트 격리가 없으므로 **엄격한 Clean-Room이라고 주장하지 않는다.**
- 완화책: ① 05 문서에는 원본 파일 경로·함수명·변수명·임계값·특징 코드명을 쓰지 않았고, ② 알고리즘은 일반 원리(베타-이항, 대조 실험)로만 서술했으며, ③ 구현 단계는 05만을 입력으로 새 세션에서 시작하도록 권고한다.

**원본은 Neodio보다 한참 뒤에 있다.** 제품 구조(테넌시·저장·점수·수집)는 Neodio가 앞서며, 가져올 가치는 사실상 **통계적 엄밀함과 비용 통제 두 축**이다.

권고 순서: D2 → D1 → (법무 확인 후) D3. D3는 구현보다 **보정 실험**(판정 모델 선호가 우리 실측 인용 데이터와 맞는지)이 먼저다.
