## 02. 아키텍처 분석

### 1. 구조

```
pnpm 모노레포
├─ apps/web   Next.js(App Router) UI + oRPC API + GEO 서비스 + BullMQ 워커(같은 이미지, 별도 컨테이너)
│   ├─ services/geo/     orchestrator(수집) · parser · scorer(LLM 채점) · sov(스냅샷) · intent · locations · dataforseo · citation-gap · site-analyzer
│   ├─ workers/          queue.ts(BullMQ 큐 1개), geo-sweep-worker.ts
│   ├─ jobs/repeatable/  scheduler.ts(주 1회 반복 잡)
│   └─ utils/            safe-fetch(SSRF), job-store
└─ packages/db  Drizzle 스키마 + 생성된 SQL 마이그레이션 3개
Docker Compose: postgres + redis + web + worker
```

### 2. 데이터 흐름 (스윕 1회)

1. **수집(checks)**: 프롬프트 × 모델(엔진) 조합을 실행 → `geo_llm_run` 1행 + 인용 N행 저장. 같은 (프롬프트, 모델, 날짜)는 **유일 키**라 하루 1건. 수동 재확인만 `force`로 덮어씀.
2. **채점(scoring)**: 점수 미산정 실행을 모아 별도 LLM 호출로 구조화 채점(JSON) → 정확도/커버리지/감성/추천 여부/순위/속성/경쟁사 목록 저장.
3. **SoV 스냅샷**: 해당 날짜의 **채점된 실행**만 분모로 자사·경쟁사 별 언급률/인용률/추천률을 계산해 날짜별 행으로 upsert.
4. 각 단계의 진행률은 job-store에 기록되어 UI가 표시.

### 3. 스케줄·큐

| 항목 | 현황 |
|---|---|
| 정기 실행 | BullMQ **반복 잡**(7일 간격, 고정 jobId로 부팅마다 upsert → 중복 등록 방지) |
| 팬아웃 | 반복 잡이 켜진 프로젝트(활성 프롬프트 있는 곳)마다 스윕 잡 1개씩 큐에 추가 |
| 재시도 | 잡 attempts 2 + 지수 백오프(5초) |
| 동시성 | 워커 concurrency **1**, 락 30분, 정체(stalled) 감지 60초 |
| 비고 | 큐는 1개뿐(코드 주석에 "Climby에서 포팅" 흔적: 호환용 별칭 존재) |

### 4. 격리·인증·비밀

- 모든 테이블이 `project_id`(cascade 삭제)를 갖는 **프로젝트 단위 격리**. 조직(org)/멤버십 계층은 이 코어에서 확인되지 않음(Better Auth로 계정은 있음 — 세부 권한 모델은 **미검증**).
- API 키: 프로젝트별 입력 가능, **AES-256-GCM**으로 저장 시 암호화, 마지막 4자리만 표시. 키는 환경변수 하나(32바이트 hex)로 관리.
- 공유 링크 토큰은 해시만 저장.
- SSRF: 사용자 입력 URL용 `safeFetch`(리다이렉트 5회 제한, 사설 대역·도커 내부 호스트명 차단). 코드 주석이 **DNS 재해석(TOCTOU)은 미해결**임을 명시.

### 5. 비용·한도

- 엔진별 호출당 실측 단가표(상수)와 사전 비용 추정 함수, DataForSEO **킬스위치**(환경 설정), 실행·채점 각각 토큰·비용 컬럼 저장.
- 조직/프로젝트별 예산 한도나 원장은 확인되지 않음.

### 6. 외부 의존성 / 종속성

OpenRouter 단일 LLM 경로(+모델 폴백 1개), DataForSEO(선택), Redis(필수 — 큐), 단일 워커 컨테이너.

### 7. 미구현·미확인

테스트(거의 없음), 조직 계층·역할 세분화, 다국어 감성/매칭, 한국 엔진, 응답 원문 증거의 재현 가능한 버전 관리(분석 버전 컬럼 없음 — 채점 모델명만 저장), 하루 내 반복 샘플링.

## 03. 핵심 로직 조사

구현 코드·프롬프트 원문은 싣지 않는다. 읽은 파일 기준, 미확인은 "미검증".

### L1. 브랜드 언급 감지 — `services/geo/parser.ts`

- 방식: 소문자화 후 **부분 문자열 포함** 검사(브랜드명·도메인·별칭 중 하나라도 포함이면 true). 이진 값만 반환(횟수·위치 없음).
- 한계: 단어 경계가 없어 짧거나 일반명사형 브랜드가 다른 단어 안에서 오탐 가능(영문 기준). 언급 위치/순서 정보가 없어 "얼마나 눈에 띄는가"를 못 잰다. 한국어는 부분 문자열이라 조사 문제는 없지만 오탐 위험은 오히려 큼(미검증).

### L2. 인용 추출·도메인 — `parser.ts`

- 인용은 OpenRouter 응답의 URL 인용 주석에서만 가져옴(본문 내 URL은 안 봄). 호스트는 소문자 + `www.` 제거.
- 자사 판정: **호스트 일치 또는 점 + 자사 도메인으로 끝남**(서브도메인 허용). 부분 문자열 포함이 아니라 접미사 규칙이라 정확도가 높다(앞 프로젝트보다 우수).
- 한계: 공개 접미사(co.kr 등)·추적 파라미터·단축 URL 정규화는 이 경로에 없음(별도 `url-host.ts` 17줄, 얕음).

### L3. LLM 구조화 채점 — `services/geo/scorer.ts` (핵심 아이디어)

- 목적: 정규식으로 못 잡는 **추천 여부, 추천 순위, 경쟁사 목록·추천·순위, 브랜드 사실 반영도**를 LLM으로 추출.
- 입력: 응답 원문 + "브랜드 지식"(우선 사실, 거래 중단 요소, 차별점, 속성)을 마크다운화한 컨텍스트 + 경쟁사 이름.
- 출력(JSON): 정확도·커버리지·감성(0–100), 추천 여부/순위, 속성별 "인정됨" 여부+증거, 경쟁사별 추천/순위/속성, 서술 이유. 합성 점수 계산.
- 장점: 브랜드 사실 기반 채점(환각/오정보 탐지 가능), 경쟁사까지 한 번에 구조화.
- 한계: ① 단일 판정·검증 세트 없음 → 정확도 미보증 ② "증거"는 자유 서술이고 **원문 구간(span) 인용을 강제하지 않아** 사후 검증 어려움 ③ 응답 1건당 LLM 호출 1회 추가 → 비용 2배 ④ 판정 모델 변경 시 과거와 비교 불가(모델명만 저장, 프롬프트/판정 버전 없음) ⑤ JSON 파싱 실패 시 바깥 중괄호 구간을 잘라 재시도하는 단순 복구 ⑥ 영어 프롬프트 중심(한국어 응답 품질 **미검증**).

### L4. Share-of-Voice 스냅샷 — `services/geo/sov.ts`

- 정의: 날짜별, 브랜드별 **언급률·인용률·추천률** = 해당 브랜드가 나온 실행 수 / 채점 완료 실행 수. (브랜드들의 합이 100%가 되는 "점유율"이 아니라 각자 독립적인 **출현율**.)
- 자사 언급은 L1 부분 문자열, 경쟁사 언급은 L3 LLM이 뽑은 이름을 **정규화 후 이름/별칭 일치**로 매칭. → **자사와 경쟁사의 탐지 방법이 비대칭**(편향 원인).
- 경쟁사 인용은 호스트 일치로 판정.
- 분모가 "채점된 실행"이므로 채점이 일부 실패하면 분모가 줄어 비율이 흔들린다.
- 결과는 날짜별 행으로 저장(upsert) → 이후 정의가 바뀌어도 과거 스냅샷은 그대로(재계산 불가).

### L5. 의도 분류 — `services/geo/intent.ts`, `classify-prompts.ts`

- 두 축을 분리: **의도**(상업적/거래/정보/탐색) × **브랜드명 포함 여부**. 기존 한 필드가 "브랜드 포함 질의"와 "상업적 질의"를 섞어 거짓 정보를 준다는 이유를 코드 주석이 설명.
- 비용 통제: 상업적·거래 의도만 스윕 대상("상업적만" 모드). 휴리스틱(수식어 목록: B2C/B2B 모두) + LLM 분류 병용. 레거시 자유 텍스트를 정식 값으로 매핑.
- 한계: 수식어 목록이 영어 중심.

### L6. 지역 처리 — `locations.ts`, `local-qualifier.ts`, `dataforseo.ts`

- 엔진별로 지원하는 지역 단위가 다름(도시/국가/없음) → **실제 적용된 지역을 별도 컬럼에 기록**하고, 도시를 질문 문장에 녹여 넣은 경우 **실제 보낸 문장을 따로 저장**(재현성).
- 한계: 지역 판별 토큰이 호주·뉴질랜드·영국·캐나다·미국 지명 하드코딩 → 한국 사용 불가. 코드 주석상 엔진 단가와 엔드포인트는 특정 시점(2026-07-17) 실측.

### L7. 오케스트레이션 — `orchestrator.ts`

- 같은 날 이미 한 (프롬프트, 모델) 조합은 **건너뜀**(비용 절약), 수동 재확인만 덮어씀. 덮어쓸 때 오래된 경쟁사 언급을 즉시 삭제해 이중 집계를 방지.
- 빈 스윕은 "성공"이 아니라 **실패로 보고**(미설정 제공자/모두 필터됨 사유 명시) — 운영 신호 설계가 좋음.
- 한계: 하루 1회 표본 → LLM 비결정성을 확률로 다루기 어려움(Neodio는 반복 실행 가중이 있음).

### L8. 품질 신호

- 테스트 2개(미실행). 타입은 TS+Drizzle로 양호. 거대 라우터 파일(2,135줄)은 유지보수 위험. README와 코드 불일치(citation-gap).
- SSRF 가드: 사설 IPv4 대역 7개 + IPv6 확장 처리, 파싱 불가 시 거부. 앞 프로젝트보다 차단 범위가 좁고(예약/문서/멀티캐스트 대역 일부 누락) TOCTOU는 명시적 미해결.

| 조직/브랜드 권한 | 프로젝트 격리만 | 조직·멤버십·브랜드별 권한 |
| 한국어 처리 | 부분 문자열, 영어 휴리스틱 | 조사 처리 매칭, 한국어 감성어 |
| 수집 | 제3자 API 일부 위탁 | 공식 API + 자체 Playwright(네이버·구글) |
| 설정/분석 버전 | 채점 모델명만 | `config_versions`, `run_analyses`, `change_log` |

### 1. 원본의 약한 부분이 곧 Neodio의 기회가 되는 지점

Neodio 점수 문서는 스스로 "감성은 단어 개수 세기라 신뢰 불가 → 신뢰할 수 있는 분류(LLM 등)가 연동되면 다시 점수에 넣는다"고 적는다(`processing/visibility.ts`). 원본의 **LLM 구조화 채점**이 정확히 이 빈칸을 겨냥한다. 단 원본은 검증 없이 쓰므로 **검증 가능한 형태**로 재설계해야 한다(I1).

### I1. 검증 가능한 LLM 답변 평가기 (추천 여부·순위·경쟁사 구조화)

1. 문제: 정규식으로는 "추천했는가 / 몇 번째로 / 어떤 경쟁사와 함께 / 사실과 맞는가"를 알 수 없다.
2. 입력: 응답 원문, 브랜드·경쟁사 사전, (선택) 브랜드 사실 목록
3. 출력: 브랜드별 {언급, 추천 여부, 순위, 입장(긍/부/중립), 사실 일치/불일치 목록} **+ 각 판단의 원문 근거 구간**
4. 요구: 한국어/영어/일본어, 재현성(판정 버전·모델·온도 기록), 사후 검증, 비용 상한
5. 원본 한계: 근거가 자유 서술, 검증 세트 없음, 판정 버전 없음, 응답당 호출 1회 추가
6. 일반 원리: 구조화 출력 + 근거 구간 강제 + 휴먼 라벨 골드셋으로 정밀도/재현율/일치도(κ) 측정, 규칙 기반 1차 필터로 LLM 호출 축소
7. Neodio 대안: 규칙(현 `findBrandMentions`)이 "언급 없음"으로 판정한 응답은 LLM을 부르지 않는다(대다수 응답 절감). 언급이 있는 응답만 판정. 근거 구간이 원문에 실제 존재하는지 **문자열 검증**으로 환각 차단
8. 개선: 자사·경쟁사를 **같은 방법**으로 탐지(원본의 비대칭 제거)
9. 검증: 한국어 골드셋(수백 건), 판정 프롬프트 버전 간 회귀 비교

### I2. 내구성 있는 잡 큐 + 멱등 팬아웃

1. 문제: Neodio의 수집 잡은 프로세스 메모리 Map + 자식 프로세스 방식이라 재시작 시 소실(코드 주석이 "개발용 단일 프로세스" 전제를 명시). 조직이 늘면 정기 배치·재개·동시성 제어가 필요(`llm-collection-guide.md`의 "아직 없는 것"과 일치).
2. 입력: 조직별 정기 실행 정의, 프롬프트 × 엔진 × 마켓 조합
3. 출력: 조직별 잡, 진행률, 재시도, 중단/재개 이력
4. 요구: 멱등(같은 날 같은 조합은 한 번만), 부분 실패 격리, 조직 공정성(한 조직이 큐를 독점 금지), 중복 등록 방지
5. 원본 특징: 고정 식별자의 반복 잡 upsert, 프로젝트별 팬아웃, 유일 키로 일 단위 중복 방지, "아무것도 안 돌았으면 실패" 규칙
6. 원본 한계: 동시성 1, Redis 필수 인프라, 조직 공정성 없음
7. Neodio 대안: Neodio는 이미 PostgreSQL 사용 → **DB 기반 큐(행 잠금 + 건너뛰기 선택)**로 Redis 없이 구현 가능. Vercel Cron 계획과도 맞음
8. 검증: 워커 N개 동시 기동 시 중복 실행 0, 강제 종료 후 재개

### I3. 브랜드 사실 기준 정확도(환각 탐지)

1. 문제: B2B 브랜드는 "AI가 우리를 잘못 설명한다"가 핵심 리스크(가격, 기능, 지원 지역).
2. 입력: 브랜드가 확정한 사실 목록(카테고리별), 응답
3. 출력: 사실별 {정확/오류/언급 없음}, 오류 근거 구간
4. Neodio 현황: 브랜드 사실 저장 구조는 **확인되지 않음**(브랜드 관리는 이름·별칭·도메인 중심) → 신규 데이터 입력 비용 발생
5. 판단: 가치 큼, 단 입력 부담 → 사이트 크롤링 기반 초안 제안(이미 sitemap 크롤 존재)과 결합 검토

### I4. 의도 × 브랜드 포함 여부를 분리한 축 + 지출 게이트

1. 문제: 정보성 질의까지 모두 돌리면 비용이 낭비되고, "브랜드 질의"와 "비교 질의"가 섞여 해석이 흐려진다.
2. Neodio 현황: `gscQueryClassifier.ts`, 프롬프트 토픽 존재 — 분류 축이 이미 이 둘로 분리돼 있는지 **미확인**
3. 판단: 분류 축 비교 후 필요 시 보강. 지출 게이트는 비용 거버너(프로젝트 1의 D1)와 결합

### I5. 재현성 증거 필드: 실제 적용 지역 / 실제 전송 문장

1. 문제: 지역·문장 변형이 있으면 같은 프롬프트라도 다른 질문이 되어 시계열이 오염됨
2. 원본 방식: 요청한 지역과 별개로 "실제 적용된 지역", "실제 보낸 문장(다를 때만)"을 저장
3. Neodio 대안: `prompt_runs`에 해당 필드가 있는지 확인(미확인) 후, 없으면 `rawMetadata`에 증거로 기록. 마켓 차원은 이미 있음

### 버리는 아이디어

- 부분 문자열 언급 감지, 이진 언급만 저장: Neodio가 이미 우수
- 날짜별 SoV 스냅샷 고정 저장: Neodio는 분석 버전 체계가 있어 읽기 시점 계산이 더 일관적(DEFER)
- 프로젝트별 BYOK 암호화 저장: 에이전시 BYOK 요구가 생길 때 재검토(DEFER)
- 호주/영미 지명 하드코딩 로컬 판별: 한국 시장에 무의미
- 코드 이식: AGPL (06)

### D4. 답변 평가기 (Answer Evaluator)

**목표**: 수집된 AI 응답에서 브랜드별 추천 여부·순위·입장·사실 정오를 **원문 근거와 함께** 구조화하되, 검증 가능하고 비용이 통제되게 한다.

**요구사항**
- R1 자사·경쟁사를 **동일한 탐지 방법**으로 처리한다(후보 탐지는 기존 규칙 매칭, 판정은 평가기).
- R2 규칙 단계에서 "대상 브랜드가 하나도 안 나온" 응답은 평가기를 호출하지 않는다(비용 절감).
- R3 평가기 출력의 모든 판단은 **원문에서 잘라낸 근거 구간**을 포함해야 한다. 구간이 원문에 정확히 존재하지 않으면 해당 판단을 무효 처리하고 재시도(최대 1회) 또는 "검증 실패"로 기록.
- R4 출력 스키마: 브랜드별 {언급 확정, 추천(예/아니오/불명), 순위(없으면 null), 입장(긍정/중립/부정/불명), 근거 구간, 확신도}, 응답 수준 {비교 구조 여부, 추천 목록 총개수}
- R5 평가 버전 = (평가 지침 버전, 모델, 온도, 스키마 버전). 모든 결과에 기록. 버전이 다른 결과는 지표를 합칠 때 분리하거나 재평가 후 합산.
- R6 한국어·영어·일본어 응답 지원. 언어별 골드셋으로 별도 보고.
- R7 배치 비용은 D1(프로젝트 1) 거버너를 통과한다.
- R8 평가 결과는 기존 `brand_observations`의 규칙 기반 값을 **덮어쓰지 않고** 별도 계열로 저장하고, 두 방법의 불일치율을 모니터링한다.

**데이터 모델(제안)**
- `eval_profile(id, version, model_id, temperature, schema_version, instruction_hash)`
- `answer_evaluation(id, organization_id, prompt_run_id, eval_profile_id, status, cost_usd, created_at)`
- `answer_evaluation_item(evaluation_id, brand_id, mentioned, recommended, rank, stance, confidence, evidence_start, evidence_end, evidence_verified)`
- `eval_gold_label(id, prompt_run_id, brand_id, labeled_by, recommended, rank, stance, locale)`

**인터페이스(제안)**
- `evaluate(promptRunId, profile) → AnswerEvaluation | skipped(reason)`
- `evaluateBatch(filter, profile, budget) → job`
- `measureProfile(profile, goldSetFilter) → {precision, recall, kappa, byLocale}`

**검증**
- 골드셋: 로케일별 최소 N건(초기 제안 200)을 사람이 이중 라벨, 평가자 간 일치도 먼저 측정(일치도가 낮으면 지침부터 수정)
- 근거 구간 존재율 100% 강제, 환각 구간 비율 보고
- 새 평가 버전 도입 시 골드셋 회귀 통과가 배포 조건
- 규칙 vs 평가기 불일치 샘플링 점검

**지표 반영 원칙(정확도 우선)**: 골드셋 기준 목표 정밀도를 만족하기 전에는 점수에 넣지 않고 **별도 지표로만 표시**한다. 기존 감성 처리 원칙과 동일.

### D5. 내구성 있는 수집 잡 엔진 (Durable Job Engine)

**목표**: 정기·수동 수집을 재시작에도 살아남게 하고, 조직 간 공정하며 멱등하게 실행한다.

**요구사항**
- R1 잡 상태는 DB에 영속(대기/실행/완료/실패/취소), 진행률·로그 요약 저장
- R2 **멱등 키**: (조직, 프롬프트, 엔진, 마켓, 일자[, 표본 번호])가 같으면 중복 실행하지 않는다. 의도적 반복 표본은 표본 번호로 구분.
- R3 정기 실행 정의는 한 곳에 있고, 여러 인스턴스가 동시에 떠도 같은 정기 실행이 한 번만 만들어진다.
- R4 워커는 동시에 여럿이어도 같은 작업을 집지 않는다(행 단위 점유 + 만료 시 회수)
- R5 조직별 동시 실행 수 상한과 라운드로빈 공정성
- R6 재시도: 일시 오류(제한/서버 오류)만 지수 백오프, 영구 오류(인증, 정책 거부)는 즉시 실패. 재시도 횟수 상한
- R7 **"아무것도 실행되지 않았다"는 성공이 아니라 실패**로 기록하고 이유(필터됨/설정 없음/예산 초과)를 표시
- R8 수동 취소는 진행 중 작업을 안전하게 중단하고 부분 결과는 보존
- R9 D1(비용 거버너) 예약 실패 시 해당 작업은 "예산 초과"로 건너뜀(실패와 구분)

**데이터 모델(제안)**
- `job_schedule(id, organization_id, kind, cadence, enabled, next_run_at)`
- `job(id, organization_id, kind, state, idempotency_key UNIQUE, attempt, max_attempts, locked_by, lock_expires_at, progress_json, result_json, error_class)`
- `job_task(job_id, task_key, state, attempt, error_class)` — 부분 실패 격리 단위

**인터페이스(제안)**
- `enqueue(kind, orgId, payload, idempotencyKey)` → 이미 있으면 기존 반환
- `claim(workerId, limit)` → 점유한 작업(조직 공정성 적용)
- `complete / fail(errorClass) / cancel`
- `tick()` → 도래한 `job_schedule`로부터 잡 생성(중복 생성 방지)

**검증**: 워커 N개 × 잡 M개에서 중복 실행 0, 강제 종료 후 회수·재개, 한 조직의 대량 잡이 다른 조직 지연에 주는 영향 측정, 멱등 키 충돌 처리.

| 아이디어(구조화 채점, 멱등 팬아웃, 의도 축 분리) | 일반 개념. 보호 대상 아님. 단 법적 판단은 변호사 |
| 상표/제품명(Climby) | 사용하지 않음 |

### 4. Clean-Room 수행의 한계 (정직한 기록)

- 이 분석은 **같은 세션, 같은 에이전트**가 원본 읽기와 설계를 모두 수행했다. 엄격한 Clean-Room이 아니다.
- AGPL 프로젝트이므로 이 한계가 더 중요하다. 완화책:
  1. 05에는 원본의 파일명·함수명·변수명·프롬프트 문구·점수 차원 이름·임계값을 쓰지 않았다.
  2. 04/05는 "새 세션이 05만 읽고 구현"하도록 구조화했다. **구현자는 원본 저장소를 열람하지 않는다.**
  3. 구현 후 원본과의 구조 유사성(스키마 구성, 함수 분해, 프롬프트 문구)을 점검하는 단계를 추가한다.
- 나는 원본의 채점 프롬프트 원문을 이번 세션에서 읽었다. 구현 단계에서 **같은 세션 재사용을 금지**하는 것이 안전하다.

### 5. 승인 보류 목록

1. DataForSEO 응답 수집 및 재가공의 적법성 — LEGAL_REVIEW
2. 05 설계 구현 전, 법무 또는 IP 담당의 AGPL 파생 가능성 검토(특히 D4 데이터 모델)
3. 의존성 라이선스 전수 검사 — 코드 이식 시에만 필요(현재 이식 안 함)
