## 02. 아키텍처 분석

> **분석 범위 제한**: ELv2/특허 고지 때문에 서버 구현(`src/phoenix/**`)과 Python `phoenix-evals`의 소스는 열람하지 않았다. 아래는 **디렉터리 구성, 공개 문서(`docs/phoenix/**`), Apache-2.0 JS 패키지의 README**에서 확인한 사실만 담는다. 확인하지 않은 것은 "미검증".

### 1. 구성 (디렉터리·문서 수준)

```
src/phoenix/        서버 본체 (core, db, server, trace, datasets, metrics, session …)  ← 미열람
packages/           phoenix-client(Apache), phoenix-otel(Apache), phoenix-evals(ELv2), phoenix-sqlean
js/packages/        phoenix-client, phoenix-otel, phoenix-evals(Apache), phoenix-cli …
docs/phoenix/       tracing, evaluation, datasets-and-experiments, prompt-engineering, self-hosting …
helm/, kustomize/, Dockerfile, docker-compose.yml   배포
```

### 2. 문서로 확인되는 기능 구조

| 영역 | 개념 (문서 기준) |
|---|---|
| 트레이싱 | OTel 기반 계측으로 LLM 앱 실행 기록 |
| 평가 | 평가기 = 코드 평가기 또는 LLM 평가기. 분류형 평가기는 **선택지→점수 매핑**(예: 사실/환각 → 1/0)으로 라벨과 점수를 함께 반환 |
| 사전 구축 지표 | 충실성(근거 기반 여부), 완전성, 간결성, 정확성, 검색 관련성, 거부, 도구 호출/선택/응답 처리, PII 탐지, 환각, 독성, 정확 일치, 정규식 일치, 정밀도/재현율/F-점수 |
| 데이터셋 | 키-값 예시 모음, **모든 삽입·수정·삭제가 버전 관리**되어 실험/평가를 특정 버전에 고정 가능. 수동 큐레이션 → 운영 로그 → 합성 데이터 순 권장 |
| 실험 | 프롬프트·모델·검색 변경을 데이터셋 위에서 평가기와 함께 실행하고 비교 |
| 평가기 추적 | 모든 평가 실행(입력, 평가 프롬프트, 모델 응답, 점수, 재시도/지연)을 추적해 **사람 판단과의 정렬** 검토에 사용 |
| 서버 평가 | 서버가 평가기를 호스팅하는 방식과 코드 평가기(예: LLM 심사위원단) |
| 부가 | 프롬프트 관리(버전·태그), 플레이그라운드, PXI 에이전트, 원격 MCP |

### 3. 평가 방법론 구조 (공개 문서의 "자체 평가기 만들기" 흐름)

1. 지표 선택 → 2. **골든 데이터셋**(정답 라벨 포함, 사용 데이터를 대표해야 함) 구축 → 3. 평가용 LLM 선택(앱 모델과 달라도 됨) → 4. 평가 템플릿 작성(입력, 질문, 출력 형식 명시) → 5. **골든 데이터셋에서 평가기를 돌려 성능 벤치마크**(전체 정확도만이 아니라 클래스별 정밀도·재현율 등을 보라고 안내) → 반복 개선.

### 4. 판정 앙상블 ("심사위원단") — 문서 개념

- 여러 제공자의 LLM이 같은 판정을 하고, 신뢰 가중치로 점수를 가중 평균, 개별 판정은 설명에 남김.
- 사용 권장 상황: 단일 판정자의 편향/자기선호가 점수를 왜곡할 때, 고위험 판정, 판정 모델 간 일치율 비교.
- **참조 없는(reference-free)** 평가(정답 라벨 없이 질문만으로)와 **참조 기반(reference-based)** 평가의 구분.

### 5. 격리·인증·스케일

서버의 인증, 멀티테넌시, 저장소, 큐 구조는 구현 열람 없이는 알 수 없다 → **미검증**. 문서상 SQLite/PostgreSQL 배포 옵션과 Helm 배포가 있다는 정도만 확인.

### 6. 품질 신호

테스트 관련 파일 약 1,355개(경로 이름 기준, 내용 미열람). 문서량이 매우 큼. 구현 품질은 **판단 불가**.

## 03. 핵심 로직 조사

> ELv2 구현은 열람하지 않았다. 아래는 **공개 문서·Apache-2.0 JS 패키지 README에서 읽은 개념**이며, 구현 로직 분석이 아니다. 원문 프롬프트는 싣지 않는다.

### L1. 분류형 LLM 평가기 (개념)

- 입력 변수(질문, 참조 텍스트, 답변)를 템플릿에 넣고 모델이 **허용된 선택지 중 하나**를 고르게 한다. 선택지는 점수로 매핑된다(이진 또는 다중 등급).
- 한계(문서·일반론): 템플릿 문구에 민감, 판정 모델 편향, 단일 호출은 재현성 한계. 골든 데이터셋으로 검증하라고 문서가 스스로 권고.
- 이 방식은 Neodio D4의 "닫힌 선택지 + 근거 구간" 설계와 같은 계열이다.

### L2. 골든 데이터셋 기반 벤치마크 (방법론)

- 평가기를 신뢰하기 전에 **정답 라벨이 있는 대표 데이터**에서 성능을 잰다. 문서는 전체 정확도만이 아니라 **클래스별 정밀도/재현율/F-점수**를 보라고 안내(클래스 불균형에서 정확도는 오해를 부른다).
- 정밀도·재현율·F-beta는 표준 정의이며(문서가 정의 표를 제시) beta로 재현율 가중을 조절.
- 한계: 골든 데이터셋 구축은 노동 집약적. 라벨러 간 일치도(신뢰도)에 대한 문서 언급은 **확인하지 못함**.

### L3. 판정 앙상블 (개념)

- 다수 판정자 + 신뢰 가중 평균, 개별 판정 보존, 판정자 간 일치율을 모델 비교에 활용.
- 한계: 호출 비용 N배, 판정자들이 같은 편향을 공유할 수 있음, 가중치 설정의 근거 불명. 문서도 "고위험일 때"로 한정.

### L4. 평가 실행 추적 (개념)

- 입력, 보낸 프롬프트, 모델의 전체 응답, 최종 점수, 시간·재시도를 모두 남겨 "판정자가 왜 그렇게 판정했나"를 사람이 검토. 목적은 **사람 판단과의 정렬(alignment)**.

### L5. 버전 고정 데이터셋 (개념)

- 모든 변경이 버전이 되고, 실험/평가는 특정 버전에 고정되어 시간에 따른 비교가 가능. 메타데이터로 세그먼트 구분.

### L6. 참조 없는 평가 vs 참조 기반 평가

- 정답이 없을 땐 질문-답변 자체의 품질 판정(참조 없음), 정답이 있으면 비교(참조 기반). Neodio에서는 브랜드 사실 정확도(D6)가 참조 기반, 추천 여부 판정(D4)은 참조 없음 + 골드셋으로 판정기 검증.

### L7. 확인하지 못한 것

서버 로직, 평가 스케줄링·동시성, 비용 처리, 데이터 모델, 인증, 특허 대상 부분 — **의도적 비열람 또는 미검증**.

## 04. 아이디어 추출

### 0. 원칙

ELv2 + 특허 고지 때문에 **Phoenix 고유의 메커니즘은 취하지 않는다.** 아래는 모두 **교과서적 평가 방법론**(정밀도·재현율, 골든 세트, 앙상블 판정, 버전 고정 데이터)으로 환원되는 아이디어만이다. 어느 하나라도 Phoenix 특유 구현 방식이 필요하면 채택하지 않는다.

### 1. Neodio 현황 (직접 확인 + 앞선 분석)

- 판정기(D4)는 아직 없음. 현재 감성은 키워드 개수 방식이라 점수에서 제외.
- 골드셋/라벨링 도구 없음(확인되지 않음). 프로젝트 2·4에서 D4의 선행 조건으로 반복 언급했을 뿐 **구체 설계는 없었다.**
- 변경 이력(`config_versions`, `change_log`)과 분석 버전 체계는 있으나 "판정기 평가용 데이터셋 버전" 개념은 없음.

→ Phoenix 분석의 가치는 **D4의 전제인 골드셋 체계를 구체화**하는 데 있다.

### I1. 골드셋 관리 체계 (D13)

1. 문제: 판정기(D4, D8, D6)의 정확도를 주장하려면 정답 라벨이 있는 대표 데이터가 필요한데, 현재는 만들고 관리하는 절차가 없다.
2. 입력: 실제 수집 응답(이미 `prompt_runs`에 있음), 브랜드/마켓/언어 메타, 사람의 라벨
3. 출력: **버전이 고정된 골드셋**, 분할(개발/검증/봉인), 라벨 이력, 라벨러 간 일치도
4. 요구:
   - 표본 추출은 **대표성**을 보장(엔진·마켓·언어·브랜드 유형·언급 유무로 층화)하고 어려운 사례(동명 브랜드, 약어, 부정 언급)를 의도적으로 포함
   - 이중 라벨 + 불일치 조정, 일치도(예: 카파 계수) 측정 — 일치도가 낮으면 판정 지침부터 수정
   - 라벨 변경은 새 골드셋 버전을 만든다(기존 버전 불변). 판정 프로필 버전은 **특정 골드셋 버전에 고정**해 평가
   - 봉인(검증용) 분할은 프롬프트/지침 개선 과정에서 열람하지 않는다(과적합 방지)
   - 개인정보·제3자 콘텐츠 포함 여부 점검과 보존 기한
5. 원본 한계(문서): 골든 데이터셋 구축 노동 부담, 라벨러 일치도 언급 없음
6. 일반 원리: 층화 표본, 이중 라벨링, 카파, 홀드아웃 검증
7. Neodio 대안: 내부 운영 도구로 시작(관리자 화면). 라벨러 = 네오다임 직원
8. 개선: 라벨링 대상 우선순위를 **판정기와 규칙 기반이 불일치한 샘플**부터 뽑아 효율화(능동 선택)
9. 검증: 골드셋으로 측정한 지표를 실제 운영 샘플 점검 결과와 대조

### I2. 판정기 벤치마크 리포트 (클래스별 지표)

1. 문제: "정확도 90%"는 소수 클래스(예: 추천 vs 비추천)가 적을 때 의미가 없다.
2. 요구: 클래스별 정밀도·재현율·F-점수(beta로 정밀도/재현율 가중 선택), 혼동 행렬, 언어/엔진/브랜드 유형별 분해, 신뢰구간(D2 방식)
3. 지표 반영 게이트: 지표에 넣기 위한 **최소 기준**(예: 핵심 클래스 정밀도 ≥ 사전 합의값)을 판정 프로필 활성화 조건으로 둔다
4. 어떤 오류가 더 해로운지 지표별로 명시(예: 자사 언급 오탐은 가시성 과대평가 → 정밀도 우선)

### I3. 앙상블 판정 (선택적, 비용 통제)

1. 문제: 단일 판정 모델의 편향/자기선호
2. 원본(문서)은 N개 판정자 가중 평균을 제시. 비용 N배.
3. Neodio 대안: **불일치 기반 2차 판정** — 1차 판정이 낮은 확신도이거나 규칙 기반과 불일치할 때만 다른 모델로 재판정, 그래도 갈리면 "불명"으로 기록하고 사람 검토 큐로. 평균 대신 **합의/불명** 범주를 둠
4. 가중 평균 점수는 사용하지 않는다(가중치 근거가 없음)
5. 검증: 골드셋에서 단일 판정 대비 정밀도 개선량 vs 비용 증가량

### I4. 판정 실행 증거 보존 (D4 보강)

- 입력, 실제 전송 프롬프트(D12 처리 후), 모델 응답 전문, 파싱 결과, 지연, 재시도 횟수를 판정 실행 레코드에 보존해 사람이 사후 검토 가능하게. 프로젝트 4의 판정 실행 원장(D4 R-B2)에 필드를 구체화.
- 보존 기간·PII는 D11과 연동.

### I5. 사람 정렬 루프

- 판정 결과와 사람 수정 사항을 비교하는 월간 점검: 오판 유형 분류 → 지침 개정 → 새 판정 프로필 버전 → 골드셋 재평가.

### 버리는 아이디어

### D13. 골드셋 및 판정기 보정 체계 (Gold Set & Judge Calibration)

**목표**: D4·D6·D8 같은 의미 판정기가 지표에 반영되기 전에, 사람이 라벨링한 대표 데이터로 **정확도를 측정·게이트**하고, 판정기 변경마다 같은 기준으로 회귀 검증한다.

#### 구성 요소

**(1) 골드셋 (Gold Set)**
- R1 골드셋은 버전을 가진다. 라벨 추가·수정·삭제는 새 버전을 만들고 이전 버전은 불변.
- R2 항목 = {응답 참조(prompt_run), 브랜드, 판정 대상 질문(예: 추천 여부, 순위, 입장, 신원), 정답 라벨, 라벨러 기록}.
- R3 **분할**: 개발용 / 검증용 / 봉인용. 봉인용은 지침 개정 과정에서 열람 불가(권한으로 강제)하고 배포 승인 시에만 사용.
- R4 **층화 표본 추출**: 엔진, 마켓/언어, 브랜드 유형(일반명사형, 약어, 동명 존재 등), 언급 유무, 답변 길이 구간으로 층화. 어려운 사례 쿼터 지정.
- R5 **이중 라벨링**: 최소 2인이 독립 라벨, 불일치는 조정자가 결정하고 조정 이력 보존. 라벨러 간 일치도를 항목 유형별로 계산해 낮으면 판정 정의 문서를 먼저 개정.
- R6 **능동 선택**: 라벨링 우선순위 큐는 규칙 기반 결과와 판정기 결과가 불일치하거나 판정기 확신도가 낮은 항목을 먼저 노출.
- R7 개인정보·제3자 콘텐츠 점검 표시와 보존 기한(D11 연동).

**(2) 판정기 보정 리포트 (Calibration Report)**
- R8 입력: 판정 프로필 버전 + 골드셋 버전 → 출력: 클래스별 정밀도, 재현율, F-beta(지표별 beta 사전 지정), 혼동 행렬, 언어/엔진/브랜드 유형별 분해, 각 수치의 신뢰구간(D2 방식).
- R9 **활성화 게이트**: 판정 프로필은 핵심 지표가 합의된 기준을 충족해야 `active`가 될 수 있다. 기준은 지표별로 문서화(오탐이 더 해로운 지표는 정밀도 하한, 누락이 더 해로운 지표는 재현율 하한).
- R10 **회귀 게이트**: 새 프로필 버전은 현행 활성 버전보다 핵심 지표가 악화되지 않아야 교체 가능. 악화가 있으면 사유와 승인 기록 필요.
- R11 **드리프트 점검**: 운영 중 주기적으로 소규모 신규 표본을 라벨링해 보정 지표 변화를 감시.

**(3) 불일치 기반 2차 판정 (선택)**
- R12 1차 판정 확신도 또는 규칙 기반과의 불일치가 기준을 넘을 때만 다른 모델로 2차 판정. 두 판정이 합의하면 채택, 갈리면 `불명` 상태로 저장하고 사람 검토 큐로 전송.
- R13 `불명`은 점수에 0으로 넣지 않고 **미측정**으로 취급해 분모에서 제외(별도 비율 표시).
- R14 2차 판정은 D1 거버너 예산을 통과하며, 가중 평균 점수는 만들지 않는다.

**(4) 판정 실행 증거 (D4 R-B2 확장)**
- R15 판정 실행 레코드에 보존: 입력 참조, 실제 전송 문서(D12 처리 후), 모델 응답 전문, 파싱 결과, 근거 구간 검증 결과, 지연, 재시도 횟수, 비용.

#### 데이터 모델 (제안)
- `gold_set(id, version, purpose, created_at, frozen)`
- `gold_item(set_id, item_id, run_ref, brand_id, question_type, split[dev|val|sealed], strata_json)`
- `gold_label(item_id, labeler, label, labeled_at, adjudicated, adjudication_note)`
- `calibration_report(id, profile_id, gold_set_id, metrics_json, passed, created_at)`
- `review_queue(id, target_ref, reason[disagreement|low_confidence|drift_sample], state)`

#### 인터페이스 (제안)
- `sampleForLabeling(strata, quota) → items`
- `computeAgreement(setId, questionType) → {kappa, byType}`
- `calibrate(profile, goldSet) → CalibrationReport`
- `canActivate(profile) → {ok, reasons}`

#### 검증
- 골드셋 크기에 대한 신뢰구간이 기준 폭 이내인지(표본 부족이면 활성화 불가)
- 알려진 오판 샘플 주입 시 리포트가 열화를 감지
- 봉인 분할 접근 로그가 비어 있음(개발 단계)
- 라벨러 일치도가 낮은 유형에서 판정 활성화가 막힘

### 2. 특허 (가장 중요한 위험)

- 이 분석은 **특허의 청구범위를 알지 못한다.** 어떤 코드·기능이 보호 대상인지 판단할 수 없고 추측하지 않는다.
- 저작권(코드 복제)과 특허(방법 실시)는 다르다. **코드를 하나도 복사하지 않아도, 특허 방법을 독립적으로 구현하면 침해가 될 수 있다.** Clean-Room은 저작권 방어일 뿐 특허 방어가 아니다.
- 따라서 05는 **일반 평가 방법론**(층화 표본, 이중 라벨링, 정밀도·재현율, 홀드아웃 검증, 불일치 기반 재판정)에만 한정했다. 이는 널리 알려진 기법이지만 **특허와의 관계는 미검증**이다.
- 구현 전 필수: **변호사/변리사의 특허 침해 가능성 검토**(FTO). 결과 전까지 D13 구현은 보류하되, 코드 없는 골드셋 파일럿(05 §단계 1)은 특허 문제가 없는 사람의 작업이므로 진행 가능.

### 3. 열람 범위의 투명한 기록

- 열람한 것: 루트 LICENSE·IP_NOTICE, 디렉터리 목록, 공개 문서 일부(평가 개념, 사전 구축 지표, 심사위원단 문서, 데이터셋 개념, 평가기 추적), Apache-2.0 JS evals README.

### 4. Clean-Room 수행의 한계 (정직한 기록)

- 같은 세션·같은 에이전트가 읽기와 설계를 모두 수행했다. 엄격한 Clean-Room이 아니다.
- 다만 이번엔 **구현 비열람** 원칙으로 노출 자체를 줄였다. 05는 문서 수준 개념에서 출발해 일반 방법론으로 환원했다.
- D13의 "골드셋 → 보정 리포트 → 활성화 게이트"는 평가 분야의 표준 절차이며 Phoenix 문서도 같은 절차를 안내한다. 개념은 겹치지만 이는 공개 지식이다.

### 5. 서비스 이용(도입) 관점

- **Phoenix를 도입해 내부 관측/평가 도구로 쓰는 안**: ELv2는 자체 호스팅 내부 사용을 허용한다고 문서가 안내하나, ① Neodio 제품에 포함하거나 고객에게 그 기능을 제공하면 위반 소지 ② 어디까지가 "내부 사용"인지 법무 판단 필요 ③ 특허 고지는 별개. → **LEGAL_REVIEW**, 그리고 같은 목적이면 Langfuse(MIT 코어)나 OpenLIT(Apache-2.0)이 라이선스상 훨씬 단순하다.
- Apache-2.0 클라이언트/JS evals 패키지를 라이브러리로 **의존**하는 안: 라이선스상 가능성이 높으나 특허 고지 범위가 해당 패키지에 미치는지 **미확인** → LEGAL_REVIEW.
