### 목적과 핵심 기능

"AI 엔지니어링 플랫폼": LLM 호출·에이전트의 **관측(트레이스)·평가·프롬프트 관리·데이터셋/실험·대시보드**. GEO 도구가 아니다.

| 영역 | 내용 (분석 범위) |
|---|---|
| 관측 | 트레이스/스팬/생성 이벤트 수집(API·OTel), 토큰·비용 계산 |
| 평가 | LLM-as-judge, 코드 평가, 결정 모델 평가, 사용자 피드백, 수동 라벨링(주석 큐) |
| 프롬프트 관리 | 버전·라벨·보호 라벨·의존성, 캐시 |
| 데이터셋/실험 | 데이터셋 항목 버전, 실행(run), 실험 큐 |
| 운영 | 조직/프로젝트/RBAC, API 키 범위, 감사 로그, 모니터(임계값 알림), 자동화(트리거→액션), 데이터 보존·삭제 |
| 기타(범위 밖) | AI 게이트웨이, 인앱 에이전트, 스킬 관리, 토픽 클러스터링 |

### Neodio와의 관계

직접 경쟁이 아니라 **플랫폼 공학 참고 자료**다. Neodio가 앞으로 필요로 하는 것(대량 수집의 내구성, LLM 평가의 거버넌스, 비용 단가 관리, 멀티테넌트 격리)을 이미 대규모로 운영하는 사례다.

### 상용 SaaS 적용 시 위험 요소

1. **`ee/` 영역은 상업 라이선스** — 어떤 형태로도 참조·이식 금지(06).
2. 시스템이 거대하고 인프라(ClickHouse, Redis, S3, Postgres)가 무겁다 — Neodio 현재 규모에 과함.
3. 코드 이식은 MIT여도 정책상 금지.
4. 분석 범위가 방대해 **정독한 부분이 일부**다(03 §0 참고).

## 02. 아키텍처 분석

### 1. 구조

```
web/        Next.js 16 + tRPC + 공개 REST API (인증·RBAC·레이트리밋·수집 엔드포인트)
worker/     별도 서비스: 큐 소비자 + 반복 작업 (수집 처리, 평가, 배치 내보내기, 삭제, 모니터 …)
packages/shared/   도메인 로직·큐 정의·ClickHouse/Prisma·평가 실행·가격 계산·SSRF 방어
  prisma/schema.prisma   PostgreSQL: 조직·프로젝트·키·프롬프트·평가기·데이터셋·모니터 등 "설정/메타"
  clickhouse/migrations  ClickHouse: 트레이스·관측·점수 등 "대량 시계열/이벤트"
ee/ 및 */ee/  상업 라이선스 영역(분석 대상에서 제외)
```

**이중 저장 분리**: 설정/관계형 = PostgreSQL, 대량 이벤트·집계 = ClickHouse, 원본 이벤트 = S3 호환 객체 저장소, 큐/캐시/제한 = Redis.

### 2. 수집(Ingestion) 데이터 흐름 — 핵심 패턴

1. **인증 → 스키마 검증**: 배치 내 이벤트를 개별 검증, 실패는 이벤트 단위로 모아 부분 성공 응답(성공 201, 오류별 400/401/404/500).
2. **정렬**: 생성 계열 이벤트 먼저, 갱신 계열 이벤트는 시간순으로 뒤에(순서 뒤섞임 흡수).
3. **엔티티 단위 묶음**: 같은 엔티티 id의 이벤트를 한 파일로 묶어 **객체 저장소에 먼저 기록**(프로젝트/엔티티 타입/엔티티 id 경로). id는 경로 안전하게 정규화·해시(길이·특수문자·PII 노출 방지).
4. **큐 적재**: 객체 저장 성공 후, **파일 참조만** 큐 작업으로 보냄(본문은 큐에 안 실음). 키 = 프로젝트+엔티티 id 해시로 **샤딩된 큐**에 분산.
5. **지연(delay)**: 평소 수 초, UTC 날짜 경계(23:45~00:15) 부근에서는 더 길게 — 날짜 경계에서 순서 역전으로 생기는 중복 처리를 피하려는 의도.
6. **샘플링**: 프로젝트별 설정 비율을 트레이스 id 해시로 결정(같은 트레이스는 항상 같은 결정).
7. **장애 격리**: 객체 저장소 스로틀(SlowDown) 시 해당 프로젝트를 **보조 큐로 분리 표시**, 프로젝트별 수집 실패 추적 → 한 테넌트의 문제가 전체를 막지 않게.
8. worker가 큐 작업을 받아 객체를 읽고 ClickHouse에 반영, 모델 매칭·비용 계산 수행.

### 3. 큐·스케줄

- Redis + BullMQ 큐가 용도별로 매우 많다(수집, OTel 수집, 평가 실행, LLM-judge 실행, 코드 평가, 실험, 배치 작업, 배치 내보내기, 데이터 보존, 삭제, 알림, 웹훅, 외부 통합…).
- 반복 작업 등록 유틸(중복 등록 방지), DLQ 재시도 큐, 큐 지표 수집 러너.
- 큐 샤딩: 키의 SHA-256 앞부분을 샤드 수로 나눈 나머지.

### 4. 멀티테넌트·권한

- 조직 → 프로젝트 계층, 조직/프로젝트 멤버십과 역할, API 키(범위: 조직/프로젝트, 접근 수준 project/scores), SSO·도메인 검증 모델, 감사 로그(스테이징→릴레이) 모델이 스키마에 존재.
- 거의 모든 테이블에 `projectId` 포함, 삭제는 프로젝트 단위 cascade + 별도 삭제 파이프라인(ClickHouse는 FK 없음 → 애플리케이션 삭제 처리 주석 확인).
- 공개 API에는 요금제별 레이트리밋 서비스.

### 5. 평가(LLM-as-judge) 구조

- **평가기(Evaluator)와 평가기 버전(EvaluatorVersion)** 분리: 버전은 프롬프트/메시지, 모델·제공자·파라미터, 변수 매핑, 출력 정의를 불변으로 보유.
- **규칙(EvaluationRule)** 이 평가기를 대상(트레이스·관측·데이터셋 항목)에 연결하고 샘플링 비율 등을 가짐.
- **실행(JobExecution)**: 상태(대기/지연/완료/오류/취소), 입력 대상 id, 결과 점수 id, 실행 트레이스 id 보존.
- **정지(Block) 사유**: 인증 무효, 엔드포인트 불가, 결제/예산 소진, 제공자 계정 미준비 등 **종결성 오류가 나오면 평가기를 일시 정지**하고 사유를 기록.
- 샘플링: 대상 id를 도메인 분리 해시로 변환해 0~1 값으로 만들고 비율과 비교(결정적).

### 6. 비용 계산

- `Model`(매칭 패턴) + `Price` + `PricingTier`(우선순위, 사용량/속성 조건) 구조. 사용량 키 합산이 조건을 만족하는 첫 티어, 없으면 기본 티어. 조건 평가는 실패 시 안전하게 불일치 처리.

### 7. 외부 URL 방어

- 검증 모듈(스킴·https 강제·URL 자격증명 금지·포트·허용 목록·인코딩 검사·여러 해석 경로의 IP 수집) + **연결 계층**(커스텀 디스패처/에이전트가 실제 연결 시 IP를 재검증) + 리다이렉트 검증.

### 8. 운영·품질

- 테스트 약 813개 파일, 린트 규칙(자체 플러그인), 지표/트레이스 계측(OTel), 배치 데이터 마이그레이션(백그라운드 마이그레이션 모델), 헬스·모니터링 러너.
- 비용: 인프라 복잡도가 매우 높음.

### 9. 미확인

web 계층의 tRPC 라우터 전체, 인증 구현 세부, 과금/요금제 로직(cloud 전용 가능성), 대시보드 쿼리 엔진, 모니터/자동화의 실행 세부는 **정독하지 않았다**.

## 03. 핵심 로직 조사

> **정독 범위(§0)**: 수집 배치 처리(`processEventBatch`), 샘플링, 샤딩, 가격 티어 매칭, 평가 실행·오류 분류, 결정적 샘플링, 외부 URL 검증 일부, Prisma 스키마(프롬프트·평가·실행). 나머지(대시보드 쿼리 엔진, 인증, 과금, 모니터 실행 등)는 **미검증**. 코드·프롬프트 원문은 싣지 않는다. **ee 영역은 열람하지 않았다.**

### L1. 수집 파이프라인 (내구성 우선)

- 목적: 많은 이벤트를 잃지 않고 받아 비동기로 처리.
- 입력/출력: 이벤트 배열 → 부분 성공 결과(이벤트별 상태).
- 핵심 속성:
  - **먼저 원본 영속, 그 다음 큐** — 큐나 DB가 막혀도 원본은 보존.
  - 큐 페이로드는 참조만 → 큐 메모리/크기 한계 회피.
  - 객체 저장 실패는 "실패로 처리하되 치명 예외 전환"(전체 배치 중단), 스로틀은 별도 신호로 분류해 재시도 가능하게.
  - 테넌트 키 샤딩과 장애 테넌트 분리.
- 한계: 설계 복잡도 매우 높고 객체 저장소·Redis 모두 필수. 날짜 경계 지연 같은 휴리스틱은 환경 변수로 조정되는 임시방편 성격(코드 주석이 "비용/성능 트레이드오프, 재검토 필요"라고 인정).

### L2. 결정적 샘플링 (두 곳)

- 수집 샘플링: 트레이스 id의 SHA-256 앞 32비트를 [0,1]로 정규화 후 비율과 비교.
- 평가 샘플링: 도메인 문자열을 섞은 해시에서 53비트를 취해 [0,1] 값 생성(부동소수점 정밀도 때문에 53비트로 고정한 이유를 주석이 설명).
- 가치: **같은 대상은 항상 같은 결정**(재처리·재시도에도 일관), 상태 저장 불필요.
- 한계: 비율 변경 시 이전에 제외한 대상이 새로 포함될 수 있음(허용된 성질).

### L3. 가격 티어 매칭

- 모델 이름 패턴으로 모델 식별 → 사용량(예: 입력 토큰 합계)이 조건을 만족하는 **우선순위 첫 티어** 선택, 없으면 기본 티어.
- 사용량 키는 패턴(정규식)으로 합산 → 제공자마다 다른 사용량 필드 명칭 흡수.
- 조건 평가 중 예외는 "불일치"로 처리(안전 쪽 실패).
- 한계: 정규식을 데이터로 저장·실행(성능·악성 패턴 위험은 코드 상 제어 여부 **미검증**).

### L4. LLM-as-judge 실행

- 평가기 버전 불변 + 규칙이 연결 + 결정적 샘플링 + 실행 레코드 → 나중에 "어떤 버전이 이 점수를 만들었나"를 추적 가능.
- 출력 정의를 영속하고 스키마로 검증. 모델에게는 안전한 필드명으로 요청하고 나중에 계약 필드로 매핑(코드 주석이 "생각(thinking) 모델은 `reasoning`이라는 필드를 사고 공간으로 써서 점수를 누락시킨다"는 관찰을 기록).
- **테스트 실행과 실제 실행이 같은 함수**를 사용(테스트가 실제 요청과 동일한 입력을 보냄).
- 실패 처리: 오류를 구조화 정보로 먼저 분류하고, 구조 정보가 없을 때만 **메시지 패턴**으로 보조 분류. 종결성 오류(인증 무효·결제 소진·엔드포인트 불가·제공자 계정 미준비)는 **평가기를 정지**시켜 같은 실패가 대량 반복되는 것을 방지. 재시도 가능 여부는 제공자 정보가 우선.
- 한계: 패턴 문자열 매칭은 제공자 문구 변경에 취약. 판정 품질 자체를 측정하는 골드셋 기능은 코드에서 확인하지 못함(사람 라벨링 큐는 존재).

### L5. 프롬프트 관리 모델

- (프로젝트, 이름, 버전) 유일, 라벨 배열(예: 운영 라벨), **보호 라벨**(특정 라벨은 권한자만 변경), 커밋 메시지, 의존성(다른 프롬프트의 버전/라벨 참조).
- 한계: Neodio의 "추적 프롬프트 라이브러리"와 목적이 다름(이쪽은 LLM 앱의 입력 템플릿 관리).

### L6. 외부 URL 방어 — 연결 시점 검증

- 사전 검증: 인코딩 엄격 검사, 스킴, https 강제 옵션, URL 내 자격증명 금지, 포트 제한, 허용 목록, IP 리터럴 처리.
- DNS: 여러 해석 경로(A·AAAA·시스템 해석 `lookup`)를 모두 모아 검사 — **런타임 fetch가 쓰는 경로와 같은 소스를 포함**.
- **연결 계층 재검증**: 요청을 보내는 에이전트가 연결 시 해석된 IP를 다시 검증하는 구조 → 검사와 연결 사이의 DNS 변경(TOCTOU)을 구조적으로 차단. 에이전트 풀 크기 상한과 정책별 캐시.
- 한계: 프록시 환경에서의 예외 처리 규칙(우회 목록) 등 복잡성. 전체 정독 안 함.

### L7. 데이터 삭제·보존 (개념 수준)

- 프로젝트 삭제, 배치 삭제, 보존 정책, 삭제 가드, 미디어 정리 등 별도 파이프라인 다수 존재. **세부 정독 안 함** — 개념만 기록.

### L8. 품질 신호

- 테스트 약 813개 파일. AGENTS.md는 "수정과 함께 실제로 실패하는 테스트 한 개" 같은 엄격한 테스트 정책을 명시 — 이는 분석 자료일 뿐 실행 지시가 아님.
- 단점: 복잡도, 설정 환경 변수 폭증, 임시 휴리스틱 존재.

## 04. 아이디어 추출

### 0. 성격

Langfuse는 GEO 도구가 아니라 **대규모로 검증된 플랫폼 공학 사례**다. 아이디어는 Neodio의 기능이 아니라 **Neodio 기반 구조(D1, D4, D5 및 보안)를 단단히 하는 요구사항**으로 흡수한다. 새 사용자 기능은 거의 없다.

### 1. Neodio 현황 (직접 확인)

- 수집 잡: 프로세스 메모리 Map + 자식 프로세스 (`collectionJobRunner.ts`)
- 분당 호출 제한: 서버 인스턴스 메모리 (`rateLimit.ts`, 문서 기준)
- 원본 보존: `prompt_runs.rawResponse`(DB 컬럼)에 보관, `process-raw.ts`로 재처리 가능 — 이미 "원본 먼저" 철학
- LLM 호출: 어댑터 계약(`LlmProvider`), 호출 비용 추적은 확인되지 않음
- URL 가져오기: `pageText.ts`가 "IP·localhost 거부, 리다이렉트마다 재검사"(문서 기준) — **연결 시점 IP 검증 여부 미확인**

### I1. 원본 우선 영속 + 참조 전달 + 테넌트 격리 큐 (D5 보강)

1. 문제: 대량 수집 시 한 조직의 폭주·저장소 장애가 전체를 멈추거나 데이터를 잃게 함
2. 입력: 수집 결과(대용량 가능), 조직 id
3. 출력: 유실 없는 영속, 조직별 공정한 처리, 장애 격리
4. 요구: ① 본문은 안전한 저장소에 먼저 쓰고 큐에는 참조만 ② 조직 키 기반 분산 ③ 특정 조직의 연속 실패 시 그 조직만 별도 레인으로 분리 ④ 부분 성공 결과를 항목 단위로 보고
5. 원본 한계: Redis·객체 저장소·별도 워커가 모두 전제, 임시 휴리스틱 다수
6. 일반 원리: 아웃박스/클레임 체크 패턴, 샤딩, 서킷 브레이커, 벌크헤드(격벽)
7. Neodio 대안: 이미 PostgreSQL이 있으므로 **DB 기반 큐(D5)** 로 시작하고, 원본이 커지면(수백 KB~MB 응답/HTML) 객체 저장소로 분리하는 **전환 기준**을 문서화
8. 개선: 원본이 아직 작은 지금은 큐 인프라를 늘리지 않는 쪽이 더 단순 — 원본 아이디어를 "필요해질 때" 단계로 구분
9. 검증: 한 조직에 인위적 장애를 주입해도 다른 조직의 처리 지연이 허용 범위 내인지

### I2. 결정적 샘플링 (부하 조절·평가 비용 조절)

1. 문제: 모든 응답에 LLM 평가를 돌리면 비용이 2배, 일부만 돌리면 재실행 때 결과가 흔들림
2. 원리: 대상 id를 도메인 분리 해시로 [0,1] 값으로 변환하고 비율과 비교 → 상태 없이 항상 같은 결정
3. Neodio 적용: D4 평가기의 **표본 평가**(전체 대신 비율), 지표 신뢰구간(D2)에 "평가 표본 비율" 반영
4. 유의: 샘플링 결과로 만든 지표는 전수 지표와 섞지 않고 표본 표시를 붙인다

### I3. 평가기 거버넌스 (D4 보강)

1. 문제: LLM 판정은 모델·지침·파라미터가 바뀌면 결과가 달라지고, 오류가 반복되면 비용이 낭비됨
2. 요구:
   - 평가기 정의를 **불변 버전**으로 저장(지침, 모델, 파라미터, 출력 스키마)
   - 모든 판정 결과가 어떤 버전·어떤 실행에서 나왔는지 추적
   - **종결성 오류**(인증 무효, 한도 소진, 엔드포인트 불가)는 즉시 평가기를 **일시 정지**하고 사유를 기록 — 같은 오류가 수천 건 반복되지 않게
   - 오류 분류는 구조화 정보 우선, 문자열 패턴은 보조
   - **테스트 실행과 실제 실행이 같은 코드 경로**
   - 모델에 요청하는 필드명이 모델 동작을 바꿀 수 있음(예: 사고 공간으로 오인되는 필드명) → 출력 계약 검증을 실제 모델별로 확인
3. Neodio 대안: 프로젝트 2의 D4 `eval_profile`에 위 요구를 추가. "정지 사유" 열거형 제공
4. 검증: 키 폐기·한도 소진 상황을 주입했을 때 정지 후 알림이 나가고 잡이 재시도 폭주하지 않는지

### I4. 버전 관리되는 모델 단가 + 조건부 티어 (D1 보강)

1. 문제: 모델 단가가 바뀌고, 컨텍스트 길이에 따라 단가가 달라지는 모델이 있음
2. 요구: 단가표를 **유효 시작일 포함 이력**으로 보관, 사용량 조건으로 티어 선택, 일치하지 않으면 명시적 기본 티어, **단가표에 없는 모델은 비용 미상으로 표시하고 예산 계산에서 보수적으로 취급**(0원 처리 금지)
3. 원본 한계: 정규식을 데이터로 저장
4. Neodio 대안: 패턴 대신 **정확한 모델 식별자 + 별칭 테이블**(정규식 없음) — 위험·성능 문제 회피
5. 검증: 과거 시점 비용 재계산이 당시 단가로 재현되는지

### I5. 외부 URL 가져오기: 연결 시점 IP 검증 (P1·P2의 TOCTOU 공백 해소)

1. 문제: 사전에 호스트를 검사해도 실제 연결 때 DNS가 다른 내부 IP로 바뀔 수 있음(리바인딩)
2. 원본 방식(개념): 사전 검증 + 연결 계층에서 실제 해석된 IP를 다시 검증 + 리다이렉트마다 재검증
3. 추가 요구: https 강제 옵션, URL 내 자격증명 금지, 포트 제한, 인코딩 엄격 검사, 런타임이 쓰는 모든 해석 경로 포함
4. Neodio: `pageText.ts` 등 서버가 사용자/브랜드 도메인을 가져오는 모든 지점에 **단일 안전 fetch 모듈**을 적용해야 함. 현 구현이 연결 시점 검증을 하는지 **확인 필요**
5. 검증: 리바인딩 시뮬레이션(첫 해석 공인 IP, 두 번째 사설 IP)에서 차단

### I6. 임계값 모니터와 알림 라우팅

1. 문제: 지표가 악화돼도 사람이 화면을 열어야 알게 됨
2. 요구: 지표·조건·기간·심각도를 정의하는 모니터, 조직/브랜드별 알림 채널, 중복 억제
3. Neodio 연결: D2(변화 신뢰도)의 "유의한 변화"를 모니터 조건으로, 알림 문구에는 노이즈 가능 표시
4. 판단: 자동 알림은 거짓 알림 위험이 있어 D2 검증 후

### I7. 데이터 보존·삭제 파이프라인 (개념)

1. 문제: B2B 고객은 원본 응답(제3자 콘텐츠 포함)의 보존 기간과 삭제를 요구
2. 요구: 조직/브랜드 단위 보존 기간, 배치 삭제, 삭제 가드(실수 방지), 감사 기록, 원본 vs 파생 데이터 구분
3. Neodio: 현 정책은 확인되지 않음 → 조사 필요(법무와 연계)

### I8. 빌드 대신 도입 검토: 내부 LLM 호출 관측

- Neodio 자체의 LLM 호출(브랜드 정리, 리서치 생성, D4 평가기 등)을 **Langfuse 같은 도구로 관측**하면 호출별 입력/출력/토큰/비용/지연을 직접 만들지 않고 얻을 수 있다.
- 주의: 고객 콘텐츠가 외부로 나가는지(호스팅/자체 호스팅), 인프라 부담(자체 호스팅은 ClickHouse·Redis·S3·Postgres), `ee` 기능 사용 금지. → RESEARCH. 이는 **제품 도입**이지 코드 이식이 아니다.

### D5 보강 — 조직 격리 요구사항

기존 D5(내구성 있는 잡 엔진)에 다음을 추가한다.

- R-A1 **격벽(bulkhead)**: 조직별 동시 실행 상한 외에, 특정 조직에서 연속 실패가 기준(초기 제안: 최근 N건 중 M건)을 넘으면 그 조직의 작업을 **격리 레인**으로 옮기고 낮은 우선순위로 처리. 다른 조직의 처리량에 영향을 주지 않는다.
- R-A2 **참조 전달**: 작업 페이로드에는 대용량 본문을 싣지 않고 식별자만 둔다. 본문은 영속 저장소에 있고 작업은 그 참조를 읽는다.
- R-A3 **원본 크기 경계**: 단일 응답/HTML이 기준 크기(초기 제안 256KB)를 넘으면 객체 저장소로 분리하는 경로를 열 수 있도록 저장소 인터페이스를 추상화. 지금은 DB 저장 유지 가능.
- R-A4 **부분 성공 보고**: 배치 결과는 항목별 {성공, 오류코드, 재시도 가능 여부}.
- R-A5 **결정적 표본**: 부하 조절·평가 비용 조절을 위한 표본 선택은 대상 식별자 기반 결정적 함수를 사용. 같은 대상은 항상 같은 결정, 비율이 바뀌어도 설정 이력과 함께 기록.
- R-A6 **샤드 확장 대비**: 큐 키에 조직 식별자를 포함해, 나중에 물리적 분리(큐/DB 분리)가 가능하도록 한다.

**검증**: 한 조직에 지속 실패를 주입한 상태에서 다른 조직의 대기 시간(p95) 증가가 기준 이내, 재시작 후 작업 손실 0.

---

### D4 보강 — 판정기 거버넌스

기존 D4(답변 평가기)의 `eval_profile`을 다음 요구로 확장한다.

- R-B1 **불변 버전**: 판정 지침, 모델, 샘플링 설정, 출력 스키마는 한 번 만든 버전은 수정할 수 없고 새 버전만 만든다.
- R-B2 **실행 원장**: 모든 판정은 {판정 버전, 대상, 상태[대기/실행/성공/오류/취소], 비용, 시작·종료, 오류코드} 행을 남긴다.
- R-B3 **종결성 오류 정지**: 오류를 {일시적, 영구(인증/한도/엔드포인트/계정), 정책 거부}로 분류한다. 영구 오류가 N회 연속이면 판정 프로필을 **정지 상태**로 전환하고 사유를 저장·알림. 정지 상태에서는 새 판정을 시작하지 않는다.
- R-B4 **분류 계약**: 오류 분류는 어댑터가 반환하는 구조화 코드가 우선이며, 문자열 패턴은 마지막 수단이고 패턴 사용 시 지표로 계수해 구조화 코드 누락을 추적한다.
- R-B5 **시험/실제 동일 경로**: "시험 실행"은 실제 판정과 같은 함수·같은 입력 조립을 사용하고, 결과를 저장하지 않을 뿐이다.
- R-B6 **표본 판정**: 비용 한도 내에서 표본 비율로 판정할 수 있으며, 표본 판정으로 만든 지표는 화면에서 표본임을 표시한다.
- R-B7 **출력 계약 점검**: 판정 모델에 요청하는 출력 필드 구성이 모델 동작에 영향을 줄 수 있으므로, 새 모델 도입 시 골드셋 소규모 점검을 통과해야 활성화한다.

**데이터(제안)**: `judge_run(id, profile_id, target_ref, state, error_class, cost_usd, started_at, finished_at)`, `judge_profile.status[active|paused]`, `judge_profile.pause_reason`.

**검증**: 키 무효화·한도 소진 주입 시 정지 전환 및 알림, 정지 중 새 호출 0건.

### D1 보강 — 단가표

- R-C1 단가표는 **유효 시작일 이력** 보관. 과거 실행의 비용은 당시 단가로 재현 가능해야 함.

### D10. 안전한 외부 요청 모듈 (Safe Outbound Fetch)

**목표**: 서버가 사용자·브랜드가 지정한 URL을 가져오는 모든 지점에서 내부망 접근을 구조적으로 차단한다.

**요구사항**
- R1 **단일 진입점**: 서버의 외부 URL 가져오기는 이 모듈만 통해야 한다(직접 fetch 금지를 린트 규칙으로 강제).
- R2 사전 검증: 스킴 제한(기본 https만, 필요 시 http 허용 설정), URL 내 자격증명 금지, 포트 허용 목록, 호스트 이름 엄격 정규화, 인코딩 이상 거부.
- R3 이름 해석: 런타임 요청이 사용할 해석 경로와 동일한 경로를 포함해 모든 주소를 수집하고, 하나라도 비공개·예약 대역이면 거부.
- R4 **연결 시점 검증**: 실제 연결 직전에 확정된 IP를 다시 검증하고, 검증을 통과한 그 IP로만 연결한다(검사와 연결 사이 이름 해석 변경 차단).
- R5 리다이렉트마다 R2~R4 재적용, 횟수·총 시간·응답 크기 상한.
- R6 IPv6의 IPv4 내장 표현, 변환 주소 대역 등 우회 표현을 모두 정규화해 검사. 해석 실패·파싱 실패는 거부(fail-closed).
- R7 거부 사유는 구조화 코드로 반환(운영 지표 집계용). 사용자 메시지에는 내부 정보를 노출하지 않는다.
- R8 조직별 허용 도메인 모드: 브랜드에 등록된 도메인만 허용하는 정책을 옵션으로 제공(현재 방식 유지 가능).

**검증**: 우회 표현 테스트 세트(IPv4 정수/16진/8진 표기, IPv6 매핑, 점 없는 호스트, 유니코드 호스트), 리바인딩 시뮬레이션, 리다이렉트 체인 테스트.
