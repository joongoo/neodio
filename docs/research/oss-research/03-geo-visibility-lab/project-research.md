### 목적과 핵심 기능

"증거 추적이 가능한 자체 호스팅 GEO 모니터." 고정 질문 세트를 여러 OpenAI-호환 모델에 보내 **브랜드 언급 / 명시적 순위 / 이름 언어(중·영) / 인용 출처 / 실패 상태 / 이력**을 **분리해서** 기록한다.

중요한 설계 철학: 이 도구는 ChatGPT 등 소비자 앱을 수집하지 않는다. **검색 API(텍스트 증거) → 모델 API(증거만으로 답변)**의 2층 구조로 "투명한 복제(transparent replica)" 환경을 만들고, 그 결과를 채점한다. README가 "모델 API 회귀는 소비자 앱 화면과 같지 않다", "내부 지식/학습 포함을 증명하지 않는다"고 명시한다.

- 버전 관리되는 질문 세트 + 비교용 지문(해시)
- 모델·검색 설정 스냅샷 저장, 토큰 사용량 기록, 키는 저장하지 않음
- 일/주/수동 모니터링 계획(기본은 드라이런, `--execute`일 때만 호출), 설치형 스케줄러 없음
- 월 비용 예측(호출 수 × 단가), 절약형 모델 설정 가이드

### 외부 서비스

## 02. 아키텍처 분석

### 1. 구조

```
domestic_geo.py       수집·채점·요약 핵심(단일 파일 822줄): 검색 → 모델 → 채점 → 리포트
monitoring_runner.py  계획 확인(드라이런 기본) / 실행(--execute) / 잠금 파일 / 상태 파일
build_web_data.py     runs-by-provider/**/report.json을 모아 웹 데이터(JS)와 추세 생성
dashboard_server.py   루프백 전용 HTTP 서버 + 모니터링 설정 API(오리진·호스트 검증)
web/                  정적 대시보드 (중/영 전환)
scripts/              bootstrap, 데모 데이터 생성, 릴리스 점검
skills/, .claude-plugin/, .codex-plugin/   에이전트 배포 패키지
```

### 2. 데이터 흐름 (한 번의 수집)

1. 설정 파일에서 **활성 질문 세트**를 불변 스냅샷으로 읽고 지문(해시)을 계산
2. 질문마다: 검색 API 호출 → 상위 N개 증거(`S1..Sn` 번호) 정규화 → 모델 API에 "증거만 사용, 증거 인용 `[S1]`, JSON으로 답하라" 요청
3. 모델의 JSON(`본문`, `추천 엔티티[이름, 순위, 증거 id]`, `사용한 증거`)을 받아 로컬에서 채점
4. 질문별 레코드(상태, 지표, 인용 메타데이터, 토큰 사용량, 경과 시간) + 원본 모델 응답을 파일로 저장
5. 리포트 JSON/Markdown 생성 → 웹 데이터 빌더가 모델별 추세로 집계

### 3. 저장·격리·인증

| 항목 | 현황 |
|---|---|
| 저장 | 로컬 JSON 파일 트리(날짜/시각별 디렉터리). DB 없음 |
| 격리/멀티테넌트 | **없음**(단일 브랜드 설정) |
| 비밀 | 환경변수 또는 macOS 키체인에서만 읽음. 리포트·로그에 기록하지 않음(설계 원칙, AGENTS.md에도 명시) |
| 대시보드 보안 | 루프백만 허용, `Host`/`Origin` 검증으로 DNS 리바인딩·교차 출처 쓰기 차단(설정 API) |
| 검색 증거 | 리포트에는 **본문(passage)을 저장하지 않고** 위치·제목·URL·점수 같은 메타데이터만 보관(제공자 약관/저작권 배려로 보임, 의도는 **미확인**) |

### 4. 스케줄·잡

- 외부 스케줄러(cron/에이전트)가 `monitoring_runner`를 호출하는 구조. 자체 상주 프로세스 없음.
- "오늘 마감 시각이 지났고 오늘 완료 기록이 없으면 실행" → **재호출에 안전한 일 단위 멱등**. 일부 모델 실패 시 "완료"로 기록하지 않아 다음 호출에서 다시 시도.
- 동시 실행 방지: 배타적 생성(O_EXCL) 잠금 파일. 정상 종료 시 삭제. **프로세스가 강제 종료되면 잠금이 남는 구조**(만료 시각 없음).
- 이어달리기(resume): 질문 세트 id+지문이 일치할 때만 이전 성공 레코드를 재사용. 단 **러너는 resume 경로를 넘기지 않아** 재시도 때 이미 성공한 모델의 호출도 반복됨(비용 누수 가능, 코드 정독 근거).

### 5. 치명적 오류 단락(circuit break)

인증/리소스 오류 계열이 한 번 나오면 같은 실행의 남은 질문에 호출을 중단하고 "업스트림 불가"로 표시 → 불필요한 과금 방지.

### 6. 미구현·미확인

DB, 사용자/조직, 통계적 처리(표본 반복, 구간), 소비자 UI 수집, 경쟁사 비교(브랜드 1개 중심 — 경쟁사 필드 확인되지 않음), 한국어. 프런트 JS(687줄)는 **정독하지 않음**.

## 03. 핵심 로직 조사

구현 코드·프롬프트 원문은 싣지 않는다. 정독한 범위: `domestic_geo.py` 대부분, `monitoring_runner.py`, 테스트 일부, `build_web_data.py` 일부. 프런트 JS는 미정독.

### L1. 증거 제한 질의 ("투명 복제")

- 목적: 모델이 학습 지식이 아니라 **제공된 검색 증거만** 근거로 답하게 하여, "이 증거가 주어지면 모델이 우리를 언급/추천하는가"를 측정.
- 입력: 질문, 검색 결과 N개(번호 부여). 출력: 본문 + 추천 목록(이름, 순위, 증거 id) + 사용 증거 목록.
- 강점: 모델이 근거 id를 반드시 달아야 하므로 **인용 유효성 검사**가 쉬움(존재하지 않는 id는 제거 — 테스트에서 확인).
- 한계: 측정 대상이 소비자 AI 제품이 아니라 "검색 API + 모델 API 조합"이라는 점(README 인정). 검색 순위가 사실상 노출을 결정하므로 **브랜드 가시성의 상당 부분이 검색 API 결과에 의해 결정**됨.

### L2. 브랜드 매칭 — 문자 체계 인지 — `brand_match_details`, `alias_spans`

- 정규화(NFKC, 대소문자 접기)한 뒤, **라틴 문자·숫자 별칭은 앞뒤에 영숫자가 없을 때만** 일치(약어가 다른 단어 안에서 오탐되지 않음 — 테스트 `highly` vs `HLY`). 한자(CJK) 별칭은 부분 일치.
- 별칭별 횟수, 중/영 이름 구분 보고, 주변 36자 스니펫 최대 5개 저장 → "왜 언급으로 셌는지"가 화면에서 추적 가능.
- 부정 맥락 단서(예: "~는 추천하지 않는다" 류 문구)가 같은 스니펫에 있으면 표시하고, 모든 언급이 부정 맥락이면 `negative_only`. **언급 수에는 그대로 포함**(경고용 플래그).
- 한계: 단서 목록이 중국어 중심, 단순 부분 문자열 포함 검사라 오탐/미탐 가능(검증 세트 없음).

### L3. 신원(동명 브랜드) 증거 — `score_answer`

- 언급이 있을 때 "정말 우리 회사인가"를 증거층으로 판단: ① 공식 도메인 인용됨 ② 정식 회사명 일치 ③ 핵심 사업어 동반 → 증거가 하나라도 있으면 `supported`, 별칭만이면 `alias_only`.
- 가치: 흔한 단어형 브랜드/동명 기업 구분. 한계: 규칙 수가 적고 가중치 없음, 별칭만 매칭된 경우를 어떻게 지표에 반영할지는 정의되지 않음(별도 표기만).

### L4. 점수 — "투명 복제 점수"

- 순위 점수 70% + 인용 점수 20% + 공식 출처 점수 10%(가중치 설정 가능).
  - 순위: 1위 100점에서 순위당 10점 감점. **언급은 됐지만 순위 없음은 고정 40점**. 미언급은 0점.
  - 인용: 사용 증거 개수 × 20, 상한 100. 공식 출처: 공식 도메인 인용 여부 이진.
- 의도: 어떤 계산인지 공개하고 "타사 사설 점수와 동일하지 않다"고 명시.
- 한계: 선형 감점·고정 40점은 임의 상수(보정 근거 없음). 순위 판정은 **모델이 직접 출력한 JSON**에 의존(규칙 검증 없음). 인용 개수 상한이 빨리 포화.

### L5. 실패 상태 분류와 "0이 아님" 원칙

- 상태: 성공/타임아웃/제한/구문 오류/API 오류/업스트림 불가. 실패 레코드는 지표를 만들지 않고, 요약에서 **분모를 "사용 가능 응답"으로** 하며 사용 가능 응답이 0이면 비율은 null(테스트 `unavailable_is_not_zero`).
- 분류는 오류 **문자열 매칭**(언어별 문구)에 의존 → 취약.

### L6. 질문 세트 버전 + 비교 가능성 지문 — `question_set_fingerprint`

- 비교에 영향 주는 필드(id, 언어, 시장, 각 질문의 id/트랙/의도/문구/태그/활성)만 정렬 직렬화해 해시. 같은 세트 id라도 지문이 다르면 추세를 이어 붙이지 않음("조용한 수정이 과거 추세를 오염시키는 것" 방지). 트랙 구분(`benchmark`/`discovery`)으로 고정 벤치마크와 탐색용 질문을 분리.
- 레거시 단순 목록은 "버전 없음" 스냅샷으로 읽기 전용 호환.

### L7. 실행 설정 스냅샷 / 사용량

- 온도, 최대 토큰, 타임아웃, 사고(thinking) 설정, 검색 모드·결과 수·제공자를 레코드에 보존. 키/헤더는 제외. 토큰 사용량은 허용 필드만 추출.

### L8. 비용 계획

- 계획 단계에서 `모델 수 × 질문 수`로 호출 수를 계산하고(드라이런 기본), README의 예측기가 월 비용을 계산. 가격 미확인 시 `unavailable`로 표시(추정값 은닉 금지).

### L9. 품질 신호

- 테스트 32개(순수 함수 중심: 정규화, 점수, 매칭, 상태, 질문 세트, 오류 변환, 스케줄 판정). CI에서 컴파일·단위 테스트·JS 문법·릴리스 게이트 실행. **실행은 하지 않았다(미검증)**.
- 타입 힌트 있음. 외부 호출은 단일 `post_json`에 모아 타임아웃 → 오류 변환.
- 약점: 단일 대형 모듈, 파일 기반 잠금의 만료 없음, 재시도 때 성공 모델 재호출.

## 04. 아이디어 추출

### 0. 이 프로젝트의 성격

앞의 두 프로젝트보다 **작고 방법론 중심**이다. 제품 구조는 가져올 게 없고(로컬 파일·단일 브랜드), 가치는 **측정의 정직함에 대한 규율**(0과 미측정 구분, 비교 가능성 지문, 증거 층 분리)과 **브랜드 매칭의 정확도 처리**에 있다.

### 1. Neodio를 직접 확인해서 발견한 사실 (이번 분석의 가장 실용적 결과)

`src/lib/backend/processing/text.ts`의 `findBrandMentions`는 영문/숫자 별칭에도 **단어 경계 검사 없이** `escaped + (선택 조사)` 정규식으로 매칭한다.
- 한국어는 조사 처리 덕분에 좋지만, **짧은 라틴 별칭**(예: 약어 `AI`, `HLY`류, 3~4자 영문 브랜드)이 다른 단어 안에서 일치할 수 있다는 코드상 가능성이 있다. 실제 데이터 영향은 **미측정**.
- 반면 원본은 이 케이스를 테스트로 고정해 둠. → I1.

그 외 Neodio 상태(이미 있는 것): 질문 세트 변경 이력(`config_versions`, `change_log`), 실행 결과 상태(`getRunOutcome`), 미측정 "–" 표시, 반복 실행 가중.

### I1. 문자 체계 인지 브랜드 매칭 + 별칭별 근거 보존

1. 문제: 브랜드명/별칭이 일반 단어·약어일 때의 오탐, 그리고 "왜 언급으로 셌는지" 설명 불가
2. 입력: 응답 텍스트, 브랜드명·별칭(한/영/일 혼합)
3. 출력: 별칭별 일치 위치·횟수, 확정 스니펫, 문자 체계별(한글/라틴/한자/가나) 구분
4. 요구: 한국어 조사 허용 유지 + 라틴 별칭 경계 적용 + 숫자·하이픈·점 포함 약어 처리
5. 원본 한계: 한국어·일본어 처리 없음(CJK 범위만), 스니펫 길이 고정, 검증 세트 없음
6. 일반 원리: 유니코드 정규화(NFKC), 문자 범주별 경계 규칙, 스팬 병합(긴 별칭 우선)
7. Neodio 대안: 문자 체계별 규칙 + **골드셋(오탐/미탐 케이스 목록)** 으로 고정 + 매칭 근거(스팬)를 `brand_observations`에 보존
8. 개선: 별칭 단위 통계(어떤 별칭이 실제로 일치를 만드는지) → 브랜드 관리 화면에서 불필요/위험 별칭 제안
9. 검증: 기존 실데이터에 새 규칙을 **그림자 실행**해 차이 건수·샘플을 사람이 점검(정확도 우선)

### I2. 신원 신뢰도 (동명 브랜드 구분)

1. 문제: 일반명사형 브랜드명·동명 기업을 자사 언급으로 잘못 셈
2. 입력: 매칭 스팬, 응답 내 공식 도메인 인용, 정식명 동반, 브랜드 사업 키워드, 주변 문맥
3. 출력: 언급별 신원 신뢰도 등급(확정/개연/미확인)과 증거 목록
4. 요구: 지표에 어떻게 반영할지 사전 정의(등급별 가중 또는 제외 기준) — **원본은 반영 규칙이 없음**
5. Neodio 대안: 등급을 우선 별도 필드로만 저장·표시하고, 골드셋으로 정밀도 확인 후 지표 반영(정확도 우선 원칙). 프로젝트 2의 답변 평가기(D4)의 입력 신호로도 사용 가능
6. 검증: 동명/일반명사형 브랜드 샘플 세트에서 등급별 정밀도

### I3. 비교 가능성 지문 (Comparability Key)

1. 문제: 질문·설정을 조금 고치면 과거와 비교가 조용히 어긋남
2. 원본 방식: 비교에 영향 주는 필드만 정렬 해시 → 같으면 추세 연결, 다르면 분리
3. Neodio 현황: 프롬프트 편집은 `change_log`에 기록되지만, **지표 추세가 편집 전후를 이어 그리는지/끊는지**는 **미확인**
4. Neodio 대안: 지문을 "프롬프트 집합" 단위가 아니라 **(프롬프트, 엔진, 마켓, 분석 버전) 단위 키**로 두고, 추세 계산 시 같은 키 구간끼리만 비교하거나 구간 경계를 시각 표시. 변경이 지표에 미치는 영향 경고(예: "이번 주 프롬프트 12개 수정됨")
5. 검증: 과거 편집 이력을 재생해 추세 단절 지점이 의도와 일치하는지 점검

### I4. 실행 설정 스냅샷 (재현성 증거)

1. 프로젝트 2의 "실제 적용 지역/전송 문장" 아이디어와 합쳐 하나의 **재현성 봉투(envelope)**로 설계: 모델 식별자, 온도·토큰·타임아웃, 웹 검색 여부, 지역, 실제 전송 문장, 토큰 사용량, 비밀 제외
2. Neodio 현황: `llm-collection-guide.md`에 웹 검색 on/off와 모델 환경변수는 있으나 **실행별 스냅샷 저장 여부는 미확인**(`rawMetadata` 확인 필요)

### I5. 실패 분류의 안정화

1. 원본: 오류 **문자열**로 분류 → 취약
2. Neodio 대안: 어댑터가 **구조화 오류 코드**(제한/타임아웃/인증/파싱/정책거부)를 직접 반환하도록 계약화(`LlmProvider` 계약 확장). 상태는 "미측정"과 "0"을 구분(이미 일부 구현)
3. 이는 프로젝트 2의 D5(내구성 잡)의 재시도 정책과 직접 연결

### I6. 치명 오류 단락과 안전한 재시도

1. 인증/쿼터 오류 시 남은 호출 중단 → D5 요구사항에 반영
2. 원본의 약점(성공 모델 재호출)을 반면교사로 D5의 멱등 키로 해결

### I7. 드라이런 기본 + 호출 수 사전 계산

→ 프로젝트 1의 D1(비용 거버너)의 `previewCost`에 흡수. 별도 설계 없음.

### I8. 증거 층 분리 원칙 (제품 메시지)

"모델 답변 / 검색 발견성 / 일반 검색 색인 / 분석 트래픽 / 비즈니스 문의"를 서로 다른 증거로 취급하고 인과를 단정하지 않는다. Neodio의 GSC·LLM·(예정)CDN 로그를 화면에서 섞어 인과를 암시하지 않도록 하는 **UX/카피 원칙**으로 채택(도움말 "가시성 숫자는 이렇게 읽으세요"와 일치).

### 버리는 아이디어

- 증거 제한 질의("투명 복제")를 핵심 측정으로 사용: 소비자 AI 노출과 다른 지표 → Neodio의 실측 철학과 충돌. 단, **콘텐츠 점검 보조 진단**("이 증거가 주어지면 모델이 우리를 언급할까?")으로는 DEFER
- 로컬 JSON 파일 저장, 루프백 서버, 파일 잠금
- 중국 검색/모델 공급자 종속 구조
- 에이전트 플러그인 배포(Neodio는 SaaS)

### D7. 브랜드 매칭 엔진 v2 (Script-Aware Brand Matcher)

**목표**: 한국어·영어·일본어 혼합 환경에서 브랜드·별칭 일치의 오탐/미탐을 줄이고, 모든 일치에 설명 가능한 근거를 남긴다.

**요구사항**
- R1 입력 정규화: 호환 문자 통일(전각/반각 등), 대소문자 접기, 연속 공백 축소. **원문 오프셋을 보존**(근거 표시용).
- R2 별칭을 문자 체계 유형으로 분류: 한글 / 라틴·숫자 / 한자·가나 / 혼합.
- R3 유형별 경계 규칙:
  - 한글: 뒤에 오는 조사·어미 허용 목록을 별도 사전으로 관리(현 방식 유지·확장), 앞은 한글 연속 문자와 결합하지 않을 것(예: 복합명사 중간 일치 방지 여부는 골드셋으로 결정)
  - 라틴·숫자: 앞뒤가 영숫자일 때 불일치. 짧은 별칭(길이 기준 초기 제안 4자 이하)은 추가로 대소문자·주변 문맥 조건 선택 적용
  - 한자·가나: 부분 일치 허용하되 별칭 길이 하한
  - 혼합: 경계는 가장자리 문자 유형을 기준으로 적용
- R4 겹치는 일치는 긴 별칭 우선으로 병합, 같은 위치는 한 번만 집계.
- R5 일치 결과는 별칭별 {시작·끝 오프셋, 매칭 규칙 id, 스니펫}를 보존. 스니펫 길이는 문자 수가 아니라 문장 경계를 우선.
- R6 위험 별칭 진단: 최근 N일 일치 중 사람이 "오탐"으로 표시한 비율, 평균 일치 길이, 일반 단어 사전 충돌 여부로 위험도 산출 → 브랜드 관리 화면에서 별칭 정리 제안.
- R7 **규칙 버전**을 기록한다. 규칙이 바뀌면 새 분석 버전으로 재분석하고, 과거 결과와 병합하지 않는다(기존 분석 버전 체계 사용).
- R8 배포 전 **그림자 실행**: 기존 데이터에 새 규칙을 적용해 결과 차이(새로 일치/사라진 일치)를 목록으로 출력하고 사람이 샘플 검토 후 승인.

**데이터 모델(제안)**
- `match_rule_version(id, rules_hash, created_at, notes)`
- `brand_match_span(observation_id, alias_id, start, end, rule_id, snippet)`
- `alias_risk(alias_id, window_days, false_positive_rate, common_word_conflict, computed_at)`
- `match_review(span_id, reviewer, verdict[correct|false_positive|ambiguous], reviewed_at)`

**인터페이스(제안)**
- `match(text, aliases, ruleVersion) → Span[]`
- `shadowCompare(ruleVersionA, ruleVersionB, filter) → DiffReport`
- `aliasRisk(brandId) → AliasRisk[]`

**검증**: 언어별 골드셋(오탐 후보·미탐 후보 각각 수십~수백 건), 규칙 변경마다 회귀 통과, 그림자 실행 차이 샘플 수동 점검.

### D8. 신원 신뢰도 (Identity Confidence)

**목표**: 일반명사형·동명 브랜드의 언급이 "정말 이 브랜드인가"를 증거 기반으로 등급화한다.

**요구사항**
- R1 입력: 매칭 스팬, 응답 내 인용 도메인(공식 도메인 여부), 정식 상호 동반, 브랜드가 선언한 사업 키워드·제품명 동반, 주변 문맥.
- R2 출력: 언급 단위 {등급(확정/개연/미확인), 증거 종류 목록}. 증거 종류는 닫힌 집합으로 관리.
- R3 **초기에는 지표에 반영하지 않는다.** 등급 분포를 별도 지표로 표시하고, 골드셋 정밀도 목표 달성 후 지표 반영 방식(제외/가중)을 별도 결정.
- R4 브랜드마다 "신원 위험도"(일반 단어 충돌, 동명 후보 존재)를 계산해 위험 브랜드에서만 강한 검증(D4 평가기 호출)을 수행해 비용을 절약.
- R5 등급 규칙도 버전 관리(D7의 규칙 버전과 같은 체계).

**데이터 모델(제안)**: `identity_assessment(observation_id, span_id, grade, evidence_kinds[], rule_version)`.

**검증**: 동명/일반명사형 브랜드 표본에서 등급별 정밀도·재현율, 사람 검토와의 일치도.

---

### D9. 비교 가능성 키와 재현성 봉투 (Comparability & Provenance Envelope)

**목표**: 추세를 이어 그려도 되는 조건을 시스템이 명시적으로 판정하고, 각 실행이 어떤 조건으로 수행됐는지 증거로 남긴다.

**요구사항**
- R1 **비교 키** = (프롬프트 내용 해시, 엔진, 마켓, 수집 방식 버전, 분석 규칙 버전). 키 구성 요소는 추세 영향도에 따라 "필수 일치"와 "경고만"으로 분류.
- R2 추세 계산은 비교 키가 같은 구간끼리 연결하고, 키가 바뀐 지점은 **단절 표시**(데이터 삭제가 아님). 사용자가 원하면 "단절 무시" 보기를 제공하되 경고를 병기.
- R3 변경 영향 알림: 한 주 안에 비교 키가 바뀐 프롬프트 비율이 기준 이상이면 요약 카드에 안내.
- R4 **재현성 봉투**(실행 단위, 비밀 제외): 모델 식별자, 샘플링 설정, 웹 검색 사용 여부, 요청 지역·실제 적용 지역, 실제 전송 문장(원문과 다를 때), 토큰·비용, 수집 도구 버전.
- R5 어댑터는 **구조화 오류 코드**(제한/타임아웃/인증/파싱/정책/알 수 없음)를 반환한다. 문자열 매칭 분류는 금지. 미측정 상태는 0과 구분해 저장·표시.
- R6 치명 오류(인증·쿼터)는 같은 잡의 남은 호출을 중단하고 사유를 기록(D5 연동).

**데이터 모델(제안)**
- `comparability_key(id, prompt_hash, engine, market, collector_version, analysis_rule_version)`
- `prompt_run`에 `provenance_json`, `error_code` 추가(기존 `rawMetadata` 확장으로도 가능 — 구현 시 결정)

**검증**: 과거 프롬프트 편집 이력을 재생해 단절 지점이 기대와 일치, 구조화 오류 코드가 모든 어댑터에서 채워지는지 계약 테스트.

## 06. 라이선스·IP 검토

> 법률 자문이 아니다. 법률 판단이 필요한 항목은 **승인 보류**.

### 1. 라이선스

- 코드: **Apache-2.0**. 허용 범위가 넓고 특허 허여 조항이 있다(일반론). 코드를 재배포·파생할 경우 라이선스 사본 포함, 변경 사실 표시, NOTICE 유지 의무가 있고, 특허 소송 제기 시 허여가 종료되는 조항이 있다.
- 상표: 로고와 회사명(恒利原)은 코드 라이선스에 포함되지 않는다(`TRADEMARKS.md`). 우리는 사용하지 않는다.
- 서드파티: Tabler Icons(MIT) 일부 아이콘 — Neodio는 사용하지 않음.
- 의존성: 서드파티 Python 패키지 없다고 README가 주장하나 `pyproject.toml`을 정독하지 않아 **미검증**.

### 2. 프로젝트 정책과의 관계

Apache-2.0이라 코드 재사용이 라이선스상 가능하지만, 이번 프로젝트 정책은 "코드 비복제, 독립 재설계"다. 따라서 **코드 이식은 법적 문제가 아니라 정책상 금지**한다. 또 언어(Python)·구조(파일 저장)가 Neodio와 달라 이식 가치도 없다.

### 3. 무엇이 보호되는가 (일반론)

| 대상 | 판단 |
|---|---|
| 소스 코드·주석·테스트 케이스 문구 | 보호됨 → 복제 금지 |
| **증거 제한 질의의 시스템 프롬프트 원문** | 표현으로 간주될 수 있어 복제 금지. 05에는 이식하지 않았고, 이 프롬프트를 쓰는 설계 자체를 채택하지 않음 |
| **부정 맥락 단서 목록, 점수 상수(순위 감점·고정 40점 등)** | 선택·배열이 표현일 수 있음 → 05에서 사용하지 않고 "보정 실험으로 결정"으로 대체 |
| 아이디어(비교 지문, 실패≠0, 신원 증거층, 문자 체계별 경계) | 일반 개념. 보호 대상 아님. 단 법적 판단은 변호사 |
| 질문 세트 스키마(`track` 두 값 등) | 05는 사용하지 않음 |

### 4. 서비스 약관·운영 위험

| 항목 | 분류 |
|---|---|
| Tencent WSA 검색 API 결과를 모델 입력으로 사용 | 약관·재가공 조건 **미검증**. 원본은 본문 저장을 피함(의도 미확인). Neodio는 사용하지 않으므로 직접 영향 없음 |
| 중국 모델 API 호출 일반 | Neodio 범위 밖 |
| 원본의 월 비용 추정치(2026-09-21 기준) | 참고용. **미검증** |

### 5. Clean-Room 수행의 한계 (정직한 기록)

- 같은 세션·같은 에이전트가 원본 읽기와 설계를 모두 수행했다. 엄격한 Clean-Room이 아니다.
- 완화책: 05에는 원본의 식별자·단서 목록·상수·프롬프트 문구를 쓰지 않았고, 일반 원리(문자 체계별 경계, 정규화, 해시 기반 비교 키, 증거 등급)만 사용했다.
- 유사성 점검: D7(문자 체계별 라틴 경계)과 D9(비교 키 해시)는 원본의 **개념**을 공유한다. 이는 일반적 공학 기법이라 위험이 낮지만, 구현 시 원본 열람을 금지하고 구조 유사성 점검을 수행한다.

### 6. 승인 보류 목록

1. Tencent WSA 등 검색 API 결과 재가공 조건 — 해당 없음(미사용), 기록만
2. 의존성 라이선스 전수 검사 — 코드 이식 시에만 필요(현재 이식 안 함)
3. 원본의 질문 세트/점수 설계를 가져오는 경우 — 하지 않음

### 종합 판단

- 프로젝트 3은 **작지만 정확도에 직결되는 두 가지**를 건졌다: 매칭 경계(D7)와 비교 가능성(D9). 둘 다 새 인프라 없이 현재 코드 근처에서 가능하다.
- **즉시 확인 가능한 현황 점검 2건** (코드 변경 없음):
  1. 짧은 라틴 별칭이 있는 실제 브랜드를 골라 기존 응답에 대해 오탐 여부를 샘플 점검
  2. 프롬프트 수정 전후로 주간 지표가 이어지는 방식 확인
- 이 둘의 결과로 D7/D9의 우선순위를 확정.
