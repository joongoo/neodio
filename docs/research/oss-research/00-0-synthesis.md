## 01. 종합 결론과 설계 카탈로그

대상(분석 순서): ① geo-aeo-tracker ② ai-visibility-tracker ③ geo-visibility-lab ④ langfuse ⑤ openlit ⑥ phoenix
각 프로젝트 문서: `01-geo-aeo-tracker/` … `06-phoenix/` (각 7종: 01 개요, 02 아키텍처, 03 로직, 04 아이디어, 05 독립 설계, 06 IP, 07 도입 판단)

### 1. 가장 중요한 결론 (먼저 읽기)

1. **제품 구조(멀티테넌트, 점수, 수집, 버전 체계)는 Neodio가 6개 모두보다 앞서 있다.** 가져올 것은 새 화면이 아니라 **측정의 엄밀함 · 운영 스케일의 기반 · 의미 판정의 검증 체계**다.
2. **Neodio가 지금 비어 있는 두 곳을 6개가 정확히 채워준다**: (a) 감성/추천 판정이 신뢰 불가라 점수에서 제외된 상태 → 판정기(D4), (b) 수집 잡이 프로세스 메모리 → 내구성 있는 잡 엔진(D5).
3. **판정기는 골드셋 체계(D13) 없이는 지표에 넣으면 안 된다.** 6개 프로젝트 중 어디도 이 검증을 제대로 하지 않는다. 이것이 정확도 우선 원칙을 실행하는 수단이자 Neodio의 차별점이 될 수 있다.
4. **IP 위험은 프로젝트마다 크게 다르다**(§3). 코드 이식은 6개 모두 금지. 특히 ② AGPL, ⑥ ELv2+특허는 취급을 달리해야 한다.
5. **LLMO 비교 논의에서 나왔던 에이전틱 트래픽(CDN 로그), 엣지 배포, 네이버 AI 검색은 6개 중 어느 것도 다루지 않는다.** 그 영역은 이번 조사로 얻은 것이 없다(별도 설계 필요). → 에이전틱 트래픽은 별도 조사함: [../agentic-traffic-spec.md](../../features/traffic/agentic-traffic-spec.md#section-02) (D14). 엣지 배포와 네이버 AI 검색은 아직 비어 있음.

#### 실제 영향 규모

**운영 DB 읽기 전용 확인 (2026-11-05, 사용자 승인)**
- 방법: Neon 운영 DB에 `BEGIN READ ONLY` 트랜잭션으로 SELECT만 실행(`transaction_read_only = on` 확인), 마지막에 ROLLBACK. 접속 정보는 출력하지 않았고 결과는 집계로만 기록한다. 조회한 표: `organizations`, `brands`, `prompt_runs`.
- 범위: 조직 3개(수집 실행이 있는 조직 2개), 브랜드 4개, 성공 수집 실행 657건(조직별 249건·408건), 매칭 패턴 49개(영문 36, 한글 포함 13). 영문 패턴 중 영숫자 5자 이하는 5개.
- 방법 비교: 각 패턴에 대해 "경계 없는 부분 문자열 일치(현행 방식)"와 "단어 경계를 지킨 일치"를 같은 조직의 성공 응답에서 세어 차이를 봤다.

| 대상 | 패턴 수 | 경계 없는 방식에만 잡힌 답변 | 판정 |
|---|---|---|---|
| 영문/숫자 패턴 | 36 | **0건** (모든 패턴에서 두 방식 결과 동일) | 현재 데이터에서 오탐 없음 |
| 한글 포함 패턴 | 13 | 2건 (한 패턴: "세일즈포스") | 두 건 모두 **정당한 언급** ("세일즈포스나"처럼 조사 '나'가 붙은 경우와 "세일즈포스닷컴" 표기). 오탐 아님 |

**결론**
- **현재 운영 데이터에서는 단어 경계 부재로 인한 오탐이 확인되지 않았다.** 짧은 영문 패턴이 5개 있었지만(예: `IBM` 등) 모두 실제 단어로만 나타났다.
- 위험은 **현재 데이터가 아니라 구조**에 있다: 앞으로 짧은 약어·일반명사형 브랜드를 가진 고객이 들어오면 즉시 발생한다. 따라서 D7의 우선순위를 "긴급 결함 수정"에서 **"고객 확장 전 선제 보강"** 으로 낮춘다.
- 설계 입력 하나: 현행은 경계 검사가 없어서 "세일즈포스**나**", "세일즈포스**닷컴**"처럼 조사·접미가 붙은 정당한 언급도 지금은 잡힌다. 경계 규칙을 도입하면서 허용 조사 목록(현재 `text.ts`는 11개, `나`·`에`·`도` 등 없음)을 넓히지 않으면 **정당한 언급을 놓치게 된다.** 한글 쪽 규칙은 이 실데이터를 회귀 시험 케이스로 삼아야 한다.
- 한계: 응답 657건 규모의 표본이며, 경쟁사 후보 자동 탐지(미등록 이름 추출)는 이 점검에 포함하지 않았다. 로컬 파일/시드에는 4자 미만 영문 별칭이 없었다.

#### 판단

- 코드상 결함은 확정(4곳 구현, 경계 없음). 같은 응답에서 구현마다 언급 판정이 달라질 수 있는 **불일치 위험**도 있다(조사 허용 여부가 다름).
- 운영 데이터 확인 결과 **현재 오탐 영향은 0건**. D7은 "고객 확장 전 선제 보강"으로 우선순위 조정(위 결론 참고).
- 4곳 구현의 **단일 모듈화**는 오탐과 무관하게 유지보수 이득이 있어 D7 범위에 그대로 둔다.

### b. 프롬프트 편집과 추세 연결

#### 사실

1. **편집은 제자리 수정**: `store.ts:566`이 `UPDATE prompts SET text=…` 로 같은 `prompt_id`의 문구를 바꾼다. 중복 문구는 거부한다(`:563`).
2. **증거는 보존됨(좋은 점)**: `prompt_runs.prompt_text_snapshot`에 실행 시점 문구가 저장된다(`schema.ts:70`). 설정 변경은 `change_log`에 전/후 값과 함께 기록된다(`store.ts:567-575`).
3. **추세는 문구 정체성을 보지 않는다**:
   - 가시성 점수는 (주, 모델, 마켓) 단위로 성공 실행 전체를 모은다(`processing/visibility.ts`).
   - 반복 실행 가중치의 묶음 키는 `프롬프트id|모델|마켓|주`(`src/lib/observations.ts:15-30`). 같은 주에 문구 수정 전후 실행이 있으면 **서로 다른 질문이 한 관측으로 묶여** 1/n 가중을 받는다.
4. **화면에 단절 표시 없음**: 추세 컴포넌트에서 변경 이력을 참조하는 곳을 찾지 못했다. 변경 이력은 별도 페이지(`ChangeHistoryClient`)에서만 본다. (UI 전수 확인은 아님 — 가시성 개요 컴포넌트 범위에서만 검색.)
5. **프롬프트 구성 변화**(추가·일시중지)도 평균에 섞인다. 추적 상태 이력(`tracking_events`)은 있으나 점수 계산이 그것을 쓰는지는 이번에 확인하지 못했다(**미검증**).
6. **브랜드·별칭 변경은 과거 전체에 소급**: 분석 캐시 키가 `해시(원문, 인용, 브랜드 목록)`(`store.ts:706, 724`)이라 브랜드/별칭이 바뀌면 다음 조회 때 모든 과거 응답이 재분석된다. 고객에게 나간 리포트는 `neodio_reports.snapshot_json`으로 고정돼 보호된다. 도움말에서 이 소급 동작을 설명하는 문구는 **찾지 못했다**(검색어: 소급, 다음 분석, 이후 분석).

#### 운영 DB 읽기 전용 확인 (2026-11-05, 사용자 승인)

방법: `BEGIN READ ONLY`(`transaction_read_only = on` 확인) + SELECT만, ROLLBACK. 조회한 표: `change_log`, `prompt_tracking`, `prompt_runs`. 주 단위는 코드와 같은 "일요일 시작 UTC 주". 조직은 익명화했고 프롬프트 문구는 조회·출력하지 않았다. (첫 실행은 날짜 타입의 시간대 처리 오류로 0건이 나왔다가 텍스트 비교로 바로잡아 재실행 — 위 수치는 재실행 값이다.)

| 항목 | 값 |
|---|---|
| 변경 이력 범위 | 2026-10-07 ~ 2026-11-03 (약 4주), 총 488행 |
| 이력 종류 | 프롬프트 생성 42 / 프롬프트 수정 261 / 추적 상태 수정 179 / 사용자 6 / **브랜드 0** |
| 프롬프트 수정 261건 중 **문구가 실제로 바뀐 건** | **186건** (문구 외 분류·토픽 변경 75건) |
| 문구를 수정한 추적 | 101개 (추적당 평균 1.8회, 최대 3회) — 전부 수집 실행 기록이 있음 |
| 조직별 분포 | 한 조직이 177건, 다른 조직이 9건 (대량 수정은 한 조직에 집중) |
| **같은 주 안에서 수정 전·후 실행이 한 관측으로 섞인 건** | **0건** |
| 수정과 같은 주에 있는 같은 프롬프트의 성공 실행 | 69건 (수정 전 62, 수정 후 7) — 모두 수정의 한쪽 편에만 있음 |
| 문구 수정이 낀 (조직, 주) | 실행이 있는 10칸 중 2칸(20%), 그 주들의 실행 114건 / 전체 657건(17%) |
| **문구가 바뀐 채 이어진 프롬프트** (스냅샷 2종 이상) | **14 / 135개**(10%), 그 프롬프트의 실행 **152 / 657건(23%)** |
| 그런 프롬프트의 실행이 들어 있는 (조직, 주) | 10칸 중 **7칸** |

해석:
- **주 내부 혼합(앞서 코드로 확인한 가중치 묶음 문제)은 아직 실제로 발생하지 않았다.** 수정이 수집과 다른 주에 몰렸기 때문이다.
- 그러나 **주를 가로지르는 연속성 문제는 이미 발생 중**이다: 문구가 바뀐 프롬프트가 전체 실행의 23%를 차지하고, 10개 주별 집계 칸 중 7칸에 들어 있다. 추세선은 같은 프롬프트 id라는 이유로 문구가 달라진 실행을 이어 붙이며, 화면에 표시가 없다.
- 문구를 수정한 추적 101개 모두에 이미 수집 이력이 있어, **앞으로의 수집분은 새 문구로 쌓이므로 연속성 문제가 점점 커진다.**
- **브랜드 이력 0건은 "기록 누락"이 아니라 "이 기간 변경 없음"에 가깝다**: 코드에는 브랜드 추가·수정·삭제를 기록하는 곳이 있다(`store.ts:797, 816, 830`). 다만 변경 이력은 10월 초에 시작해 그 이전 브랜드 변경은 알 수 없다.
- 한계: 약 4주·657건 규모, 수정 대량 입력이 한 조직에 몰려 초기 설정 작업일 가능성이 크다(의도는 미확인). 이 규모는 운영이 커지면 달라진다.

#### 판단

- D9(비교 가능성 키)의 필요성 확인. 우선 가장 싼 단계는 **추세 계산 변경 없이** 변경 이력의 "프롬프트 문구 수정" 시점을 차트에 표식으로 보여주는 것(D9의 경량 1단계). 데이터상 **지금 바로 표식이 필요한 칸이 7칸**이다.
- 소급 재분석은 정확도에는 이로우나 "지난주 숫자가 오늘 다르게 보일 수 있음"을 사용자가 모를 수 있다 → 문서화/표시 필요.

### c. 서버 외부 URL 가져오기 지점

서버(또는 서버가 띄우는 수집 프로세스)가 **사용자·고객이 지정한 주소**를 직접 여는 지점을 전수 점검했다.

| # | 지점 | 입력 출처 | 현재 방어 | 공백 |
|---|---|---|---|---|
| 1 | `pageText.ts` `fetchPageText` (← `/api/llm-generate`) | 요청의 `sourceUrl` | 브랜드 등록 도메인 허용 목록(자신+하위), IP 리터럴·localhost·`:` 포함·점 없는 호스트 거부, 리다이렉트 수동 처리+매 홉 재검사(최대 3), 크기 1.5MB·10초 제한, HTML만 | 아래 ①~④ |
| 2 | `robotsTxtReader.ts` `getRealRobotsTxtOpportunity` (← 기회/robots 페이지) | 조직의 `domain` | **없음** (`https://${domain}/robots.txt`를 기본 `fetch`) | ⑤ |
| 3 | `youtube.ts:119` `fetchText` | 영상/채널 URL 파생 | 고정 도메인 가정(검증 코드 미확인) | ⑥ |
| 4 | `pageSpeedInsightsReader.ts`, GSC, 네이버 데이터랩, OAuth | 고정 외부 API | 고정 호스트 | 서버가 임의 주소를 열지 않음 — 공백 없음 |
| 5 | `scripts/crawl-sitemap.mjs` (수집기 에이전트가 사용자 PC에서 실행, `collector/agent.ts`) | 사이트맵 URL, 사이트맵 안의 `<loc>` | 시작 URL은 `collectorCrawlSpec.sameSite`로 브랜드 도메인 일치 검사(스킴 http/https만) | ⑦ |

#### 공백 상세

- ① **이름 해석 미검사**: 허용된 도메인이라도 그 이름이 **내부 IP로 해석**되는지 보지 않는다. 브랜드 URL은 사용자가 등록하므로, 공격자가 자기 브랜드의 도메인을 내부 주소로 연결하면 허용 목록을 통과한다.
- ② **포트 제한 없음**: `https://허용도메인:6379` 같은 비표준 포트도 통과(호스트명만 비교).
- ③ **사용자 정보 포함 URL(`user:pass@`)·스킴 검증**은 스킴만 http/https 확인, 자격증명 거부 없음.
- ④ **연결 시점 IP 검증 없음**: 사전 검사와 실제 연결 사이에 이름이 바뀔 수 있다(리바인딩) — 다만 ①이 선행 공백이다.
- ⑤ **robots 가져오기는 방어가 없다**: 호스트 검증도 리다이렉트 제한도 없이 기본 `fetch`(리다이렉트 자동 추적). 입력이 조직 `domain`(관리자가 입력)이라 위험도는 중간이나 구조상 가장 약하다.
- ⑥ 유튜브 쪽 URL 구성 방식은 정독하지 않았다(**미검증**).
- ⑦ 사이트맵 **안에 적힌 주소**와 하위 사이트맵은 호스트 필터 없이 수집기가 열어 본다. 수집기는 **사용자 PC에서** 돌기 때문에 영향 대상은 서버가 아니라 그 PC/LAN이며, 결과 파일이 서버로 올라간다. 사이트맵은 브랜드 도메인 소유자가 통제하므로 일반적으론 위험이 낮으나 구조상 경계가 약하다.

#### 판단

- 강점: 지점 1은 허용 목록·수동 리다이렉트·크기/시간 제한이 갖춰져 **다른 5개 OSS 사례보다 단순하고 이해하기 쉬운 설계**다(허용 목록 모델).
- D10(단일 안전 fetch 모듈)이 필요: ①②⑤를 한 모듈로 해소(해석 결과 IP 검증, 포트 허용 목록, 자격증명 거부, 리다이렉트 제한, 지점 2 적용). 지점 5는 사이트맵 안 URL에도 `sameSite` 적용이 필요.
- 우선순위: ⑤ 방어 없음 > ① 해석 미검사 > ⑦ 사이트맵 내부 URL.

### d. 외부 텍스트가 LLM 프롬프트로 들어가는 경로

서버가 LLM을 호출하는 곳은 3곳이다(`provider.ask`).

| # | 호출 지점 | LLM에 들어가는 텍스트 | 출처 신뢰도 | 출력 처리 |
|---|---|---|---|---|
| 1 | `/api/llm-generate` (`app/api/llm-generate/route.ts`) | 클라이언트가 보낸 `promptText`(최대 3만 자) + (콘텐츠 수정 가이드일 때) **서버가 가져온 외부 페이지 본문 발췌 최대 8천 자** | 페이지 본문은 **제3자 통제**(브랜드 도메인이지만 사용자 생성 콘텐츠·해킹 가능) | 텍스트를 모달 칸에 채움 → 사람이 확인 → 기존 `parse` 검증 후 저장 |
| 2 | `/api/prompt-research` | 사용자가 입력한 토픽·마켓 | 사용자 입력 | 파싱 후 저장, 재생성 시만 호출 |
| 3 | `lib/backend/llm/runner.ts` (수집 CLI) | 추적 프롬프트 문구 | 사용자 소유 | 응답은 원본으로 저장(재투입 안 함) |

지점 1에서 `promptText`는 클라이언트 모달이 조립한다. 대표적으로 **브랜드 최적화**(`src/lib/brandOptimization.ts:144-208`)가 프롬프트에 넣는 내용:
- 등록 브랜드·별칭, 탐지된 후보 이름(**AI 답변에서 추출한 이름**), 이름별 근거 발췌(**AI 답변 원문 150자**).

#### 방어 현황

- 있음: 외부 페이지는 등록 도메인만(지점 1 URL), 길이 상한, 조직별 호출 한도, 응답 JSON 검증("목록에 없는 이름은 버림", `parseBrandOptimization`), **사람 검토 후 반영**(자동 적용 없음).
- 없음: 외부 텍스트의 **구획 분리**(발췌를 지시문 뒤에 그대로 이어 붙이고, 마지막에 "위 발췌를 근거로 답하세요" 지시가 따라옴), 지시문처럼 보이는 문구 탐지, 출력의 근거-입력 대조.

#### 판단

- **현재 영향 범위는 제한적**: 출력이 제안일 뿐이고 사람이 검토하며 자동 반영이 없다. 가능한 피해는 "조작된 콘텐츠 수정 가이드/브랜드 정리 제안이 사용자에게 보임" 수준으로 추정(실제 악용 시나리오 **미검증**).
- 단 **D4(답변 평가기)가 도입되면 같은 경로가 지표 오염 경로가 된다** → D12를 D4 이전에 설계·적용해야 한다는 결론 유지.
- 부수 사실: `/api/llm-generate`는 `write` 권한이 있는 사용자가 **임의 프롬프트(3만 자)를 Gemini에 보낼 수 있는 범용 통로**다(조직별 분당 한도 있음, 메모리 기반이라 인스턴스 간 공유 안 됨). 비용 통제 관점에서 D1의 대상.

### 추출 방법

- 운영 DB를 `BEGIN READ ONLY`(`transaction_read_only = on` 확인) + SELECT만으로 조회하고 마지막에 ROLLBACK. 쓰기·비밀 값 출력 없음.
- 모집단: 성공 수집 실행 657건 × 그 프롬프트가 추적하는 브랜드의 (자사 + 등록 경쟁사) = 후보 쌍 7,512개. **항목 단위 = (응답, 대상 브랜드)**.
- 난수 시드 20261105로 재현 가능.
- 층화: 역할(자사/경쟁사) × 규칙 기반 언급 여부(있음/없음)를 4칸으로 나눠 60/40/60/40건을 배정. 각 칸 안에서 (조직, 플랫폼, 길이 3분위) 그룹을 돌아가며 뽑고, 한 응답에서 최대 2건, 경쟁사 한 곳이 칸의 20%를 넘지 않게 제한.
- **어려운 사례 우선 배정**(칸 정원의 약 35%): 언급이 있는 칸은 별칭으로만 일치 / 조사가 붙은 일치 / 응답 후반부의 단 한 번 언급 / 단 한 번 언급, 언급이 없는 칸은 공백·기호를 지우면 이름이 나오는 근접 미탐 후보.
