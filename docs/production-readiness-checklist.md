# 프로덕션 운영 준비 점검 프롬프트

실제 배포/운영 전, 또는 큰 기능을 머지한 뒤 아래 프롬프트를 그대로 Claude에게
주면 이 문서의 체크리스트를 순서대로 훑습니다. 새로 발견한 항목은 이 문서에
직접 추가해서 다음 점검부터 누락되지 않게 합니다.

## 점검 프롬프트 (복사해서 사용)

```
docs/production-readiness-checklist.md의 체크리스트를 하나씩 코드에서 직접
확인해줘. "아마 괜찮을 것"이라고 넘어가지 말고 실제로 grep/읽기로 확인하고,
프로덕션(Vercel+Neon)과 로컬 dev의 차이를 특히 의심해줘 — 로컬에서만 되고
서버리스에서는 안 되는 패턴(자식 프로세스 spawn, 파일시스템 쓰기, 인메모리
상태)이 지금까지 반복적으로 나온 버그 유형이야. 항목별로 통과/미해결/해당없음
표시하고, 미해결 항목은 우선순위(P0/P1/P2)를 매겨서 보고해줘. 이 문서에 없는
새로운 위험을 발견하면 문서에도 추가해줘.
```

## 체크리스트

### A. 서버리스 호환성 (반복적으로 터진 카테고리)
- [ ] `writeFile`/`mkdir`/`unlink` 등 파일시스템 쓰기가 요청 경로에 없는가
      (`grep -rn "writeFile\|mkdir(" src`) — 있다면 DB(`bridge_entries` 등)로
      옮겨야 함. `.tmp/` 읽기는 로컬 전용 스크립트 결과물이라 허용되지만,
      프로덕션 요청 경로에서 쓰기가 걸리면 안 됨.
- [ ] `child_process.spawn`/`exec`로 외부 바이너리(Playwright, ffmpeg 등)를
      요청 경로에서 실행하지 않는가 — Vercel 함수는 실행시간 제한과 읽기전용
      파일시스템 때문에 브라우저 설치·장시간 작업을 못 함.
- [ ] 진행 상황/작업 상태를 인메모리(`Map`, 모듈 스코프 변수)에만 저장하지
      않는가 — 서버리스 인스턴스는 언제든 재활용되므로 폴링이 유실될 수 있음.
      DB나 외부 큐에 영속화해야 함.
- [ ] 새 DB 연결 풀이 `POSTGRES_URL`(pooled)을 쓰는가, `_NON_POOLING`을
      실수로 우선하지 않는가.

### B. 보안 / 접근 제어
- [ ] 프로덕션 URL에 인증(비밀번호, SSO, IP 제한 중 하나)이 있는가 — 없으면
      URL 아는 누구나 데이터를 보고 고칠 수 있음.
- [ ] API 라우트(`src/app/api/**/route.ts`)가 인증 없이 쓰기 작업을 허용하지
      않는가.
- [ ] 시크릿(.env.local의 클라이언트 시크릿, API 키 등)이 클라이언트 번들에
      섞여 들어가지 않는가 (`NEXT_PUBLIC_` 접두사 오·남용 확인).
- [ ] 외부 서비스 API 키/토큰이 Vercel 프로덕션 env에도 등록돼 있는가
      (로컬 `.env.local`에만 있고 배포엔 없는 경우가 실제로 있었음 — GSC
      OAuth 사례).

### C. 데이터 정합성
- [ ] 로컬 dev DB와 프로덕션(Neon) DB의 스키마/데이터가 divergence 나지
      않았는가 — 로컬에서 UI로 편집한 내용이 Neon에 반영 안 된 사례가 실제로
      있었음(`npm run db:sync-to-prod`로 병합).
- [ ] 로컬에서만 수집되는 데이터(AI 검색 결과 등)가 있다면, 프로덕션으로
      옮기는 절차가 문서화돼 있고 최신 상태인가 (`npm run db:push-to-prod`).
- [ ] DB 백업/PITR이 설정돼 있는가 (Neon 콘솔에서 직접 확인 — 프리 티어는
      기본적으로 제한적일 수 있음).

### D. 관측성 / 장애 대응
- [ ] 에러 모니터링(Sentry 등)이 연결돼 있는가, 아니면 최소한 Vercel 런타임
      로그를 주기적으로 확인하는 습관/알림이 있는가.
- [ ] 외부 API(GSC, PageSpeed Insights, Naver/Google AI) 호출에 쿼터 초과
      시 사용자에게 보이는 에러 메시지가 있는가 (조용한 실패 금지).
- [ ] 배포 실패/런타임 에러 발생 시 알림 채널(Slack, 이메일 등)이 있는가.

### E. 성능
- [ ] Vercel 함수 리전과 DB(Neon) 리전이 같은가 (`x-vercel-id` 응답 헤더로
      확인) — 다르면 쿼리마다 지역간 왕복 지연이 곱해짐.
- [ ] 한 페이지 요청 안에서 같은 무거운 집계를 여러 번 중복 호출하지 않는가
      (React `cache()`로 묶여 있는가).
- [ ] N+1 쿼리(반복문 안에서 개별 쿼리)가 새로 추가된 기능에 없는가.

### F. 사용자 경험
- [ ] 저장/삭제/브릿지 완료 등 상태를 바꾸는 액션에 성공/실패 피드백(토스트
      등)이 있는가 — 조용히 성공하거나 조용히 실패하는 액션 금지.
- [ ] 폼 제출 실패 시 사용자가 원인을 알 수 있는 에러 메시지가 뜨는가
      (`window.alert`로 대충 넘기지 않고, 구체적인 이유 표시).

## 2026-09-23 점검 결과

- **P0 조치완료** 사이트맵 크롤/AI 수집 시작 API가 Vercel(`process.env.VERCEL`)
  에서는 spawn을 아예 시도하지 않고 즉시 명확한 에러를 반환하도록 변경
  ([sitemap-crawl/start](../src/app/api/sitemap-crawl/start/route.ts),
  [collection-runs/start](../src/app/api/collection-runs/start/route.ts)).
  타임아웃까지 조용히 기다리다 실패하는 대신 바로 이유를 안내한다.
  **단, 실제로 프로덕션에서 크롤/수집이 되게 만든 건 아니다** — 여전히
  로컬에서만 실행 가능하고, 이걸 서버리스에서 돌리려면 별도 워커/큐 같은
  아키텍처 변경이 필요하다(범위 밖).
- **P0 조치완료(부수적으로 해소)** 사이트맵 크롤 진행 상황의 인메모리 Map
  문제 — 위 가드로 크롤이 프로덕션에서 아예 시작되지 않으므로, "여러
  서버리스 인스턴스가 같은 Map을 못 본다"는 문제 자체가 발생하지 않게 됨.
  로컬(단일 프로세스)에서는 원래도 문제 없었음.
- **P0 조치완료** 프로덕션에 `SITE_PASSWORD` env var + `src/proxy.ts`의
  HTTP Basic Auth 게이트 추가. Vercel 프로덕션/프리뷰 env에 비밀번호 설정
  완료. 사용자명 `neodigm` + 발급된 비밀번호로 접근.
- **P1 조치완료(부분)** `src/app/error.tsx`/`global-error.tsx` 추가로
  렌더링 에러가 조용히 하얗게 죽지 않고 콘솔에 로그 + 사용자에게 재시도
  화면을 보여줌. **Sentry 등 외부 모니터링 서비스는 계정이 필요해서
  연결하지 않음** — 원하면 DSN을 알려주면 그때 붙일 수 있음.
- **P1 조치완료** GSC API(`gscSearchAnalyticsReader.ts`)의 `.catch(() => [])`
  4곳과 PageSpeed Insights의 `if (!res.ok) return null`이 실패 이유를
  전혀 로그에 안 남기던 것을 전부 `console.error`로 로그하도록 수정.
  UI 동작(빈 결과 폴백)은 그대로 유지 — 대신 Vercel 런타임 로그에서
  원인 추적 가능.
- **P1 미해결 — 코드로 해결 불가** Neon 백업/PITR 설정 확인. 이 세션엔
  Neon API 접근 도구가 없어서 자동 확인 불가능 — Neon 콘솔
  (console.neon.tech → 프로젝트 → Backups/Branches)에서 직접 확인 필요.
  무료 티어는 PITR 보관 기간이 짧을 수 있음.
