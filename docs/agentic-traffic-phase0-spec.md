# 에이전틱 트래픽 0단계 명세 — 로그 파일 업로드 분류기 (D14-0)

상위 문서: [agentic-traffic-research.md](agentic-traffic-research.md). 문서 수준 명세이며 구현은 시작하지 않았다.
전제: **고객 호스팅·CDN 현황을 모른다.** 그래서 어떤 환경에서도 나오는 "로그 파일"을 입력으로 삼는다.

## 1. 목적과 범위

**목적**: 연동 없이, 고객(또는 자사)이 가진 웹 서버·CDN 로그 파일 하나로 "AI 봇이 어떤 목적으로, 진짜로, 어디를 방문했는가"를 보여 준다. 이 단계의 두 번째 목적은 **분류기를 실제 로그로 검증**하는 것이다(1단계 자동 연동 전에).

**하는 것**: 파일 파싱 → 정규화 → 봇 분류 → 진위 검증 → 집계 리포트(+저장 선택).
**하지 않는 것**: 실시간 수집, 호스팅별 자동 연동, 리퍼러/전환 분석, 차단 규칙 생성, 원본 로그 서버 보관.

## 2. 설계 원칙

1. **원본 로그는 서버로 보내지 않는다.** 브라우저에서 파싱·분류하고 **집계 결과만** 보낸다. (개인정보·용량·신뢰 모두에 유리)
2. **진위는 UA가 아니라 UA + IP로 판정한다.** UA만 맞으면 "미검증"이지 "검증됨"이 아니다.
3. **모르는 것은 모른다고 표시한다.** IP 열이 없거나 목록이 낡았으면 "검증 불가"로 분류하고 숫자에서 섞지 않는다(0과 미측정을 구분하는 기존 원칙).
4. **봇 목록은 코드가 아니라 버전 관리되는 데이터**다. 출처와 확인 일자를 가진다.
5. **UA 매칭에 단어 경계를 둔다**(브랜드 매칭에서 배운 교훈, D7).

## 3. 사용자 흐름

1. 브랜드 연결 화면 → "AI 봇 방문 분석(로그 업로드)" 진입
2. 로그 파일 선택(`.log`, `.txt`, `.json`, `.ndjson`, `.csv`, `.gz`) — 여러 파일 가능
3. **형식 자동 감지** → 감지 결과와 첫 5줄 미리보기를 보여 주고 **사용자가 확인**(틀리면 열 매핑을 직접 지정)
4. 호스트(도메인) 선택 — 로그에 여러 호스트가 섞여 있으면 브랜드 도메인만 고르기
5. 브라우저에서 처리(진행률 표시, 취소 가능)
6. **리포트** 표시 → "저장" 선택 시 집계만 서버에 저장
7. 처리 후 원본 파일은 메모리에서 폐기(디스크에 쓰지 않음)

## 4. 지원 입력 형식

| 형식 | 감지 단서 | 비고 |
|---|---|---|
| Apache/Nginx **combined** | `IP - - [날짜] "METHOD 경로 HTTP/x" 상태 크기 "리퍼러" "UA"` | 가장 흔함. 예시 §4.1 |
| Apache/Nginx **common**(UA 없음) | 따옴표 필드가 1개 | **UA가 없어 분류 불가** — 안내 후 중단 |
| Cloudflare Logpush `http_requests` NDJSON | 키 `ClientRequestUserAgent`, `ClientIP`, `ClientRequestPath`, `EdgeResponseStatus`, `EdgeStartTimestamp` (공식 문서 확인) | `VerifiedBotCategory`가 있으면 **참고 열**로 보존(우리 판정과 대조용) |
| Vercel Log Drain NDJSON/JSON 배열 | 중첩 `proxy.userAgent[]`, `proxy.clientIp`, `proxy.path`, `proxy.statusCode`, `host`, `timestamp` (공식 문서 확인) | `proxy`가 없는 행(빌드 로그 등)은 건너뜀. UA는 배열이므로 첫 값 사용 |
| 일반 CSV/TSV | 헤더 행 | 열 매핑 화면 필요(시각, 호스트, 경로, 상태, UA, IP) |

- `.gz` 지원(스트림 해제). 그 외 압축은 거절하고 안내.
- 형식 감지 방법: 앞 200줄에서 형식별 파서를 시도해 **파싱 성공률이 가장 높은 형식**을 제안. 성공률이 낮으면(예: 80% 미만) 자동 확정하지 않고 사용자에게 매핑을 요구.
- **지원하지 않는 형식에서는 조용히 추측하지 않고 중단**하고 이유를 보여 준다.

### 4.1 입력 예시 (합성)
```text
132.196.86.10 - - [05/Nov/2026:09:12:44 +0900] "GET /pricing HTTP/1.1" 200 18342 "-" "Mozilla/5.0 (compatible; GPTBot/1.1; +https://openai.com/gptbot)"
203.0.113.77 - - [05/Nov/2026:09:12:51 +0900] "GET /pricing HTTP/1.1" 200 18342 "-" "Mozilla/5.0 (compatible; GPTBot/1.1; +https://openai.com/gptbot)"
```
첫 줄의 IP는 OpenAI가 공개한 GPTBot 범위 안의 값(조사 시점 목록의 첫 항목 `132.196.86.0/24`)을 **예시로** 쓴 것이고, 둘째 줄은 문서용 예약 주소(`203.0.113.0/24`)다. 같은 UA인데 둘째 줄은 범위 밖 → "의심"이 되어야 한다.

## 5. 정규화 이벤트

모든 형식을 아래 모양으로 맞춘다. 이 이후의 단계는 형식을 모른다.

| 필드 | 설명 | 규칙 |
|---|---|---|
| `time` | UTC 시각 | 로그의 시간대 표기를 따라 변환. **시간대가 없는 형식은 사용자에게 시간대를 묻는다**(기본 추측 금지) |
| `host` | 요청 호스트 | 소문자, 포트 제거. 호스트 열이 없으면 사용자에게 도메인 입력을 요구 |
| `path` | 경로 | 쿼리 문자열 제거, 퍼센트 인코딩 정규화, 끝 슬래시 정책 통일(제안: 루트 외 끝 슬래시 제거) |
| `status` | 상태 코드 | 정수. 군(2xx/3xx/4xx/5xx)으로도 집계 |
| `method` | 메서드 | GET/HEAD/기타. HEAD는 별도 집계(링크 확인용 호출이 많음) |
| `ua` | User-Agent | 원문 유지(집계 시에만 정규화) |
| `ip` | 클라이언트 IP | **분류 직후 폐기.** IPv4/IPv6 모두 지원 |
| `kind` | 요청 종류 | 경로 확장자로 `page`(HTML 추정) / `asset`(이미지·JS·CSS·폰트) / `robots`(`/robots.txt`) / `sitemap` / `llms`(`/llms.txt`) / `other` |

### 5.1 클라이언트 IP 선택 규칙 (중요)
- **CDN·프록시 뒤의 원본 서버 로그**는 기록된 IP가 프록시 주소일 수 있다. 이 경우 모든 봇이 "범위 밖"으로 보여 전부 "의심"이 되는 **심각한 오분류**가 난다.
- 규칙:
  1. 형식이 실제 클라이언트 IP를 직접 제공하면(Cloudflare `ClientIP`, Vercel `proxy.clientIp`) 그것을 사용.
  2. combined 형식 등에서는 기록된 IP를 사용하되, **로그 전체의 IP 분포 점검**을 먼저 한다: 요청 수 대비 고유 IP 비율이 매우 낮거나 상위 소수 IP가 대부분을 차지하고 UA는 다양하면 "프록시 IP로 보임" 경고를 띄우고 **진위 판정을 보류**(전체를 "검증 불가"로 표시). 임계값은 제안 단계(예: 상위 3개 IP가 전체의 50% 초과) — 실제 로그로 보정.
  3. `X-Forwarded-For` 열이 있어도 **위조 가능하므로 기본은 신뢰하지 않는다.** 사용자가 "신뢰하는 프록시 목록"을 지정한 경우에만 오른쪽에서부터 해석.

## 6. 분류 파이프라인

```
이벤트 → ① UA 매칭 → ② 목적 결정 → ③ 진위 판정 → ④ 미분류 수신함 → ⑤ 집계
```

### ① UA 매칭
- 레지스트리의 UA 토큰을 **단어 경계 규칙**으로 대소문자 무시 매칭(영숫자·하이픈이 이어진 토큰 내부 일치는 불일치). 예: `OAI-SearchBot`은 `OAI-SearchBot/1.0`에는 일치, `xOAI-SearchBotz`에는 불일치.
- 여러 토큰이 겹치면 **더 긴(구체적인) 토큰 우선**.
- 일반 브라우저 UA(Chrome/Safari 등)는 봇 후보에서 제외. 봇 힌트 단어(`bot`, `crawler`, `spider`, `fetch`, `agent`, `+http`)가 있는데 레지스트리에 없으면 ④로.

### ② 목적 결정 (UA 토큰 → 목적)
| 목적 | 예 (조사 시점) |
|---|---|
| 학습 | GPTBot, ClaudeBot |
| 검색 색인 | OAI-SearchBot, Claude-SearchBot, PerplexityBot, Googlebot(검색) |
| **사용자 요청 가져오기** | ChatGPT-User, Claude-User, Perplexity-User, Google 사용자 트리거 가져오기 |
| 광고 점검 | OAI-AdsBot, AdsBot(Google) |
| 기타 | (레지스트리에 등록된 그 밖의 목적) |

목적은 **IP가 아니라 UA로** 정한다(Anthropic 목록은 봇을 구분하지 않기 때문 — §7 참고).

### ③ 진위 판정
| UA 일치 | IP 범위 목록 | IP가 운영사 범위 안 | 결과 |
|---|---|---|---|
| 예 | 있음(신선) | 예 | **검증됨** |
| 예 | 있음(신선) | 아니오 | **의심(위장 가능)** |
| 예 | 없음/낡음/IP 열 없음/프록시 IP로 보임 | - | **검증 불가** |
| 아니오 | 있음 | 예 | **"운영사 IP인데 모르는 UA"** → ④ 수신함의 우선 후보(신규 봇 발견 단서) |
| 아니오 | - | - | 일반 트래픽(제외) |

- 운영사 범위 = 해당 운영사의 모든 목록 합집합. 목적별 범위가 따로 있는 운영사(OpenAI, Google)는 **그 UA 목적의 목록**과 대조하고, 다른 목적 목록과만 일치하면 "검증됨(목적 불일치 표시)"로 별도 표기.
- 역DNS 검증은 브라우저에서 불가능하므로 0단계에서는 **쓰지 않는다**(Google도 JSON 범위로 판정).

### ④ 미분류 수신함
- 봇 힌트가 있는데 레지스트리에 없는 UA, 또는 운영사 범위 IP인데 UA를 모르는 요청을 집계: `UA 정규화 문자열(버전 숫자 제거)`, 횟수, 상위 경로, 상태 코드 분포.
- **네이버 AI 계열 같은 신규·국내 봇은 여기서 발견**한다. 사람이 검토해 레지스트리에 추가 요청(수동 승인).

### ⑤ 집계 키
`(날짜[호스트 시간대 기준, 사용자 지정], 호스트, 경로 정규화, kind, 운영사, 봇, 목적, 진위, 상태군, method)` → `횟수`

## 7. 봇 레지스트리와 IP 범위 데이터

### 7.1 레지스트리 항목(데이터 모델 제안)
`id`, `operator`, `uaToken`, `purpose`, `obeysRobots`(yes/no/partial/unknown), `rangeSources[]`(URL 목록, 없을 수 있음), `sourceDocUrl`, `checkedAt`, `status`(active/deprecated), `notes`.

### 7.2 IP 범위 스냅샷(조사 시점 2026-11-05 실물 확인)
| 운영사 | 목록 | 구조 | 규모 | 비고 |
|---|---|---|---|---|
| OpenAI | `openai.com/gptbot.json` 등 목적별 | `{creationTime, prefixes:[{ipv4Prefix}]}` | GPTBot 18개(IPv4만) | 목적별 목록(gptbot / searchbot / chatgpt-user / adsbot) |
| Perplexity | `perplexitybot.json`, `perplexity-user.json` | 동일 구조 | PerplexityBot 13개(단일 IP `/32` 포함) | |
| Anthropic | `claude.com/crawling/bots.json` | 동일 구조 | 14개, **봇별 구분 없는 한 목록** | 목적 판단은 UA로만 가능 |
| Google | `common-crawlers.json` 등 4~5종, 일반 `googlebot.json`도 존재 | 동일 구조, IPv4+**IPv6** | 확인한 목록은 317개(IPv6 147, IPv4 170) | 역DNS 접미사도 있으나 0단계는 JSON만 |
- 위 값은 **조사 시점 스냅샷**이며 변한다. 구현 첫 작업은 각 목록을 받아 **실제 스키마를 코드로 다시 검증**하는 것(스키마 이탈 시 해당 운영사를 "검증 불가"로 격하하고 경고).
- 본 문서가 확인하지 못한 것: OpenAI의 나머지 목록(searchbot/chatgpt-user/adsbot)과 Google 각 JSON의 실제 URL 경로, Perplexity-User 목록 내용.

### 7.3 갱신과 배포
- 서버가 목록을 주기적으로(제안: 일 1회) 받아 보관한다. 각 스냅샷에 `creationTime`(파일 자체), `fetchedAt`, 항목 수, 해시를 남긴다. **받아오는 곳은 고정 목록**이며 D10 안전 fetch를 거친다.
- 실패하면 마지막 성공 스냅샷을 쓰되 **나이가 N일(제안 14일)을 넘으면 "낡음" → 해당 운영사 진위 판정을 "검증 불가"로 격하**.
- 브라우저는 업로드 시작 시 `GET /api/bot-registry`로 {레지스트리, 범위 스냅샷, 버전}을 받는다. 리포트에는 **사용한 레지스트리 버전과 스냅샷 날짜**를 기록한다(재현성).
- CIDR 매칭: IPv4/IPv6 모두. 접두사를 숫자 범위로 정렬해 이진 탐색(수백 개 규모라 성능 문제 없음).

## 8. 브라우저 처리 구조

- 파일은 `File.stream()`으로 **스트리밍**하고 `Web Worker`에서 줄 단위 처리(메인 스레드 멈춤 방지). `.gz`는 스트림 해제.
- 메모리에는 **집계 맵만** 유지(요청 단위 보관 금지). 집계 키 수가 상한(제안 50만)을 넘으면 경로를 상위 N개 + "기타"로 접어 폭주를 막는다.
- 처리량 목표와 파일 크기 상한은 **벤치마크 후 결정**(제안 단계 숫자를 쓰지 않는다). 우선 순서: 정확도 → 메모리 안정성 → 속도.
- 오류 줄은 건너뛰되 **건수와 샘플 줄 번호**를 리포트에 표시. 파싱 실패율이 임계(제안 5%) 넘으면 경고.
- 서버 전송은 집계 JSON뿐. 서버는 스키마·크기 상한·합계 일관성을 검증하고, 호출자 권한(브랜드 접근 권한, 쓰기 권한)을 확인한다.

## 9. 리포트 구성

1. **요약 카드**: 분석 기간, 총 요청 수, 봇 후보 요청 수, 검증됨/의심/검증 불가 비율, 미분류 UA 수
2. **운영사 × 목적 표**: 방문 수와 진위 분해
3. **사용자 요청 가져오기 방문 상위 경로**: 어떤 페이지가 AI 답변을 위해 읽혔나
4. **상태 코드**: 봇별 4xx/5xx 비율과 상위 오류 경로
5. **robots.txt 교차**(기존 robots 진단 결과가 있을 때): 차단 규칙 대비 실제 방문, "막았는데 방문", "허용인데 방문 없음"
6. **사이트맵 커버리지**(기존 사이트맵 크롤 결과가 있을 때): 사이트맵 URL 중 AI 봇이 방문한 비율
7. **의심 요청 표**: UA, 상위 경로, 횟수 (IP는 표시하지 않음 — 집계 시 폐기됨)
8. **미분류 수신함**
9. **이 분석의 한계 박스**: 로그 기간, 호스트, 레지스트리 버전·스냅샷 날짜, IP 판정 불가 사유

표시 원칙: 진위가 다른 요청은 **합산하지 않고** 분해해서 보여 준다. 검증 불가는 0이 아니라 "판정 불가"로 표기.

## 10. 개인정보·보안

- 원본 IP는 분류 후 즉시 폐기하고 서버로 가지 않는다. 의심 요청도 IP를 남기지 않는다.
- 경로의 쿼리 문자열 제거. 경로에 식별자(예: 숫자/UUID 세그먼트)가 있을 때 **마스킹 옵션**(`/user/123` → `/user/:id`) 제공.
- UA 원문에 개인 정보가 들어갈 가능성은 낮으나, 미분류 수신함에 저장하는 UA는 길이 상한과 숫자 버전 제거 정규화를 적용.
- 업로드 파일은 서버에 저장하지 않음을 화면에 명시.
- 법무 확인 필요: 고객 로그 분석의 계약상 근거, 로그 내 개인정보가 브라우저 메모리에서만 처리되는 구조가 충분한지.

## 11. 엣지 케이스

| 상황 | 처리 |
|---|---|
| UA 열 없음(common 형식) | 중단하고 combined 형식 안내 |
| IP 열이 마스킹됨(`x.x.x.0` 등) | 진위 판정 전체 "검증 불가" |
| 한 파일에 여러 호스트 | 호스트 선택/분리 집계 |
| 시간대 불명 | 사용자에게 묻기. 기본값 추측 금지 |
| 로그가 며칠만 포함 | 기간 표시, 주 단위 추이는 최소 2주 이상일 때만 |
| 대용량·중복 파일 업로드 | 파일 해시 + 기간으로 중복 감지 안내 |
| HEAD 요청 다량 | 별도 집계 |
| 봇이 정적 자산만 받음 | `kind`로 분리, 페이지 방문과 합산하지 않음 |
| 레지스트리 신규 봇을 나중에 추가 | 과거 리포트는 재분류하지 않음. 재분석은 사용자가 같은 파일을 다시 올릴 때 |
| 범위 목록 스키마 변경 | 해당 운영사 "검증 불가"로 격하 + 운영 알림 |
| IPv4-mapped IPv6(`::ffff:1.2.3.4`) | IPv4로 변환해 매칭 |

## 12. 정확도 검증 계획 (D13 방식)

1. **합성 픽스처**(공개 가능): 형식별 로그(combined / Cloudflare / Vercel / CSV)에 정상·위장·경계 UA·IPv6·프록시 IP 상황을 섞은 소형 파일. 기대 결과를 함께 작성.
2. **단위 시험 목록**(UA 토큰 경계 포함): `GPTBot`↔`xGPTBot`, `Claude-User`↔`Claude-SearchBot` 충돌 없음, 대소문자, 버전 접미사, 우선순위 규칙, Mozilla 접두 UA.
3. **실로그 골드셋**(자사 사이트 로그 우선): 사람이 줄을 보고 (봇 여부, 목적, 진위 판단 근거)를 라벨링. 같은 이중 라벨링·일치도 절차 사용. 목표 기준(제안): **"검증됨"으로 분류된 요청의 위장 비율 0에 수렴**(정밀도 우선), 그 다음 재현율.
4. **프록시 IP 시나리오**: CDN 뒤 서버 로그로 만든 시험 파일에서 "프록시 IP 경고"가 뜨고 진위 판정이 보류되는지.
5. **레지스트리 변경 회귀**: 목록 갱신 전후로 같은 파일의 분류 차이 목록 출력.
6. 성능은 §8의 벤치마크로 별도.

## 13. 수락 기준 (0단계 완료의 정의)

- 4개 형식을 올바르게 감지하거나, 못 할 때 중단·안내한다.
- 합성 픽스처 전부 기대 결과와 일치, 단위 시험 전부 통과.
- 자사 실로그에서 "검증됨"의 위장 의심 건수가 사람 검토로 0건 확인.
- 프록시 IP 로그에서 오분류 없이 "검증 불가"로 처리.
- 리포트에 레지스트리 버전·스냅샷 날짜·한계 박스가 항상 표시.
- 원본 IP·원본 로그 줄이 서버로 가지 않음을 요청 본문 점검으로 확인.

## 15. 구현 순서 제안

1. 레지스트리·범위 스냅샷 수집기(스키마 재검증 포함) — D10 위에서
2. 정규화 어댑터 4종 + 형식 감지
3. 분류기(UA 매칭·목적·진위) + 합성 픽스처 시험
4. 브라우저 워커(스트리밍·집계)
5. 리포트 화면과 저장
6. 자사 실로그로 골드셋 라벨링과 보정

1~3은 서버·화면 없이 순수 함수로 만들 수 있어, 먼저 분류 정확도만 독립적으로 검증할 수 있다.

## 16. 구현 현황 (1~3단계, 2026-11-05)

위치: `src/lib/agentic/` (UI·DB 없음, 외부 호출 없음). 기존 파일은 변경하지 않았고 `package.json`의 `test:unit`에도 아직 등록하지 않았다(등록은 한 줄 추가라 승인 후).

| 파일 | 역할 |
|---|---|
| `types.ts` | 정규화 이벤트·분류 타입 |
| `cidr.ts` | IPv4/IPv6 파서(앞자리 0 거부, mapped→IPv4), CIDR 포함 판정. BigInt 미사용 |
| `normalize.ts` | 호스트·경로(쿼리 제거, 디코딩) 정규화, 요청 종류, ID 마스킹, 시각 해석(시간대 추측 금지) |
| `ranges.ts` | 공개 IP 목록 검증(스키마 이탈·빈 목록은 무효), 낡음 판정 보관소 |
| `registry.ts` | 봇 레지스트리 v`2026-11-05.1` + 일관성 검증. 확인하지 못한 항목은 `confidence`/`urlVerified`로 표시 |
| `adapters.ts` | combined / Cloudflare / Vercel / CSV 어댑터 |
| `detect.ts` | 형식 자동 감지(확신 0.8 미만·CSV·시간대 없음은 사용자 확인 요구) |
| `uaMatch.ts` | 단어 경계 UA 매칭, 수신함 후보 판별·정규화 |
| `ipTrust.ts` | 기록된 IP가 프록시 주소인지 점검(스트리밍, 메모리 상한) |
| `authenticity.ts` | 진위 판정표 구현(검증됨/의심/검증 불가 + 사유) |
| `classify.ts` | 이벤트 → 분류 결과 |
| `*.test.ts`, `testing.ts` | 단위 시험 98개와 합성 IP 목록 도우미 |

실행: `npx tsx --test src/lib/agentic/*.test.ts` → 98개 통과. 타입 검사·ESLint 통과.

**시험이 잡은 실제 버그**: combined 정규식의 캡처 그룹 번호를 한 칸씩 잘못 읽어 리퍼러를 UA로 취급했다. 구현 직후 시험에서 발견해 수정했다.
**시험 민감도 확인**: 복사본에서 일부러 (1) 단어 경계 제거 (2) 프록시 IP 점검 제거 (3) "일부 목록만 쓸 때 단정 방지" 제거 (4) 빈 목록 허용 — 4가지 모두 시험이 실패로 잡았다.

명세 대비 달라지거나 새로 정한 것:
- combined 시각에 오프셋이 없으면 `bad-time`이 아니라 `time-needs-timezone`으로 돌려 사용자에게 묻도록 함(명세 §5 취지와 일치).
- 로그가 작아(200건 미만) IP 신뢰를 판단할 수 없으면 "범위 밖"을 의심 근거로 쓰지 않고 `ip-trust-unknown`으로 둔다(검증됨은 유지).
- 프록시 의심 신호를 "상위 IP 점유율"만이 아니라 "그 IP들 뒤의 서로 다른 UA 수"와 결합했다 — 봇이 트래픽 대부분인 작은 사이트의 오탐 방지. 임계값(점유 50%, UA 10종, 최소 200건)은 **제안값**이며 실로그로 보정이 필요하다.
- 일부 목록만 쓸 수 있는 봇(Googlebot의 두 목록 중 하나 누락 등)은 "포함"이면 검증됨, "미포함"이면 단정하지 않고 `ranges-partial`.

아직 확인하지 못한 것:
- Cloudflare `ClientRequestMethod` 필드는 문서 조사에서 확인하지 못해 "있으면 사용, 없으면 UNKNOWN"으로 처리.
- Cloudflare `EdgeStartTimestamp`의 실제 형식(RFC3339/숫자)은 설정에 따라 다를 수 있어 둘 다 허용.
- 레지스트리의 OpenAI·Perplexity-User·Google 일부 목록 URL은 문서의 이름만 확인(`urlVerified: false`). 구현 후속 작업인 "수집기"가 첫 번째로 실제 스키마를 재검증해야 한다.
- 네이버 `Yeti`는 2차 자료 기반(`confidence: low`), AI 브리핑 전용 봇은 여전히 미확인.
- 실제 로그로 검증하지 않았다(합성 픽스처만). 골드셋 라벨링과 자사 로그 보정이 다음 단계.
