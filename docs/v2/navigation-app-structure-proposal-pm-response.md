# Neodio 메뉴 및 앱 진입 구조 개편 지침

## 1. 작업 목적

Neodio의 기능 확장에 대응하기 위해 기존 단일 메뉴 구조를 **업무 영역별 앱 전환 구조**로 개편합니다.

이번 작업의 목적은 기능을 추가하거나 기존 기능을 재개발하는 것이 아니라, 사용자가 현재 업무 영역을 쉽게 이해하고 관련 기능 사이를 자연스럽게 이동할 수 있도록 정보 구조(IA)와 내비게이션을 개선하는 것입니다.

**핵심 구조**

`전역 컨텍스트 → 앱 GNB → 앱별 LNB → 페이지 탭 → 상세 드릴다운`

별도의 서비스, 데이터베이스 또는 인증 시스템으로 분리하지 않습니다. 기존 Neodio 애플리케이션 내에서 UI와 라우팅 중심으로 개편합니다.

## 2. 기본 구현 원칙

1. 기존 기능, 데이터, API, DB 스키마, 수집 파이프라인, 권한 정책은 변경하지 않습니다.
2. 기존 화면과 컴포넌트를 최대한 재사용하고, 메뉴 및 레이아웃 구조를 중심으로 최소한의 수정을 진행합니다.
3. 기존 URL의 직접 접근 및 북마크 호환성을 유지합니다. 경로 변경이 필요한 경우 리다이렉트 또는 호환 라우팅을 제공합니다.
4. UI상 앱을 분리하더라도 인증, 조직, 브랜드, 공통 데이터는 공유합니다.
5. 메뉴 분류는 DB 테이블이나 코드 모듈이 아닌 사용자의 업무 목적을 기준으로 합니다.
6. 일반 사용자가 접근하는 기능과 내부 운영·검증 기능을 구분합니다.
7. 기존 화면이나 메뉴를 임의로 삭제하지 않습니다. 중복 또는 통합이 필요한 화면은 먼저 현황과 영향 범위를 보고합니다.
8. 승인되지 않은 신규 분석 기능이나 데이터 가공 로직을 추가하지 않습니다.

## 3. 전역 GNB 구조

GNB는 다음 5개 영역으로 구성합니다.

| GNB | 역할 |
|---|---|
| 홈 | 서비스 전체 현황과 다음 행동을 안내하는 허브 |
| AI 가시성 | AI 답변 내 브랜드 언급, URL 인용, 프롬프트 성과 분석 |
| 검색·콘텐츠 | 검색 성과 분석과 웹 콘텐츠 진단 및 개선 기회 관리 |
| YouTube | YouTube AIO 모니터링 및 영상 관리 |
| 관리 | 조직, 브랜드, 사용자, 데이터 연결, 운영 설정 |

조직·브랜드 선택, 사용자 메뉴 등은 전역 컨텍스트로 유지합니다.

`관리`는 업무 분석 앱과 성격이 다르므로 GNB에서 시각적으로 구분하는 것을 권장합니다.

전역 검색은 향후 확장 대상으로 두며 이번 1차 구현의 필수 범위에서 제외합니다.

## 4. 앱별 목표 메뉴 구조

아래 구조는 목표 IA입니다. 기존 기능과의 매핑을 우선 수행하고, 기능이 아직 존재하지 않는 메뉴는 빈 화면을 신규 생성하지 않습니다.

# 4-A. 메뉴 확정 기준 및 의사결정 규칙

## 1. 기본 원칙

목표 IA는 최종 확정된 메뉴 목록이 아니라 **메뉴 재분류를 위한 기준 구조**입니다.

개발자는 현재 코드와 실제 구현 기능을 확인한 뒤 AS-IS → TO-BE 매핑을 작성해야 합니다.

메뉴 확정 시 다음 우선순위를 적용합니다.

1. 기존 기능 및 사용자 업무 흐름 보존
2. 기능의 목적과 사용자 관점의 명확성
3. 중복 메뉴 최소화
4. 앱 간 역할과 책임 구분
5. 향후 기능 확장성
6. 구현 비용 및 기존 코드 변경 최소화

**메뉴 개수 제한이나 목표 IA에 맞추기 위해 기존 기능을 삭제·축소·병합해서는 안 됩니다.**

## 2. 앱 분류 기준

메뉴가 속할 앱은 해당 기능의 **주요 사용자 목적**을 기준으로 결정합니다.

| 판단 기준 | 소속 앱 |
|---|---|
| AI 답변에서 브랜드 언급·인용 여부를 확인하거나 분석 | AI 가시성 |
| AI 관측 대상 프롬프트를 조사·설계·관리 | AI 가시성 |
| Google 검색 성과, 검색어·페이지 성과 분석 | 검색·콘텐츠 |
| 웹페이지 상태 진단, 콘텐츠 개선 과제 관리 | 검색·콘텐츠 |
| YouTube 영상·채널 및 관련 AI 노출 관리 | YouTube |
| 조직·브랜드·사용자·권한·연결 설정 | 관리 |
| 전체 서비스의 주요 변화와 다음 행동 안내 | 홈 |

### 복수 앱에 관련된 기능

하나의 기능이 여러 앱에서 사용되더라도 **정식 메뉴 소속은 하나만 지정**합니다.

다른 앱에서는 Deep Link, CTA 또는 관련 항목 링크로 접근하게 합니다.

예시:

- AI 가시성에서 발견한 문제 → 검색·콘텐츠의 `개선 기회` 상세로 이동
- 검색 성과에서 특정 URL 선택 → `URL 인스펙터`로 이동
- 홈의 이상 징후 카드 → 해당 앱의 분석 화면으로 이동

동일 기능을 여러 앱에 중복 구현하지 않습니다.

## 3. 메뉴 유지·통합·분리 판단 규칙

### 3.1 기존 메뉴 유지

다음 조건에 해당하면 기존 메뉴를 유지하는 것을 기본값으로 합니다.

- 사용 목적이 명확함
- 다른 메뉴와 실질적인 기능 중복이 없음
- 독립적으로 반복 사용되는 업무임
- 기존 데이터·권한·라우팅과 정상 연결되어 있음

명칭 변경이나 앱 이동이 필요하더라도 기존 기능은 그대로 유지합니다.

### 3.2 메뉴 통합

다음 조건을 대부분 충족할 때만 통합을 제안할 수 있습니다.

- 동일한 사용자 질문을 해결함
- 분석 대상 또는 주요 데이터 컨텍스트가 같음
- 필터·기간·브랜드 등의 상태를 자연스럽게 공유할 수 있음
- 하나의 화면에서 탭이나 섹션으로 제공하는 것이 더 이해하기 쉬움
- 기존 기능과 접근 경로를 손실 없이 보존할 수 있음

**통합은 개발자가 독자적으로 결정하지 않습니다.**

통합 후보는 기존 화면별 기능 차이, 통합 후 화면 구조, 영향 범위를 보고한 뒤 승인을 받습니다.

예시:

`AI 가시성 대시보드 / 가시성 개요 / 브랜드 가시성`

세 화면은 중복 가능성이 있으므로 검토 대상이지만, 이름이 유사하다는 이유만으로 통합하지 않습니다.

### 3.3 메뉴 분리

다음 조건에 해당하면 메뉴 분리를 검토합니다.

- 서로 다른 사용자 질문을 해결함
- 주요 데이터 대상 또는 업무 목적이 다름
- 독립적인 필터·상태·작업 흐름이 필요함
- 한 화면에 함께 배치했을 때 복잡도가 증가함
- 독립적으로 자주 접근하는 기능임

예시:

`인용 분석`과 `프롬프트 라이브러리`는 업무 목적이 다르므로 별도 메뉴가 적절합니다.

단, 목표 IA에 명시되어 있다는 이유만으로 기존 단일 화면을 반드시 분리해야 하는 것은 아닙니다.

### 3.4 신규 메뉴 생성

다음 조건을 모두 충족해야 신규 메뉴를 생성할 수 있습니다.

1. 실제 구현된 기능 또는 승인된 개발 범위가 존재함
2. 기존 메뉴에 배치하기 어려운 명확한 사용자 목적이 있음
3. 중복되는 기존 메뉴가 없음
4. 사용자에게 독립적인 진입점이 필요함
5. 메뉴 생성에 대한 승인을 받음

**미구현 기능을 위한 빈 메뉴나 Placeholder 화면은 생성하지 않습니다.**

## 4. LNB 메뉴와 페이지 탭 구분

다음 기준을 적용합니다.

| 구분 | LNB 메뉴 | 페이지 탭 |
|---|---|---|
| 주요 목적 | 서로 다른 기능 이동 | 동일 기능의 분석 관점 변경 |
| 데이터 대상 | 달라도 됨 | 기본적으로 동일하거나 밀접하게 연결 |
| 필터 | 독립적일 수 있음 | 공통 필터 활용 가능 |
| 사용자 업무 | 서로 다른 작업 | 동일 작업의 관점 전환 |
| URL | 독립 라우트 권장 | 상태 공유 및 직접 접근 가능해야 함 |

예시:

**LNB 분리가 적절한 경우**
- 프롬프트 라이브러리 / 프롬프트 전략
- URL 인스펙터 / 개선 기회
- 영상 관리 / 수집 이력

**페이지 탭이 적절한 경우**
- AI Overview / AI Mode
- 검색어 / 페이지 / 국가 / 디바이스
- 동일 URL의 개요 / 인용 / 변경 이력

탭과 LNB 중 어느 쪽이 적절한지 불분명하면, 현재 사용자 업무와 기존 기능 관계를 확인한 후 결정합니다.

## 5. 화면 및 메뉴 명칭 결정 규칙

메뉴 이름은 내부 기술 명칭보다 사용자가 이해할 수 있는 업무 용어를 우선합니다.

- 서로 다른 메뉴에 동일하거나 유사한 명칭을 반복하지 않습니다.
- `대시보드`, `개요`, `분석`이라는 추상적인 메뉴가 불필요하게 중복되지 않도록 합니다.
- `관리`, `설정`, `운영`은 실제 기능 목적에 따라 구분합니다.
- Provider 이름이나 내부 구현 기술을 고객용 메뉴명에 불필요하게 노출하지 않습니다.
- 기존 사용자에게 익숙한 명칭은 변경 효과가 명확하지 않으면 유지합니다.

명칭 변경 시에는 기존 명칭, 제안 명칭, 변경 이유를 매핑 표에 기록합니다.

## 6. 고객 기능과 내부 운영 기능 구분

기능의 주 사용자를 기준으로 구분합니다.

| 기능 성격 | 노출 위치 |
|---|---|
| AI 관측 결과 및 수집 상태 확인 | AI 가시성 |
| 고객이 직접 수행하는 승인된 수집 작업 | 해당 업무 앱 |
| Provider Task 관리·강제 재시도 | 내부 운영 도구 |
| API 응답 검증 및 디버깅 | 내부 운영 도구 |
| 데이터 연결 및 조직별 설정 | 관리 |
| 보고서 조회·다운로드 | 해당 업무 앱 |

내부 운영 기능은 메뉴를 숨기는 것만으로 접근 제한을 완료한 것으로 간주하지 않습니다. 기존 서버 측 권한 검사를 유지해야 합니다.

기존 고객 기능을 내부 기능으로 재분류해야 하는 경우에는 사용 현황과 영향을 확인하고 승인을 받습니다.

## 7. 상세 화면의 메뉴 처리 규칙

상세 화면은 원칙적으로 별도 LNB 메뉴를 생성하지 않습니다.

다음 조건을 충족하는 경우 드릴다운으로 처리합니다.

- 특정 목록·분석 결과·항목에서 진입함
- 상위 메뉴의 업무 목적을 그대로 공유함
- 개별 항목 확인이나 편집이 주목적임

상세 화면에서는 다음 정보를 유지합니다.

- 상위 앱 및 LNB 활성 상태
- 브레드크럼
- 상위 목록으로 돌아가기
- 기존 검색·필터·정렬·페이지 상태
- 직접 URL 접근 가능 여부

단, 상세 화면 자체가 독립적으로 반복 사용되는 주요 기능이라면 별도 메뉴 승격을 제안할 수 있습니다. 이 경우 승인받아야 합니다.

## 8. 메뉴 충돌 및 예외 판단

여러 앱에 속할 수 있거나 통합 여부가 불분명한 기능은 다음 순서로 결정합니다.

1. 사용자가 해당 기능을 사용하는 주된 목적 확인
2. 현재 실제 화면에서 수행하는 작업 확인
3. 다른 메뉴와의 기능·데이터 중복 확인
4. 가장 자연스러운 단일 메뉴 소속 제안
5. 다른 앱에서 필요한 진입 경로 정의
6. 기존 기능·권한·라우팅 영향 확인
7. PM 승인 후 최종 반영

판단이 불명확한 경우 기존 구조를 유지하고 검토 대상으로 표시합니다.

**모호함을 해결하기 위해 임의로 새로운 메뉴를 만들거나 기존 기능을 삭제하지 않습니다.**

## 9. 의사결정 권한

| 결정 항목 | 개발자 권한 |
|---|---|
| 기존 메뉴의 현황 조사 | 자율 수행 |
| AS-IS → TO-BE 매핑 제안 | 자율 제안 |
| 승인된 메뉴 구조의 UI 구현 | 수행 가능 |
| 기존 화면 재사용 및 공통 컴포넌트 정리 | 기능 불변 범위에서 수행 가능 |
| 기존 메뉴 통합·삭제 | 사전 승인 필요 |
| 신규 메뉴 및 화면 추가 | 사전 승인 필요 |
| 기존 URL 계약 변경 | 사전 승인 필요 |
| 데이터 모델·API·권한 로직 변경 | 별도 승인 필요 |
| 미구현 기능 신규 개발 | 별도 기획·개발 승인 필요 |

## 10. 메뉴 확정 절차

### Step 1. 현황 조사

전체 기존 메뉴와 실제 구현 기능을 확인합니다.

### Step 2. 매핑 작성

각 메뉴의 유지·이동·명칭 변경·통합 후보·분리 후보·미구현 여부를 구분합니다.

### Step 3. 충돌 검토

다음 사항을 별도로 정리합니다.

- 중복 가능성이 있는 메뉴
- 여러 앱에 걸쳐 있는 기능
- 고객용과 내부용 구분이 필요한 기능
- 목표 IA에는 있으나 현재 구현되지 않은 메뉴
- 기존 URL 및 권한 영향이 있는 변경

### Step 4. 메뉴 확정 승인

PM 검토를 통해 최종 앱 소속, 명칭, 통합·분리 여부를 결정합니다.

### Step 5. 구현

승인된 IA 범위 안에서 GNB, LNB, 라우팅, 상세 탐색 UX를 변경합니다.

### Step 6. 회귀 검증

기존 기능의 접근성과 동작이 유지되는지 확인합니다.

## 11. 최종 승인 기준

다음 조건을 모두 충족하면 메뉴 구조를 확정할 수 있습니다.

- 모든 기존 기능의 신규 위치가 정의됨
- 기능이 누락되거나 임의로 제거되지 않음
- 각 메뉴의 주요 사용자 목적이 명확함
- 중복 메뉴에 대한 처리 방침이 정해짐
- 여러 앱에 관련된 기능의 정식 소속이 하나로 정의됨
- 필요한 Cross-app Deep Link가 식별됨
- 기존 URL과 권한 정책의 영향이 정리됨
- 미구현 메뉴와 후속 개발 범위가 구분됨
- PM이 최종 메뉴 매핑을 승인함

---

**개발자 최종 지시**

Phase 0에서는 메뉴를 실제로 변경하지 말고, 위 기준에 따라 **AS-IS → TO-BE 메뉴 매핑 및 의사결정이 필요한 항목**을 먼저 제출해 주세요.

특히 `가시성 대시보드 / 가시성 개요 / 브랜드 가시성`, `개선 기회`, `수집 실행`, `YouTube`의 메뉴 소속과 분리·통합 여부를 중점적으로 검토해 주세요.

명확하게 판단할 수 없는 항목은 기존 기능을 유지한 상태로 `PM 결정 필요`로 표시합니다.

### 4.1 홈

홈은 모든 메뉴를 나열하는 화면이 아니라 현재 상태와 다음 행동을 안내하는 Action Hub로 구성합니다.

주요 정보:

- AI 가시성 핵심 지표 및 주요 변화
- 검색 및 YouTube 이상 징후
- 최근 수집 상태
- 우선 확인할 개선 기회
- 최근 리포트
- 앱별 바로가기

각 카드의 CTA에는 이동 목적지를 명확하게 표시합니다.

예시:
- `AI 가시성에서 확인`
- `검색 성과 확인`
- `개선 기회 보기`
- `YouTube 모니터링 열기`

실제 데이터가 없는 항목은 임의로 생성하지 않고 기존 데이터와 화면을 활용합니다.

### 4.2 AI 가시성

```text
AI 가시성
│
├─ 개요
│   └─ 가시성 대시보드
│
├─ 분석
│   ├─ 가시성 분석
│   ├─ 인용 분석
│   └─ 경쟁 분석
│
├─ 프롬프트
│   ├─ 프롬프트 리서치
│   ├─ 프롬프트 라이브러리
│   └─ 프롬프트 전략
│
└─ 운영
    ├─ 수집 현황
    └─ 리포트
```

**주의사항**

- 기존 `가시성 개요`, `브랜드 가시성`, `AI 가시성 대시보드`의 기능 중복을 먼저 조사합니다.
- 기존 분석 기능을 임의로 합치거나 제거하지 않습니다.
- `가시성 분석 / 인용 분석 / 경쟁 분석`은 목표 분류이며, 신규 분석 기능 개발을 의미하지 않습니다.
- AI 가시성은 Google AI Overview 및 AI Mode 중심으로 구성합니다.
- 일반 Google Organic 검색 순위를 AI 가시성 KPI에 혼합하지 않습니다.
- 브랜드 언급과 URL 인용은 별개의 분석 지표로 유지합니다.
- Provider Task 관리, 재시도, 내부 디버깅 등은 고객용 `수집 현황`과 분리합니다.

### 4.3 검색·콘텐츠

```text
검색·콘텐츠
│
├─ 개요
│   └─ 검색·콘텐츠 대시보드
│
├─ 검색
│   ├─ 검색 트렌드
│   └─ 검색 성과(GSC)
│
└─ 콘텐츠
    ├─ URL 인스펙터
    └─ 개선 기회
```

**개선 기회 운영 원칙**

`개선 기회`는 단순한 SEO 진단 목록이 아니라, AI 관측 결과와 콘텐츠 개선 작업을 연결하는 실행 허브입니다.

다음 정보와 연결 가능한 구조를 유지합니다.

- 관측된 AI 답변 및 프롬프트
- 브랜드 언급 및 인용 URL
- 경쟁 URL과 목표 URL
- 콘텐츠 진단 결과
- 개선 가설 및 실행 상태
- 변경 이력과 재측정 결과

이번 IA 작업에서 해당 기능을 새로 개발하는 것은 아닙니다. 기존 기능과 링크를 유지하고 향후 확장 가능한 메뉴 구조를 확보하는 것이 목적입니다.

**Cross-app 이동 예시**

```text
AI 가시성
  └─ 인용 분석
      └─ 특정 프롬프트 상세
          └─ 개선 기회 보기
              ↓
검색·콘텐츠
  └─ 개선 기회
      └─ 해당 개선 기회 상세
```

AI 가시성에서 개선 기회로 이동하더라도 기능을 중복 생성하지 않고 단일 화면을 재사용합니다.

`robots.txt`, FAQ, 구조화 데이터 등의 개별 진단 유형은 LNB 메뉴로 추가하지 않고 개선 기회 내부의 필터·카드·상세 화면으로 구성합니다.

### 4.4 YouTube

```text
YouTube
│
├─ 개요
│   └─ YouTube 대시보드
│
├─ 분석
│   └─ AIO 모니터링
│
├─ 콘텐츠
│   └─ 영상 관리
│
└─ 운영
    ├─ 수집 이력
    └─ 채널 설정
```

YouTube는 독립 앱 진입점으로 분류하되, 실제 구현된 기능과 업무 흐름을 먼저 확인합니다.

기존 기능이 없는 메뉴를 채우기 위해 신규 기능을 만들지 않습니다. 메뉴가 지나치게 비어 보이는 경우에는 현행 기능에 맞춰 LNB를 단순화합니다.

### 4.5 관리

```text
관리
│
├─ 워크스페이스
│   ├─ 조직 관리
│   └─ 브랜드 관리
│
├─ 사용자
│   └─ 사용자 및 권한
│
├─ 연결
│   ├─ 데이터 연결
│   └─ 수집 설정
│
├─ 기록
│   └─ 변경 이력
│
└─ 운영 도구 [내부 권한 전용]
    ├─ Provider 작업 관리
    ├─ 수집 재시도 및 실패 확인
    └─ 내부 검증 도구
```

`운영 도구`는 기존에 구현된 내부 기능이 있는 경우에만 노출합니다.

일반 사용자에게 내부 Task 실행, API 디버깅, Provider 검증 기능을 노출하지 않습니다. 메뉴 숨김뿐 아니라 기존 서버 측 접근 권한도 유지해야 합니다.

## 5. 내비게이션 정책

### 5.1 메뉴 깊이

| 단계 | UI | 역할 |
|---|---|---|
| 전역 | 헤더 | 조직·브랜드·사용자 컨텍스트 |
| 1뎁스 | GNB | 앱 전환 |
| 2뎁스 | LNB | 앱 내부 주요 기능 |
| 3뎁스 | 페이지 탭 | 동일 기능의 분석 관점 전환 |
| 상세 | 드릴다운 | 개별 항목 확인 및 편집 |

권장 수량:

- GNB: 최대 5개
- 앱별 LNB: 가급적 7~9개 이하
- 페이지 탭: 가급적 5개 이하

이는 권장 기준이며 기능을 임의로 제거하기 위한 절대적인 제한은 아닙니다.

### 5.2 LNB

- 현재 선택한 앱의 메뉴만 표시합니다.
- 메뉴 그룹은 기본적으로 고정된 섹션 라벨을 사용합니다.
- 메뉴가 많지 않다면 아코디언은 사용하지 않습니다.
- 현재 메뉴의 Active 상태를 명확하게 표시합니다.
- 상세 화면에서도 상위 LNB 메뉴의 Active 상태를 유지합니다.
- 권한 및 기능 활성화 여부에 따라 메뉴 표시를 제어합니다.

### 5.3 페이지 탭

탭은 동일한 대상이나 분석 컨텍스트를 공유하는 경우에만 사용합니다.

적절한 예:

```text
검색 성과
  검색어 | 페이지 | 국가 | 디바이스

AI 가시성
  전체 | AI Overview | AI Mode

URL 상세
  개요 | 인용 | 변경 이력
```

서로 다른 목적을 가진 `영상 관리 / 프롬프트 관리 / 수집 이력` 등을 단순히 한 화면의 탭으로 묶지 않습니다.

## 6. 상세 화면과 복귀 UX

상세 페이지는 독립 LNB 메뉴로 추가하지 않고 드릴다운으로 처리합니다.

예시:

```text
검색·콘텐츠 > 개선 기회 > robots.txt 진단

← 개선 기회로 돌아가기

robots.txt 진단 결과
...
```

공통 요구사항:

1. 브레드크럼 표시
2. 상위 목록으로 돌아가기 제공
3. 상세 진입 전 검색어·필터·정렬·페이지 상태 보존
4. 상세 화면에서도 상위 LNB Active 상태 유지
5. 목록 기반 상세 화면에서 이전·다음 항목 이동 지원 검토
6. 새로고침이나 직접 URL 접근 시에도 올바른 앱 및 메뉴 활성화
7. 브라우저 뒤로 가기·앞으로 가기 정상 동작

목록 상태 보존은 기존 라우터 및 URL Query Parameter 구조를 우선 활용합니다.

## 7. 통합 검색 — 후속 단계

전역 검색은 이번 1차 필수 구현에 포함하지 않습니다.

향후 Command Palette 형태로 다음 검색을 지원할 수 있도록 확장성을 고려합니다.

- 메뉴 및 페이지
- 실행 가능한 기능
- 브랜드와 콘텐츠
- 최근 방문 화면
- 도움말

예시:

```text
검색: "구글 연결"

기능
  GSC 연결 설정

페이지
  검색 성과
  데이터 연결

도움말
  GSC 권한 설정 방법
```

별도의 검색 인프라나 신규 백엔드를 이번 IA 개편 목적으로 도입하지 않습니다.

| 기회 | 기존 경로 | 검색·콘텐츠 | 개선 기회 | 유지·이동 |

위 표는 예시이며 실제 코드 조사 결과에 따라 확정합니다.

- 기존 사용자 권한 유지
- 권한 없는 메뉴 및 화면 접근 차단
- 내부 운영 기능 일반 사용자 접근 제한
- 앱 전환으로 인한 조직·브랜드 간 데이터 노출 없음

**UI**

- 데스크톱 및 모바일 내비게이션 정상
- 메뉴 길이 증가 시 레이아웃 문제 없음
- 상세 페이지 및 빈 데이터 상태에서 UI 정상
