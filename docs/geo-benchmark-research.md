# GEO 경쟁 제품 리서치 로그

목적: 경쟁/유사 제품 자료를 계속 모아두고, 다 모인 뒤 한 번에 정리해서
기획 → 작업 순서로 진행한다. 지금 단계에서는 **분석만 쌓아두고 코드/앱
콘텐츠(help.ts 등)에는 반영하지 않는다.**

각 항목: 원문 출처 요약 → 우리 제품과 비교했을 때 눈에 띄는 점 → 반영
여부 판단(반영 검토/이미 있음/방향 다름)은 전체 리서치가 끝난 뒤 마지막에
한 번에 정리한다. 지금은 "관찰"만 기록.

---

## 2026-09-23 — VIVI (Content Assistant + Insight/Action)

### 원문 요약
- **VIVI Content Assistant**: 크롬 사이드패널 확장 프로그램. 지금 보고
  있는 페이지를 9개 모듈(AI 크롤러 접근성, 구조화 데이터, 메타데이터,
  인용 신뢰도 등)로 진단, 100점 환산 점수 제공. CMS 편집 화면에서는
  JSON-LD·메타데이터·FAQ를 바로 삽입 가능한 형태로 생성. 자체 포함 HTML
  리포트로 공유, 최근 진단 40개 이력 보관.
- **VIVI Insight**: 국내외 AI 엔진 6개(Naver AI Briefing, Google AI
  Overview, AI Mode, Gemini, Perplexity, ChatGPT — Claude/Bing/Yahoo는
  지원 예정)에서 동일 질문의 답변을 수집. Mention Rate·Citation
  Rate·Share of Voice·Visibility Funnel(단계별 이탈) 4개 지표로 측정.
  플랜별로 엔진/프롬프트 수 다르고, 브랜드 아래 프로젝트 단위로 구분.
- **VIVI Action**: Insight가 찾은 약점에 대응하는 콘텐츠 생성/개선 실행.
  취약 토픽 → 콘텐츠 생성, 통이미지 상세페이지 → AI가 읽는 텍스트(PDP
  변환)로 전환. 실행 후 같은 지표로 재측정.
- 사용 흐름: Setup(최초 1회) → Metrics → Topics → Topic Research →
  Pages, 이후 매주 같은 순서로 반복.

### 관찰 (우리 제품과 비교)
- **없는 개념**: 구조화 데이터(JSON-LD) 진단/생성이 별도 기회 유형으로
  없음. 언급→인용 단계별 퍼널 뷰가 없음(우리는 독립된 숫자만). 수집
  엔진이 네이버 AI검색·구글 AI Overview 2개뿐(Perplexity/ChatGPT/Gemini
  없음).
- **개념은 있는데 형태가 다름**: Share of Voice ≈ 우리 브랜드 가시성의
  마켓 트래킹 비교. PDP 변환 ≈ 우리 멀티미디어 가시성 보강. 진단 이력
  40개 ≈ 우리 토픽 상세의 "수집 로그별 변화".
- **배포 형태 자체가 다른 것**: 크롬 익스텐션형 실시간 단일 페이지
  진단(CMS 편집 화면에 바로 삽입) — 우리는 사이트맵 전체 크롤 기반
  대시보드. 별도 프로덕트 라인에 가까움.

## 2026-09-23 — VIVI 공식 문서 (Getting Started 4편)

### 원문 요약
- **제품 개요**: AI 답변은 검색 결과와 달리 순위가 없고 질문 하나에
  답변 하나 — 언급 안 되면 그 화면엔 아예 존재하지 않는다는 게 측정
  필요성의 근거. 측정(Insight) → 실행(Action) → 재측정(Insight)이
  한 번으로 안 끝나고 반복되는 루프. 개선 반영 표시를 한 시점의
  인용률을 **기준선(baseline)**으로 기록해두고, 그 대비 상승폭을
  산출한다.
- **계정 구조**: Organization(계약 단위) > Brand(측정 대상 브랜드,
  이름 변형+공식 도메인 등록) > Project(실제 측정 단위 — 국가·엔진·
  자동수집 설정, 국가 하나만 가짐이라 시장별로 Project를 나눔). 지표는
  Project 단위 집계, Project끼리 합산 안 함. 탭 구성: Brand / **Brand
  Voice**(생성물 어조·표현 규칙, PDP Convert·Page Optimizer·Localizer에
  공통 적용) / Project / Competitor / Integrations / Reports / Plan &
  usage / Access. 질문 추가/삭제는 별도 화면(Topics의 Modify Prompts)에서.
- **측정 방식**: 단위는 Category(선택, Topic 묶음) > Topic(검색 키워드
  1개 대응, 측정 여부 결정 단위) > Prompt(실제 전송 문장). 파이프라인:
  ①승인된 Prompt 세트 ②AI 엔진 질의(Prompt×엔진 전 조합) ③답변 원문+
  출처 URL 저장 ④언급/인용 판정 ⑤날짜·엔진·Topic별 집계. 수집은 주
  1회, 한국시간 자정 직후 시작·오전 6시경 집계, 요일은 온보딩일 기준
  Organization마다 다름. **답변 변동성**을 정면으로 문서화 — 같은 질문도
  매번 다르게 답하는 게 정상이라 하루 숫자가 아닌 추이로 판단하라고
  안내. 고객이 "내가 직접 물어보니 나오던데 왜 0%냐"는 문의에 대한
  공식 답변까지 문서화(질문 문구·계정·지역·시점이 다 다르기 때문).
  판단 기준 3가지: ①자사 지표 추이(가장 신뢰) ②Share of Voice(경쟁사
  대비 상대 위치) ③**AI Existence**(그 주제로 AI 답변 자체가 생성되는
  비율 — 이게 낮으면 Mention이 낮은 원인이 콘텐츠가 아니라 "애초에 AI가
  답을 안 만듦"). 피해야 할 해석도 명시: 인과 단정 금지(모델 자체가
  갱신되면 아무것도 안 해도 숫자가 움직임), SoV를 실제 시장점유율로
  착각 금지(등록한 Competitor 안에서의 비중일 뿐).
- **AI 엔진별 특성**: 최대 7개 엔진 — ChatGPT(대화형), Google(검색 내
  AI Overview), Google AI Mode(검색과 분리된 대화형), NAVER(AI
  브리핑, 한국어만, 브리핑 내 쇼핑카드는 인용이 아니라 "제품 노출"로
  별도 표시), NAVER AI Tab(대화형, rollout 켜진 계정만), Gemini(대화형),
  Perplexity(출처 표기 전제). 엔진 간 절대 비교를 하지 말라고 명시 —
  엔진마다 출처를 다는 습성 자체가 달라서(Perplexity는 거의 항상,
  어떤 엔진은 드물게) 인용률 차이가 성과 차이가 아니라 엔진 성격 차이일
  수 있음. Google 계열 인용은 검색 결과의 중간 리다이렉트 링크가 아니라
  실제 도착 페이지 주소로 정리해서 저장. Google AI Overview·NAVER AI
  브리핑은 검색 결과 안에 뜨는 블록이라 질문에 따라 아예 안 뜰 수 있음
  — 그래서 이 두 엔진은 AI Existence가 구조적으로 낮게 나오고, Mention
  Rate를 읽을 때 반드시 AI Existence를 같이 보라고 안내.

### 관찰 (우리 제품과 비교)
- **AI Existence 개념이 우리한텐 없음**: 우리는 수집 실행의 성공/실패
  (봇 차단 등)만 구분하지, "그 프롬프트에 대해 AI가 애초에 답변 블록을
  만들었는지"를 별도 지표로 안 본다. 특히 우리가 이미 다루는 Google AI
  Overview는 문서에 따르면 구조적으로 안 뜨는 경우가 많은 엔진이라,
  우리 "미노출" 판정이 "콘텐츠 문제"인지 "애초에 AI Overview 자체가 그
  질문엔 안 뜨는 것"인지 구분이 안 될 수 있음 — 지표 해석에 영향.
- **수집 주기가 근본적으로 다름**: VIVI는 주 1회 자동 배치, 우리는
  사람이 로컬에서 수동으로 트리거. 이건 이미 로드맵(db-collection-
  pipeline)에 있는 "AI 수집 파이프라인의 서버 실행" 항목과 직결.
- **계정 구조(Org>Brand>Project)가 우리 "다중 조직" 로드맵과 겹침**:
  특히 "같은 브랜드, 다른 시장은 Project 추가"라는 규칙은 우리가 지금
  마켓을 브랜드 하위 속성(markets 배열)으로만 다루는 것과 다른 모델 —
  나중에 다중 조직/다중 시장 설계할 때 참고할 만한 대안 구조.
- **Brand Voice(어조·표현 규칙)를 여러 생성 기능에 공통 적용하는 개념이
  없음**: 우리는 LLM 브릿지 기능(가이드 등록 등)마다 어조 설정이 없음.
  LLM API 연동 이후 콘텐츠 생성 기능이 늘어나면 브랜드 톤 일관성 문제가
  생길 수 있어 참고할 만함.
- **Localizer(다른 시장 언어로 페이지 재작성) 개념이 없음**: 우리는
  마켓별 콘텐츠 현지화 기능 자체가 없음.
- **"기준선(baseline) 기록 후 상승폭 산출" 메커니즘**: 우리도 "수정
  완료 확인" 재크롤이 있지만, 그건 크롤 점수(가독성 등) 재검증이지
  실제 언급/인용률의 전/후 비교가 아님. VIVI는 반영 시점의 인용률
  자체를 기준선으로 못박고 그 이후 실측 상승폭을 보여줌 — 더 설득력
  있는 "효과 증명" 방식일 수 있음.
- **해석 가이드 문서화 자체가 좋은 패턴**: "답변 변동성은 정상", "직접
  물어본 결과와 다를 수 있는 이유", "인과 단정 금지", "SoV는 시장
  점유율이 아님" 같은 안내를 공식 문서에 미리 박아두는 방식은, 우리
  도움말에도 비슷한 "숫자를 어떻게 읽어야 하는지" 섹션이 없어서 참고할
  가치가 있음(특히 우리도 감성/언급 수가 실행마다 흔들릴 수 있는 구조).
